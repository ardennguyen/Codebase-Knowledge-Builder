    prompts.py

    Source: utils/prompts.py

    Following the console logging, terminal styling, and localized string management provided by output.py, the prompts.py module encapsulates prompt loading, inline prompt generation, and model response extraction. It decouples the synthesis pipeline's prompt lifecycle from model invocation drivers, providing unified filesystem loaders for Markdown prompt templates and robust parsing routines for model-generated YAML data structures and file indices.

    Technical Overview

    The prompts.py module provides centralized prompt construction and response parsing utilities across the repository documentation pipeline. Upstream workflow graph nodes in nodes.py require structured communication with Large Language Models (LLMs) across multiple operational modes, including tutorial, advanced, api-reference, and sdk. This module abstracts prompt template locations on disk, ensures safe UTF-8 file reading with Byte Order Mark handling, dynamically generates specialized inline prompts, and extracts structured data from LLM text completions.

    A critical design requirement of the response parsing layer is defense against silent failure modes caused by LLM output truncation. When model completions hit max token ceilings, partial YAML blocks can sometimes be parsed as incomplete data structures (such as truncated lists or dictionaries), leading to silently dropped files or corrupted chapter structures. The module prevents this by validating response objects for truncation sentinels (such as TruncatedResponse defined in llm_common.py) prior to YAML parsing, failing fast with explicit exceptions that prompt workflow nodes to retry.

    Public API

    parse_file_index()

    Visibility: Public
    Signature: def parse_file_index(idx_value) -> int | None:

    Description: Extracts the first continuous sequence of numeric digits from an LLM-generated file index representation and converts it into an integer. LLM outputs referencing file indices frequently deviate from strict numeric formats, producing annotated strings such as "3 # path/to/file.py", range indicators such as "0-3", or standard integers. This function applies a regular expression match to isolate the leading integer value, returning None if no numeric characters exist.

    Parameters: * idx_value (Any): The raw input representation from the LLM, which can be an integer, string, or mixed object.

    Returns: * int | None: The first parsed integer index, or None if no numeric digits are detected.

    Raises: * No exceptions are raised directly; unparseable non-digit representations safely return None.

    Example: 

    def parse_file_index(idx_value):
    """Extract the first integer from an LLM-returned file index value.

    Handles multiple formats the LLM may produce:
    - Plain int: 3
    - Annotated string: "3 # path/to/file.py"
    - Range notation: "0-3" → returns first number only (caller handles ranges)

    Returns:
        int or None if no digits found.
    """
    nums = re.findall(r"\d+", str(idx_value))
    return int(nums[0]) if nums else None

    Under the hood, parse_file_index() coerces idx_value to a string using str(idx_value) before running re.findall(r"\d+", ...). This design accommodates heterogeneous types produced by YAML deserialization, such as native Python integers, floats, or raw strings. If multiple numeric segments exist (such as range notations like "0-3" or annotated lines like "12 # src/utils/token.py:44"), it deliberately selects the first integer group nums[0]. Downstream callers in nodes.py handle higher-level range expansion or index validation against the repository's file list.

    load_prompt_template()

    Visibility: Public
    Signature: def load_prompt_template(template_name, advanced_mode=False, mode=None) -> str:

    Description: Locates and loads a Markdown prompt template file from the repository's prompts/ directory hierarchy. The function resolves the target subdirectory based on explicit execution modes (tutorial, advanced, api-reference, sdk, or common) with backward-compatible fallback behavior for legacy boolean flags. It reads the file using the utf-8-sig encoding to eliminate Byte Order Marks and emits an operational debug trace to the disk audit log.

    Parameters: * template_name (str): Base name of the Markdown template file without the .md extension (e.g., "identify_abstractions", "draft_chapters"). * advanced_mode (bool, optional): Legacy fallback flag used when mode is None. If True, resolves to the "advanced" directory; otherwise defaults to "tutorial". Defaults to False. * mode (str | None, optional): The execution mode string specifying the target subdirectory inside prompts/. Overrides advanced_mode when provided. Defaults to None.

    Returns: * str: The decoded text content of the target Markdown template file.

    Raises: * FileNotFoundError: If the resolved template path does not exist on disk. * OSError: If the filesystem encounters an I/O error while reading the file.

    Example: 

    def load_prompt_template(template_name, advanced_mode=False, mode=None):
    """Load a prompt template file from the prompts/ directory."""
    if mode is None:
        prompt_dir = "advanced" if advanced_mode else "tutorial"
    else:
        prompt_dir = mode

    path = os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "prompts", prompt_dir, f"{template_name}.md")
    with open(path, encoding="utf-8-sig") as f:
        content = f.read()
    from utils.output import emit_raw

    emit_raw("DEBUG", f"load_prompt_template | loaded '{template_name}.md' from prompts/{prompt_dir}/", dest="LOG")
    return content

    The function computes the absolute root path of the project using os.path.dirname(os.path.dirname(os.path.abspath(__file__))), navigating two levels up from utils/ to ensure path resolution remains invariant regardless of the current working directory. Opening with utf-8-sig guarantees that Markdown templates authored or modified across different operating systems—specifically Windows text editors that introduce a UTF-8 BOM—do not inject hidden zero-width non-breaking spaces (\ufeff) into the prompt payload. The logging invocation uses a deferred local import (from utils.output import emit_raw) with dest="LOG", routing prompt loading traces strictly to file logs without polluting interactive console output.

    parse_yaml_response()

    Visibility: Public
    Signature: def parse_yaml_response(response) -> Any:

    Description: Extracts, strips, and deserializes a YAML document enclosed within triple-backtick Markdown fences (```yaml ... ```) from an LLM completion response. Prior to extraction, it checks for a truncated attribute on the response object; if detected, it aborts execution immediately by raising a ValueError. This protects upstream pipeline nodes from parsing incomplete YAML payloads that could silently drop classes, modules, or chapter mappings.

    Parameters: * response (str | Any): The raw string response from the LLM or an instance of a string subclass (such as TruncatedResponse from llm_common.py).

    Returns: * Any: The deserialized Python data structure (typically a list or dict) produced by yaml.safe_load.

    Raises: * ValueError: Raised if the response was flagged as truncated (getattr(response, "truncated", False) is True), if the response lacks the ```yaml code block delimiter, or if yaml.safe_load fails to parse the extracted string.

    Example: 

    def parse_yaml_response(response):
    """Extract and parse YAML from an LLM response fenced in ```yaml blocks."""
    # A reply cut off at max tokens (llm_common.TruncatedResponse) can still contain a parseable
    # fenced prefix that silently drops items — raise so the node retries instead.
    if getattr(response, "truncated", False):
        raise ValueError("LLM response was truncated before the YAML block completed")
    try:
        yaml_str = response.strip().split("```yaml")[1].split("```")[0].strip()
        return yaml.safe_load(yaml_str)
    except Exception as e:
        raise ValueError(f"Failed to parse YAML: {e}") from e

    The method isolates the YAML block by performing sequential string splits: splitting on "```yaml" to isolate the opening fence, selecting index 1, splitting on "```" to strip trailing text, and taking index 0. Wrapping the parsing logic in a broad try-except block guarantees that formatting irregularities—such as missing closing backticks, unclosed quotes, invalid indentation, or an absent ```yaml delimiter—are consistently re-raised as ValueError instances containing the underlying exception message. This exception model signals the calling graph node in nodes.py that retry escalation or model re-prompting is required.

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description: Constructs a specialized, self-contained prompt string used by the DeterministicFileMapper node in api-reference mode. The prompt instructs the LLM to analyze a formatted codebase file listing and filter out non-code assets (such as UI markups, build manifests, configuration files, and static assets), returning exclusively the numeric indices of files containing functional source code, classes, and APIs.

    Parameters: * project_name (str): The name or identifier of the project being documented. * file_listing (str): A pre-formatted string of indexed repository files (typically formatted as index-path pairs, such as "0: src/main.py\n1: config.json").

    Returns: * str: The complete prompt payload formatted with system instructions, exclusion constraints, and a few-shot YAML schema example.

    Raises: * No exceptions are raised directly.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The constructed prompt enforces strict categorical exclusions directly in the natural language contract, explicitly listing extensions and file classes that must be omitted (.xaml, .storyboard, .html, .xml, .json, .manifest, .ini, .csproj, .sln). The prompt terminates with a few-shot example instructing the model to wrap its output in a fenced ```yaml block containing an array of integers. This strict output framing guarantees compatibility with downstream processing by parse_yaml_response().

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description: Constructs a structured prompt instructing the model to synthesize a technical brief of an already generated chapter. This brief is fed into the context of subsequent chapter generation passes, maintaining architectural continuity across the documentation set. The prompt enforces a uniform summary structure spanning four distinct technical dimensions: scope and responsibility, key technical elements, implementation patterns and architecture, and system integration and dependencies.

    Parameters: * chapter_num (int): The 1-based numerical index of the chapter being summarized. * abstraction_name (str): The title, architectural concept, or module name of the chapter. * chapter_content (str): The complete Markdown source code of the drafted chapter. * language (str, optional): The target natural language for the output summary. Defaults to "english".

    Returns: * str: The assembled prompt payload ready for submission to the LLM.

    Raises: * No exceptions are raised directly.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.

    The summary captures 4 technical dimensions with 3-5 sentences each:
    1. Component scope & responsibility
    2. Key classes/services/functions and their roles
    3. Implementation patterns & architectural decisions
    4. Inter-component interfaces & dependencies
    """
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The prompt construction logic conditionally prepends an internationalization instruction (lang_instruction) when language differs from "english". It explicitly requires that each of the four numbered dimensions contains between 3 and 5 concise sentences, constraining the LLM from generating overly verbose prose that could exhaust the token budget of subsequent chapter prompts. Appending Chapter {chapter_num}: {abstraction_name} alongside the raw Markdown ensures that the model preserves domain terminology and component identifiers accurately.

    Internal Helpers

    The prompts.py module defines no private or internal helper functions (_-prefixed). All template loaders, parsers, and prompt generators are exposed directly as part of the module's public utility contract.

    Data Structures

    The module does not declare custom object classes or data models. Instead, it defines operational contracts for YAML extraction payloads and dynamic prompt schemas consumed by external pipeline nodes.

    Chapter Summary Structure

    The text structure generated by models responding to build_chapter_summary_prompt(). Downstream drafting nodes inject this text directly into chapter prompt templates:

    Dimension Header Sentence Constraint Description
    (1) **Component Scope & Responsibility** 3–5 sentences Functional boundary, system role, and technical problems solved by the chapter.
    (2) **Key Technical Elements** 3–5 sentences Concrete identifiers, classes, functions, data structures, and APIs defined.
    (3) **Implementation Patterns & Architecture** 3–5 sentences Algorithmic patterns, error handling, protocol implementations, and data flows.
    (4) **System Integration & Dependencies** 3–5 sentences Consumed dependencies, upstream/downstream interfaces, and integration points.

    Error Handling

    The module implements focused error validation centered around LLM output safety and filesystem access:

    • Truncation Detection (ValueError): In parse_yaml_response(), the function checks for response truncation via getattr(response, "truncated", False). When an upstream provider driver flags that output was cut off mid-stream due to max token limits (such as TruncatedResponse in llm_common.py), the function immediately raises a ValueError("LLM response was truncated before the YAML block completed"). This prevents partial YAML lists from passing as valid completions, which would silently omit files or pipeline entities.
    • Malformed YAML Extraction (ValueError): In parse_yaml_response(), missing ```yaml code fences or invalid syntax inside the block raises ValueError(f"Failed to parse YAML: {e}") from e. The original parsing or splitting exception is chained using from e to preserve diagnostic stack traces for debugging.
    • Missing Prompt Templates (FileNotFoundError): If load_prompt_template() attempts to read a non-existent template file, Python's native FileNotFoundError propagates to the caller, highlighting missing template files across mode directories (prompts/advanced/, prompts/tutorial/, prompts/api-reference/, prompts/sdk/).
    • Defensive Index Extraction: parse_file_index() treats malformed, non-numeric, or missing index representations defensively, returning None instead of throwing IndexError or ValueError.
