    prompts.py

    Source: utils/prompts.py

    Technical Overview

    Following the presentation and telemetry infrastructure established in output.py, the prompts.py module serves as the centralized prompt composition, template resolution, and structured response parsing engine for the repository analysis pipeline. It operates as the semantic interface between pipeline orchestrators—such as nodes.py and flow.py—and the downstream inference gateway call_llm.py. The module decouples prompt engineering definitions from workflow execution logic, standardizing how external markdown prompt templates are located, loaded from disk, validated, and converted into concrete LLM instructions.

    The component addresses critical failure modes inherent in large language model pipelines: non-deterministic output structures, silent truncation of structured formats, and inconsistent numerical identifier outputs. When models return structured data wrapped in Markdown code blocks, standard deserializers often fail if formatting anomalies or partial payload cutoffs occur. To maintain deterministic execution, prompts.py provides resilient extraction utilities that intercept incomplete stream outputs flagged by llm_common.py, isolate fenced YAML segments, and perform multi-stage chunked recovery when top-level YAML specifications contain syntax errors.

    Additionally, prompts.py defines standardized inline prompt builders that generate system-level queries for file-classification filters and cross-chapter contextual summaries. These summaries capture four distinct technical dimensions—scope, elements, patterns, and integration points—which are dynamically injected into subsequent chapter generation phases to maintain architectural coherence across large codebases.

    Public API

    parse_file_index()

    Visibility: Public
    Signature: def parse_file_index(idx_value) -> int | None:

    Description: Extracts the leading integer value from an LLM-generated index representation. Because language models often append descriptive annotations, file system comments, or numeric range delimiters (such as "3 # utils/prompts.py" or "0-3"), standard integer casting operations fail. This function normalizes raw input values to string format and uses a regular expression to extract the first continuous sequence of digits. If no digits are present in the provided value, it returns None.

    Parameters: * idx_value (Any): The raw index value returned by the model, typically an int, str, or composite annotation string.

    Returns: * int | None: The first integer parsed from the input, or None if no numerical digits are detected.

    Raises: * No exceptions are raised directly; unparseable values safely evaluate to None.

    Example: 

    def parse_file_index(idx_value):
    """Extract the first integer from an LLM-returned file index value.

    Handles multiple formats the LLM may produce:
    - Plain int: 3
    - Annotated string: "3 # path/to/file.py"
    - Range notation: "0-3" → returns first number only (caller handles ranges)

    Returns:
        int or None if no digits found.
    """
    nums = re.findall(r"\d+", str(idx_value))
    return int(nums[0]) if nums else None

    The function handles multiple LLM response formats by converting idx_value directly into a string representation using str(idx_value). It executes re.findall(r"\d+", ...) to harvest all contiguous numeric matches. When a non-empty sequence of digit matches is found, it extracts the first element nums[0] and converts it via int(). Callers receiving range notations (such as "0-3") receive 0, delegating range expansion and boundary checks to the calling node. If the input contains no numeric characters (for instance, an empty string or invalid identifier), the ternary condition yields None, preventing downstream runtime ValueError exceptions during type conversion.

    load_prompt_template()

    Visibility: Public
    Signature: def load_prompt_template(template_name, advanced_mode=False, mode=None) -> str:

    Description: Resolves and loads a Markdown prompt template from the project's root prompts/ hierarchy. It translates pipeline execution settings into a target subdirectory path (tutorial, advanced, api-reference, sdk, or common), retrieves the file from disk using UTF-8 Byte Order Mark (BOM) tolerant decoding (utf-8-sig), logs the file loading operation to the persistent execution ledger via utils.output.emit_raw, and returns the unformatted template content.

    Parameters: * template_name (str): The base name of the template file excluding the .md file extension (e.g., "identify_abstractions", "draft_chapters"). * advanced_mode (bool, optional): Legacy configuration flag indicating whether to pull from the advanced or tutorial prompt directory when mode is unspecified. Defaults to False. * mode (str | None, optional): The explicit operational mode corresponding to a subdirectory within prompts/ (e.g., "api-reference", "sdk", "tutorial", "advanced", "common"). Takes precedence over advanced_mode. Defaults to None.

    Returns: * str: The raw text content of the target Markdown prompt template.

    Raises: * FileNotFoundError: If the resolved path does not exist on disk. * OSError: If the file cannot be accessed or read due to filesystem permission issues.

    Example: 

    def load_prompt_template(template_name, advanced_mode=False, mode=None):
    """Load a prompt template file from the prompts/ directory."""
    if mode is None:
        prompt_dir = "advanced" if advanced_mode else "tutorial"
    else:
        prompt_dir = mode

    path = os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "prompts", prompt_dir, f"{template_name}.md")
    with open(path, encoding="utf-8-sig") as f:
        content = f.read()
    from utils.output import emit_raw

    emit_raw("DEBUG", f"load_prompt_template | loaded '{template_name}.md' from prompts/{prompt_dir}/", dest="LOG")
    return content

    The function computes the directory name using a fallback mechanism: if mode is explicitly provided, it serves as the directory name; otherwise, it evaluates advanced_mode to toggle between "advanced" and "tutorial". The physical path is computed dynamically by traversing two parent directory levels from __file__ using os.path.abspath and os.path.dirname, ensuring correct path resolution regardless of the current working directory. The file read operation explicitly specifies encoding="utf-8-sig" to prevent character corruption or decoding crashes on systems where Windows or external editors prefix files with a UTF-8 BOM. To prevent circular import dependencies between prompt handling and presentation modules, emit_raw is lazily imported from utils.output within the function scope, routing a diagnostic trace directly to the audit log destination (dest="LOG").

    parse_yaml_response()

    Visibility: Public
    Signature: def parse_yaml_response(response) -> Any:

    Description: Extracts and parses structured YAML payloads enclosed within Markdown code fences (```yaml) from an LLM response string. The function validates that the incoming payload was not prematurely terminated by model context limits by checking for truncation markers (truncated attributes from llm_common.py). It isolates the fenced YAML text block, deserializes it using yaml.safe_load, and catches syntax errors, wrapping them in a standardized ValueError.

    Parameters: * response (str | TruncatedResponse | Any): The raw completion response returned by the language model.

    Returns: * Any: The deserialized Python data structure (typically a dict or list) represented by the YAML payload.

    Raises: * ValueError: Raised if the response has its .truncated attribute set to True, indicating incomplete generation that would yield a partial data structure. * ValueError: Raised if the response does not contain valid ```yaml fences or contains invalid YAML syntax.

    Example: 

    def parse_yaml_response(response):
    """Extract and parse YAML from an LLM response fenced in ```yaml blocks."""
    # A reply cut off at max tokens (llm_common.TruncatedResponse) can still contain a parseable
    # fenced prefix that silently drops items — raise so the node retries instead.
    if getattr(response, "truncated", False):
        raise ValueError("LLM response was truncated before the YAML block completed")
    try:
        yaml_str = response.strip().split("```yaml")[1].split("```")[0].strip()
        return yaml.safe_load(yaml_str)
    except Exception as e:
        raise ValueError(f"Failed to parse YAML: {e}") from e

    The parsing pipeline begins with a defensive check against silent generation failures. If the response object wraps an instance of TruncatedResponse (or carries a truncated attribute), the function raises a ValueError immediately. This behavior ensures that partial YAML documents—which might otherwise parse into an incomplete subset of elements—are rejected so the calling pipeline node can trigger a retry or context expansion. When valid, the function strips surrounding whitespace and isolates the substring between the opening ```yaml token and the subsequent closing ``` token using successive .split() operations. It executes yaml.safe_load(yaml_str) within a try-except block, intercepting scanner, parser, and index errors to re-raise them as descriptive ValueError instances chaining the original exception context via from e.

    parse_grouping_response()

    Visibility: Public
    Signature: def parse_grouping_response(response) -> dict[str, Any]:

    Description: A specialized, fault-tolerant parser designed for structural module grouping responses generated by the prompts/common/group_modules.md prompt. In complex repositories, models generating architectural navigation hierarchies, module descriptions, and dependency graphs frequently generate formatting errors in one section while formatting others correctly. This function attempts a standard YAML parse via parse_yaml_response(), and if that fails, executes a fallback routine that partitions the YAML text into individual top-level root sections (sections, descriptions, and dependencies) to salvage valid blocks.

    Parameters: * response (str | TruncatedResponse | Any): The raw LLM output expected to contain a fenced YAML document with module grouping metadata.

    Returns: * dict[str, Any]: A dictionary containing the recovered top-level keys, guaranteed to contain at least the validated sections list.

    Raises: * ValueError: Raised if the incoming response is truncated, if no ```yaml code block is found, if the fallback parser cannot extract a dictionary, or if the resulting structure lacks a valid sections list.

    Phase 1: Direct Whole-Block Deserialization

    Attempts to parse the entire response in a single operation using parse_yaml_response().

        try:
        return parse_yaml_response(response)
    except ValueError:
        if getattr(response, "truncated", False) or "```yaml" not in response:
            raise

    In this initial phase, the function attempts full deserialization via parse_yaml_response(). If the document is well-formed, the resulting dictionary returns immediately. If a ValueError is caught, the handler inspects the failure context. If the error was triggered by an explicit generation truncation (getattr(response, "truncated", False)) or if the payload lacks the required ```yaml fence entirely, recovery is impossible; the function re-raises the ValueError immediately to trigger upstream retry mechanics.

    Phase 2: Fenced Payload Extraction and Regex Partitioning

    Extracts the raw YAML substring and splits it into independent chunks based on top-level key patterns.

            yaml_str = response.split("```yaml", 1)[1].split("```", 1)[0]
        parsed = {}
        for chunk in re.split(r"(?m)^(?=(?:sections|descriptions|dependencies)\s*:)", yaml_str):
            try:
                part = yaml.safe_load(chunk)
            except Exception:
                continue
            if isinstance(part, dict):
                parsed.update(part)

    If the response was not truncated but failed parsing due to local syntax anomalies (such as invalid quotation marks or unescaped colons in descriptions), the function isolates the YAML string using single-split slicing split("```yaml", 1)[1].split("```", 1)[0]. It then splits the text using a multiline regular expression with a positive lookahead: r"(?m)^(?=(?:sections|descriptions|dependencies)\s*:)". This partitions the document into individual text segments anchored by the target root keys. Each chunk is individually parsed via yaml.safe_load(chunk). Any chunk containing a syntax error is safely ignored without discarding previously parsed valid blocks. Successfully parsed sub-dictionaries are merged into the accumulator dictionary parsed via parsed.update(part).

    Phase 3: Core Schema Validation

    Enforces that the minimum required architectural structure was preserved during piecewise recovery.

            if not isinstance(parsed.get("sections"), list):
            raise ValueError("Failed to parse YAML: no sections list in the grouping reply") from None
        return parsed

    Following the chunk parsing loop, the function validates the recovered schema. While descriptions and dependencies are optional or degradable, the sections mapping is strictly required by mkdocs.py to generate the navigation tree. The function checks isinstance(parsed.get("sections"), list). If the sections key is absent, null, or not formatted as a list, the function raises a terminal ValueError("Failed to parse YAML: no sections list in the grouping reply"). Otherwise, it returns the partially or fully recovered dictionary to the caller.

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description: Constructs the prompt string used during api-reference documentation generation to filter out non-code assets. In large software repositories, crawled listings contain UI layouts, configuration files, static assets, binary descriptors, build project files, and documentation. This builder formats a deterministic extraction query instructing the LLM to inspect the complete directory listing and return exclusively the integer file indices representing substantive business logic, APIs, and classes, formatted as a YAML list.

    Parameters: * project_name (str): The name of the codebase or repository undergoing analysis. * file_listing (str): The formatted, indexed directory tree or file listing string generated by files.py (e.g., matching the (idx:N) format).

    Returns: * str: The complete prompt string ready for transmission to an LLM provider.

    Raises: * No exceptions are raised directly during string assembly.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The function performs template variable interpolation on a fixed multi-line prompt string. It embeds the provided project_name and the structural file_listing text block. To minimize hallucination and downstream parsing failures, the template defines explicit exclusion criteria—specifically targeting .xaml, .storyboard, .html, .xml, .json, .manifest, .ini, .csproj, .sln, static assets, and pre-existing documentation. The prompt explicitly specifies the required output format using a few-shot code block example (- 0\n- 1\n- 3), ensuring compatibility with parse_yaml_response() and parse_file_index().

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description: Assembles the prompt used to generate a structured four-dimension technical summary of a newly generated documentation chapter. In multi-chapter workflows, passing entire preceding chapters into the LLM context window quickly exhausts token budgets. This builder standardizes an extraction prompt that condenses each chapter into an architectural brief covering four explicit dimensions (scope, elements, patterns, and integrations). These briefs are chained into subsequent generation prompts, maintaining cross-chapter narrative coherence while keeping token usage bounded.

    Parameters: * chapter_num (int): The sequential numerical index of the chapter being summarized. * abstraction_name (str): The architectural abstraction or module title associated with the chapter. * chapter_content (str): The raw Markdown text of the generated chapter. * language (str, optional): The target natural language for the summary. If set to any value other than "english" (case-insensitive), an explicit language directive is prepended to the prompt. Defaults to "english".

    Returns: * str: The complete prompt string instructing the model to generate the four-part technical brief.

    Raises: * No exceptions are raised directly during string assembly.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.

    The summary captures 4 technical dimensions with 3-5 sentences each:
    1. Component scope & responsibility
    2. Key classes/services/functions and their roles
    3. Implementation patterns & architectural decisions
    4. Inter-component interfaces & dependencies
    """
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The function evaluates the target language argument: if the normalized lowercase string does not equal "english", it formats a leading directive ("Write the entire summary in <Language>. "), ensuring consistent localization matching the pipeline's configured output language. The body of the prompt enforces four structured headings: Component Scope & Responsibility, Key Technical Elements, Implementation Patterns & Architecture, and System Integration & Dependencies. It requires 3 to 5 concise sentences per section, establishing uniform information density across summaries. The prompt concludes with a structural divider, the chapter header (Chapter {chapter_num}: {abstraction_name}), and the raw chapter_content.

    Data Structures

    The prompts.py module defines structural contracts for LLM outputs parsed by its parsing functions.

    Grouping Response Data Contract (parse_grouping_response)

    The dictionary schema returned when deserializing architectural module groupings from prompts/common/group_modules.md.

    Key Type Requirement Description
    sections list[dict[str, Any]] Mandatory A list of architectural sections defining the navigation hierarchy. Each item defines a section title and the list of module filenames or indices assigned to it.
    descriptions dict[str, str] Optional A mapping of module filenames or identifiers to concise architectural responsibility summaries.
    dependencies list[dict[str, Any]] Optional A list of explicit dependency relationships or data flow linkages detected between grouped modules.

    Chapter Technical Summary Schema (build_chapter_summary_prompt)

    The four-dimension architectural summary schema produced by models in response to build_chapter_summary_prompt.

    Section Heading Token Constraints Description
    (1) Component Scope & Responsibility 3–5 sentences Outlines the main technical domain, system role, and specific engineering problems solved.
    (2) Key Technical Elements 3–5 sentences Enumerates the primary classes, interfaces, entry points, functions, schemas, or protocols.

    (4) System Integration & Dependencies 3–5 sentences Details upstream consumers, downstream dependencies, shared ledgers, and external network APIs.

    Error Handling

    The module implements defensive parsing and fail-fast validation patterns to safeguard pipeline execution against non-deterministic LLM behavior:

    • Truncation Defense: Language models constrained by token generation limits can produce truncated output containing opening ```yaml fences without valid terminal closures. Attempting to parse such blocks can either fail or silently drop truncated items at the end of lists. Functions parse_yaml_response() and parse_grouping_response() check getattr(response, "truncated", False) prior to parsing. If set, they immediately raise a ValueError("LLM response was truncated before the YAML block completed"), forcing the calling graph node in nodes.py to re-dispatch the prompt with a larger token ceiling.
    • Piecewise Recovery: During navigation clustering via parse_grouping_response(), an unescaped character inside a descriptions string can invalidate the entire YAML document. Rather than failing the entire clustering pipeline, the fallback routine splits the block on top-level key boundaries (sections, descriptions, dependencies) and parses each chunk independently with yaml.safe_load().
    • Structural Enforcement: In parse_grouping_response(), if the recovered structure lacks a valid sections list, the function raises ValueError("Failed to parse YAML: no sections list in the grouping reply") from None, preventing downstream static site generation errors in mkdocs.py.
    • Missing Index Fallback: When models emit descriptive text instead of plain numbers, parse_file_index() uses regular expressions to extract digit sequences and safely returns None instead of raising an exception if no digits match.
