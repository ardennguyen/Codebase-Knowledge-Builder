    prompts.py

    Source: utils/prompts.py

    While utils/output.py manages localized console output, user-facing diagnostics, and real-time terminal telemetry, utils/prompts.py acts as the programmatic template and artifact generation engine for the Codebase-Knowledge-Builder system. It centralizes inline prompt construction routines and static asset synthesis required for documentation site compilation, eliminating ad-hoc string formatting across workflow execution nodes.

    Technical Overview

    utils/prompts.py serves two distinct functional roles within the system architecture: inline Large Language Model (LLM) prompt engineering and static documentation site compilation. Unlike mode-specific document prompts that are loaded from external Markdown templates (such as prompts/{mode}/), the prompts generated in this module are programmatic, structured payloads designed for internal deterministic operations. These include filtering non-code files during repository analysis and compressing generated chapters into dense technical briefs for cross-chapter context chaining.

    In its second role, the module provides configuration and script builders for generating static documentation sites using MkDocs. It handles the dynamic assembly of mkdocs.yml configuration files, client-side JavaScript initializers for Mermaid diagram rendering, and the recursive compilation of nested navigation trees based on LLM section groupings and repository directory structures.

    Public API

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description: Generates an inline prompt instructing the LLM to act as a deterministic file mapper. It takes a complete list of repository files and prompts the model to return a strict YAML list containing only the integer indices of files that represent executable or API-relevant source code (e.g., classes, functions, business logic), filtering out UI layouts, configuration files, static assets, build manifests, and documentation.

    Parameters: * project_name (str): The name of the target repository or project being analyzed. * file_listing (str): A formatted string representing repository file indices and relative paths.

    Returns: * str: A formatted prompt ready for submission to call_llm().

    Raises: * None.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The function guarantees strict index-based mapping constraints by embedding explicit negative rules (excluding .xaml, .json, .csproj, etc.) alongside a standardized YAML code block schema. This format simplifies regex or YAML parsing downstream in nodes.py.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description: Builds a structured summarization prompt designed to compress a generated chapter into a dense technical brief across four specific architectural dimensions. The resulting summary is passed into subsequent chapter prompts to maintain cross-chapter coherence without exhausting model context budgets.

    Parameters: * chapter_num (int): The sequence number of the chapter being summarized. * abstraction_name (str): The title or abstraction boundary covered by the chapter. * chapter_content (str): The full Markdown content of the generated chapter. * language (str, optional): The target natural language for the output summary. Defaults to "english".

    Returns: * str: The complete prompt payload for cross-chapter context generation.

    Raises: * None.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter."""
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The function dynamically prepends a localization instruction when language is not English, ensuring consistent summarization across multi-language documentation runs. By constraining each dimension to 3–5 sentences, the prompt enforces information density and prevents unbounded token growth in downstream memory buffers managed by token_utils.py.

    build_mkdocs_config()

    Description: Assembles a complete mkdocs.yml configuration string optimized for the Material for MkDocs theme. The configuration includes code copy buttons, dark/light theme toggling, search, pan-zoom capabilities for Mermaid diagrams, Python Markdown syntax highlighting extensions, and custom superfences to support raw Mermaid diagram rendering.

    Parameters: * site_name (str): The display title for the documentation website. * nav_yaml (str): A YAML-formatted navigation hierarchy string.

    Returns: * str: The complete serialized YAML content for the mkdocs.yml file.

    Raises: * None.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    """Build a complete mkdocs.yml for local --mkdocs output."""
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"    - navigation.indexes\n"
        f"  palette:\n"
        f"    - scheme: default\n"
        f"      toggle:\n"
        f"        icon: material/brightness-7\n"
        f"        name: Switch to dark mode\n"
        f"    - scheme: slate\n"
        f"      toggle:\n"
        f"        icon: material/brightness-4\n"
        f"        name: Switch to light mode\n"
        f"plugins:\n"
        f"  - search\n"
        f"  - panzoom:\n"
        f"      include_selectors:\n"
        f"        - '.mermaid-raw'\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid-raw\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"extra_javascript:\n"
        f"  - https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.min.js\n"
        f"  - javascripts/mermaid-init.js\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The function parses the incoming nav_yaml string by stripping any top-level nav: declaration to prevent key duplication. It maps pymdownx.superfences to assign the .mermaid-raw CSS class instead of .mermaid, preventing MkDocs Material from overriding diagram color palettes.

    build_mermaid_init_js()

    Visibility: Public
    Signature: def build_mermaid_init_js() -> str:

    Description: Constructs an inline vanilla JavaScript initializer string to be written to javascripts/mermaid-init.js. This script resolves DOM compatibility issues between pymdownx.superfences and the Mermaid rendering engine, while preserving Mermaid's default styling.

    Parameters: * None.

    Returns: * str: Executable JavaScript source code contained in an Immediately Invoked Function Expression (IIFE).

    Raises: * None.

    Example: 

    def build_mermaid_init_js() -> str:
    """Build JS to initialize Mermaid on .mermaid-raw elements."""
    return """\
// Initialize Mermaid on .mermaid-raw elements (bypasses Material theme override)
// Material for MkDocs targets .mermaid class for its own color overrides.
// By using .mermaid-raw, diagrams render with Mermaid's default theme:
// yellow subgraph backgrounds, lavender nodes, clean rectangles.
//
// pymdownx.superfences fence_code_format wraps content as:
//   <pre class="mermaid-raw"><code>flowchart TD ...</code></pre>
// Mermaid expects the diagram text directly in the target element,
// so we unwrap the <code> child before calling mermaid.run().
(function() {
  function initMermaid() {
    if (typeof mermaid === 'undefined') return;
    try {
      // Unwrap: move <code> text content up to <pre> and remove <code>
      document.querySelectorAll('pre.mermaid-raw > code').forEach(function(code) {
        var pre = code.parentElement;
        pre.textContent = code.textContent;
      });
      mermaid.initialize({
        startOnLoad: false,
        theme: 'default',
        securityLevel: 'loose'
      });
      mermaid.run({ querySelector: '.mermaid-raw' }).catch(function(err) {
        console.warn('Mermaid render error:', err);
      });
    } catch (e) {
      console.warn('Mermaid init error:', e);
    }
  }
  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initMermaid);
  } else {
    initMermaid();
  }
})();
"""

    The returned script unwraps inner <code> elements generated by pymdownx.superfences (<pre class="mermaid-raw"><code>...</code></pre>), moving text directly into the parent <pre> node. It configures mermaid.initialize with startOnLoad: false and securityLevel: 'loose', invoking mermaid.run() explicitly across all .mermaid-raw selectors.

    build_grouped_nav()

    Visibility: Public
    Signature: def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:

    Description: Recursively constructs indented YAML navigation entries from hierarchical section groupings and a list of generated chapter files. It matches modules to their source file metadata and groups sub-directory files into structured navigation levels while keeping root-level files flat.

    Parameters: * sections (list): A list of dictionary objects defining section names, nested child sections, and assigned module names. * chapter_files (list): A list of metadata dictionaries containing module_name, filename, and original_path mappings. * indent (int, optional): Indentation space count for the current recursion level. Defaults to 4.

    Returns: * list[str]: A list of formatted YAML navigation lines.

    Raises: * None.

    Phase 1: Section Traversal & Child Processing

        lines = []
    pad = " " * indent
    for section in sections:
        lines.append(f"{pad}- {section['name']}:")
        if "children" in section:
            lines.extend(build_grouped_nav(section["children"], chapter_files, indent + 2))
    This phase creates the top-level section header and recursively processes any nested structures defined in the children key, incrementing the indentation by 2 spaces per recursion level.

    Phase 2: Module Identification & Path Resolution

            # Collect matched modules with directory info
        matched = []
        for mod_name in section.get("modules", []):
            match = next((cf for cf in chapter_files if cf["module_name"] == mod_name), None)
            if match:
                dir_path = os.path.dirname(match.get("original_path", "")) or ""
                matched.append((dir_path, mod_name, match))
    The algorithm iterates through all module names declared in the current section, matching each against the chapter_files lookup list. For every match, os.path.dirname extracts the directory path from original_path, normalizing empty strings for root-level modules.

    Phase 3: Directory Grouping & YAML Emission

            # Group by directory
        from collections import defaultdict

        dir_groups = defaultdict(list)
        for dir_path, mod_name, match in matched:
            dir_groups[dir_path].append((mod_name, match))

        # Emit dir sub-layers for non-root dirs, flat for root files
        has_non_root = any(d for d in dir_groups)
        if has_non_root:
            for dir_path in sorted(dir_groups.keys()):
                if dir_path:
                    # Non-root: add directory sub-layer with bare module names
                    lines.append(f"{pad}  - {dir_path}:")
                    for mod_name, match in dir_groups[dir_path]:
                        lines.append(f"{pad}    - '{mod_name}': 'api/{match['filename']}'")
                else:
                    # Root files: flat (no sub-layer)
                    for mod_name, match in dir_groups[dir_path]:
                        lines.append(f"{pad}  - '{mod_name}': 'api/{match['filename']}'")
        else:
            # All root files → flat list
            for _dir_path, mod_name, match in matched:
                lines.append(f"{pad}  - '{mod_name}': 'api/{match['filename']}'")

    return lines
    Matched modules are organized into directory buckets using collections.defaultdict. If any module belongs to a sub-directory, non-root paths are emitted as nested directory nodes with their contained files indented below. Root files remain flat at the section level.

    collect_all_modules()

    Visibility: Public
    Signature: def collect_all_modules(sections: list) -> set:

    Description: Recursively traverses a section hierarchy tree to extract every referenced module name into a flat set.

    Parameters: * sections (list): The list of section dictionaries to traverse.

    Returns: * set: A set of all distinct module name strings found across the section tree.

    Raises: * None.

    Example: 

    def collect_all_modules(sections: list) -> set:
    """Recursively collect all module names referenced in a sections tree."""
    result = set()
    for section in sections:
        result.update(section.get("modules", []))
        if "children" in section:
            result.update(collect_all_modules(section["children"]))
    return result

    This helper aggregates module identifiers across arbitrary nesting depths. It is used to validate that all documented files have been assigned to navigation sections without omissions or duplicates.

    Internal Helpers

    The functions defined in utils/prompts.py are exported as part of the module's public utility interface and are invoked across nodes.py, flow.py, and main.py. The only internal non-exported routine is initMermaid(), which is embedded inside the client-side JavaScript payload returned by build_mermaid_init_js().

    initMermaid()

    Visibility: Internal (JavaScript closure scope within build_mermaid_init_js())
    Signature: function initMermaid(): void

    Description: A client-side JavaScript closure that checks for the global mermaid object, unwraps DOM code nodes, sets default rendering themes, and runs the rendering pipeline across .mermaid-raw elements while handling render exceptions.

    Data Structures

    Section Dictionary Schema

    Used by build_grouped_nav() and collect_all_modules() to represent section hierarchies generated during workflow execution.

    Field Type Description
    name str Display title of the navigation section.
    modules list[str] Optional list of module identifiers assigned directly to this section.
    children list[dict] Optional nested list of child Section Dictionaries.

    Chapter File Metadata Schema

    Used by build_grouped_nav() to correlate module identifiers with generated documentation files and original filesystem paths.

    Field Type Description
    module_name str Name of the module or component (e.g., "call_llm.py").
    filename str Target output Markdown filename (e.g., "utils_call_llm.py.md").
    original_path str Original relative repository path (e.g., "utils/call_llm.py").

    Error Handling

    • Missing Keys in Dictionaries: build_grouped_nav() and collect_all_modules() defensively use .get("modules", []), section.get("children"), and match.get("original_path", "") to avoid KeyError exceptions when handling incomplete dictionary structures.
    • Empty Navigation YAML: build_mkdocs_config() handles empty or single-line nav_yaml strings without raising IndexError by slicing nav_lines[1:] and checking collection truthiness before joining lines.
    • Client-Side Rendering Errors: build_mermaid_init_js() wraps diagram unwrapping, initialization, and execution within try...catch blocks and appends a .catch() handler to the mermaid.run() Promise. This ensures that a single invalid diagram does not break the documentation site or halt browser execution.
