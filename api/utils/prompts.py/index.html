    prompts.py

    Source: utils/prompts.py

    Following the observability and localization mechanics established in output.py, the utils/prompts.py module defines the prompt loading, synthesis, and response parsing infrastructure for the documentation generation pipeline. It coordinates the creation of targeted system instructions for Large Language Models (LLMs) and isolates the deserialization logic required to process structured outputs returned by inference gateways.

    Technical Overview

    utils/prompts.py acts as the prompt engineering and structured-output decoding layer of the Codebase-Knowledge-Builder architecture. In an automated documentation pipeline, execution nodes frequently require specialized instructions conditioned on project metadata, file paths, and target output languages. Simultaneously, intermediate pipeline states depend on structured data (such as lists of code file indices or navigation hierarchies) extracted reliably from non-deterministic LLM text responses. This module bridges prompt assembly and response processing, decoupling orchestration nodes in nodes.py from raw string templating and Markdown extraction logic.

    The module operates across two functional domains: 1. Prompt Ingestion and Construction: File-based prompt templates residing in the filesystem tree under prompts/ are located and ingested via load_prompt_template(). The module supports mode-driven directory scoping (tutorial, advanced, or arbitrary mode identifiers). For specialized pipeline stages where disk-based templates are inappropriate, the module provides dynamic string synthesis functions—namely build_code_file_filter_prompt() for identifying executable code modules, and build_chapter_summary_prompt() for compiling multi-dimensional technical chapter abstracts used for cross-chapter context injection. 2. Structured Response Extraction: Because LLMs return freeform conversational strings interspersed with Markdown formatting, parse_yaml_response() extracts text contained within ```yaml code fences and deserializes it into native Python dictionaries or lists via PyYAML.

    The architecture addresses several operational considerations: * Path Resolution Autonomy: Template loading calculates root paths relative to __file__, allowing portable execution across development environments, container images, or working directories. * Encoding Resiliency: Disk reads enforce utf-8-sig encoding, stripping Byte Order Marks (BOM) transparently to prevent parsing syntax errors in downstream Jinja or Python formatting operations. * Decoupled Telemetry: The module uses late imports (from utils.output import emit_raw) inside load_prompt_template() to log template access directly to internal debug logs without triggering circular dependency loops during interpreter startup.

    Public API

    load_prompt_template()

    Visibility: Public
    Signature: def load_prompt_template(template_name, advanced_mode=False, mode=None) -> str

    Description:
    Locates and loads the UTF-8 encoded text of a Markdown prompt template from the repository's prompts/ filesystem hierarchy. The target directory is dynamically resolved according to a three-tier precedence model: if mode is explicitly provided, it selects prompts/{mode}/; otherwise, if advanced_mode is True, it selects prompts/advanced/; defaulting finally to prompts/tutorial/.

    Once the canonical path is computed relative to the project root, the file is read using utf-8-sig encoding. The method then issues a debug diagnostic to the operational log via a late import of emit_raw(), ensuring template access is recorded without polluting stdout.

    Logical Phases

    Phase 1: Directory Scope Resolution

        if mode is None:
        prompt_dir = "advanced" if advanced_mode else "tutorial"
    else:
        prompt_dir = mode
    This phase determines which subdirectory under prompts/ holds the requested template. By checking mode is None first, callers can pass arbitrary mode strings (such as "api-reference" or specialized testing profiles) directly. If mode is unspecified, the binary advanced_mode flag routes between "advanced" and "tutorial".

    Phase 2: Filesystem Resolution and Ingestion

        path = os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "prompts", prompt_dir, f"{template_name}.md")
    with open(path, encoding="utf-8-sig") as f:
        content = f.read()
    The absolute path is determined by stepping up two directory levels from utils/prompts.py to reach the repository root, then descending into prompts/{prompt_dir}/{template_name}.md. File opening explicitly mandates utf-8-sig to gracefully strip Windows UTF-8 BOM headers that may be introduced during manual template editing.

    Phase 3: Telemetry Dispatch

        from utils.output import emit_raw

    emit_raw("DEBUG", f"load_prompt_template | loaded '{template_name}.md' from prompts/{prompt_dir}/", dest="LOG")
    return content
    The final phase lazily imports emit_raw from utils.output. This prevents module-level circular imports between output telemetry and prompt initialization. It logs the resolution event at severity level "DEBUG" explicitly directed to the "LOG" destination (bypassing standard output). The raw template string is then returned to the caller.

    Parameters: * template_name (str): Base name of the prompt Markdown file (excluding the .md extension). * advanced_mode (bool, optional): Legacy boolean flag used when mode is None. Selects "advanced" if True, or "tutorial" if False. Defaults to False. * mode (str | None, optional): Explicit subdirectory name under prompts/ to load templates from. Overrides advanced_mode when provided. Defaults to None.

    Returns: * str: The complete raw string content of the resolved template file.

    Raises: * FileNotFoundError: If the constructed path does not exist on disk. * IOError: If the file cannot be accessed due to OS permissions.

    Example: 

    # Sourced from utils/prompts.py implementation:
path = os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "prompts", prompt_dir, f"{template_name}.md")
with open(path, encoding="utf-8-sig") as f:
    content = f.read()
from utils.output import emit_raw

emit_raw("DEBUG", f"load_prompt_template | loaded '{template_name}.md' from prompts/{prompt_dir}/", dest="LOG")

    parse_yaml_response()

    Visibility: Public
    Signature: def parse_yaml_response(response: str) -> Any

    Description:
    Isolates, sanitizes, and parses YAML data structures embedded within an LLM completion string. Standard generative language models frequently envelope structured responses in Markdown code blocks. parse_yaml_response() extracts text specifically bounded by ```yaml and closing ``` tokens, ignoring preamble explanations, thinking traces, or postscript commentary.

    The extracted substring is then parsed via yaml.safe_load(). If the delimiters are missing or if the payload contains invalid YAML syntax, the routine intercepts the resulting standard exception and raises a formatted ValueError preserving the underlying cause.

    Logical Phases

    Phase 1: Boundary Isolation

        try:
        yaml_str = response.strip().split("```yaml")[1].split("```")[0].strip()
    The input string is stripped of leading and trailing whitespace, then partitioned using "```yaml" as the opening delimiter. Index 1 isolates the text immediately following the fence header. A subsequent partition on "```" selects index 0, extracting only the payload between the fences. A final .strip() removes boundary whitespace and carriage returns.

    Phase 2: Deserialization and Error Normalization

            return yaml.safe_load(yaml_str)
    except Exception as e:
        raise ValueError(f"Failed to parse YAML: {e}") from e
    The isolated YAML string is passed to yaml.safe_load(), which converts the text into corresponding native Python collections (e.g., list, dict, int, str). If an IndexError occurs during splitting (indicating missing code fences) or a yaml.YAMLError occurs during parsing, the exception is caught and re-raised as a standard ValueError with chained context (from e).

    Parameters: * response (str): The raw text response received from an LLM call.

    Returns: * Any: The deserialized Python data structure (typically a dict or list).

    Raises: * ValueError: If "```yaml" or "```" fences are missing, or if the extracted payload violates YAML syntax rules.

    Example: 

    # Sourced from utils/prompts.py implementation:
try:
    yaml_str = response.strip().split("```yaml")[1].split("```")[0].strip()
    return yaml.safe_load(yaml_str)
except Exception as e:
    raise ValueError(f"Failed to parse YAML: {e}") from e

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str

    Description:
    Synthesizes the prompt payload utilized by file mapper stages (such as DeterministicFileMapper in API-reference documentation mode). This prompt directs an LLM to evaluate an enumerated listing of repository files and filter out non-code assets, configurations, UI layouts, and build artifacts.

    The generated prompt injects the target project_name and the pre-formatted file_listing string. It articulates explicit negative filtering constraints (specifying extensions like .xaml, .storyboard, .html, .xml, .json, .manifest, .ini, .csproj, and .sln) and mandates that the model output only a YAML list containing integer indices of genuine code modules.

    Prompt Assembly Phase

        return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )
    The prompt combines the contextual inputs into a single multiline string. By terminating the prompt with a concrete Markdown fence example (```yaml\n- 0\n- 1\n- 3\n```), the instruction anchors the expected few-shot schema pattern for zero-shot inference, ensuring compatibility with parse_yaml_response().

    Parameters: * project_name (str): Name or identifier of the repository being processed. * file_listing (str): Enumerated list of repository files (typically formatted with index identifiers such as (idx:0) path/to/file.py via files.py).

    Returns: * str: The fully interpolated prompt string ready for LLM consumption.

    Example: 

    # Direct implementation extracted from utils/prompts.py:
prompt = build_code_file_filter_prompt(
    project_name="Codebase-Knowledge-Builder",
    file_listing="(idx:0) utils/prompts.py\n(idx:1) config.json\n(idx:2) main.py"
)

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str

    Description:
    Assembles the prompt required to synthesize a standardized, 4-dimension technical brief of a completed documentation chapter. This summary is injected into subsequent chapter synthesis prompts to maintain architectural coherence and cross-chapter referencing across large documentation jobs.

    The prompt enforces a strict structure requiring 3 to 5 concise technical sentences across four architectural dimensions: 1. Component Scope & Responsibility: Core domain, problem space, and system role. 2. Key Technical Elements: Explicit naming and characterization of classes, services, functions, and protocols. 3. Implementation Patterns & Architecture: Design patterns, communication channels, error strategies, and threading models. 4. System Integration & Dependencies: External consumption, interface contracts, and boundary touchpoints.

    If the requested language parameter is set to any value other than "english" (case-insensitive), an explicit language constraint prefix is dynamically prepended to ensure localized generation.

    Prompt Assembly Phase

        lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )
    The function evaluates the target language and conditionally builds the lang_instruction string. It then formats the four technical questions, appending the chapter index, title, and body text separated by a Markdown thematic break (---).

    Parameters: * chapter_num (int): Sequential index of the chapter being summarized. * abstraction_name (str): Title or high-level abstraction name representing the chapter. * chapter_content (str): Markdown text of the fully generated chapter. * language (str, optional): Target natural language for the summary output. Defaults to "english".

    Returns: * str: The fully constructed technical summary prompt string.

    Example: 

    # Direct implementation extracted from utils/prompts.py:
prompt = build_chapter_summary_prompt(
    chapter_num=1,
    abstraction_name="LLM Execution Gateway",
    chapter_content="## Technical Overview\nThis module manages LLM routing...",
    language="english"
)

    Data Structures

    The module does not declare custom object classes; instead, it relies on structured string contracts and parsed deserialization schemas.

    Parsed YAML Extraction Schemas

    parse_yaml_response() transforms YAML fenced blocks into native Python data structures. The expected shapes depend on the consuming pipeline node:

    1. Integer Index List Schema

    Emitted by LLM responses answering build_code_file_filter_prompt():

    Field Element Type Description
    [item] int Zero-based index of a valid code file corresponding to the indexed input listing.

    Example Payload: 

    - 0
- 1
- 3
- 8

    2. Navigation / Grouping Hierarchy Schema

    Emitted by LLM clustering tasks (e.g., when structuring MkDocs navigation in mkdocs.py):

    Field Name Type Description
    title str Display title of the documentation grouping or category.
    items list[str] List of file paths, module names, or sub-group mappings.

    Technical Summary Schema

    build_chapter_summary_prompt() enforces a standardized output contract across four discrete technical dimensions:

    Dimension Header Expected Content Format Functional Role in Pipeline
    (1) **Component Scope & Responsibility** 3–5 concise technical sentences Defines boundary scope and domain problems resolved.
    (2) **Key Technical Elements** 3–5 concise technical sentences Enumerates concrete functions, classes, and protocol entities.
    (3) **Implementation Patterns & Architecture** 3–5 concise technical sentences Summarizes algorithms, design patterns, and failure paths.
    (4) **System Integration & Dependencies** 3–5 concise technical sentences Details inbound/outbound calls, data shapes, and contracts.

    Error Handling

    utils/prompts.py applies targeted defensive error management for file I/O and non-deterministic LLM output parsing:

    1. Code Fence Partitioning and YAML Syntax Trapping

    Language models frequently generate conversational commentary alongside structured outputs. parse_yaml_response() isolates the block using .split("```yaml")[1].split("```")[0]. * If the opening token "```yaml" or closing token "```" is missing, a Python IndexError is triggered during list indexing. * If the enclosed payload contains unescaped characters, inconsistent tab indentations, or invalid scalar mappings, yaml.safe_load() raises yaml.YAMLError (or one of its subclasses such as yaml.scanner.ScannerError or yaml.parser.ParserError). * All exceptions are caught uniformly by an except Exception as e: block and re-raised as a standard ValueError(f"Failed to parse YAML: {e}") from e. This consolidates diverse downstream parsing failures into a single predictable exception type that orchestration nodes in nodes.py can catch and handle (e.g., by triggering a retry prompt).

    2. Filesystem Encoding and Path Anomalies

    In load_prompt_template(): * UTF-8 Byte Order Marks (BOM): Opening files with utf-8-sig prevents \ufeff prefix characters from remaining in the template string, avoiding subtle formatting errors during subsequent string interpolation. * Missing Templates: If a referenced template_name does not exist within prompts/{prompt_dir}/, the native FileNotFoundError propagates directly to the calling node, signaling a misconfigured pipeline stage.
