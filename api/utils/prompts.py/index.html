    prompts.py

    Source: utils/prompts.py

    Following the runtime logging, user telemetry, and translation mechanics provided by output.py, the prompts.py module supplies specialized, programmatically generated prompt templates and static site generation (SSG) configuration builders. While large-scale documentation modes load their comprehensive system prompts from external markdown files under the prompts/ directory tree, internal pipeline operations—such as deterministic source code filtering, cross-chapter technical summarization, and MkDocs site synthesis—rely on the inline, parameter-driven prompt builders housed in this module.

    Technical Overview

    The prompts.py module serves as the centralized repository for non-template-driven LLM prompt builders and MkDocs documentation scaffolding utilities within Codebase-Knowledge-Builder. It is designed to decouple string formatting, heuristic layout generation, and navigation tree compilation from core workflow execution nodes in nodes.py.

    The module fulfills three primary architectural responsibilities:

    1. Source Code Classification: Constructs deterministic file-filtering prompts for the DeterministicFileMapper subsystem in api-reference mode, allowing the LLM to prune configuration manifests, build scripts, static assets, and markup templates from the active documentation set.
    2. Context Memory Bus: Generates structured, 4-dimensional technical summary prompts after each documentation chapter is written. This ensures that cross-chapter architectural context, key interfaces, and dependency relationships are preserved and passed to subsequent chapter prompts without overflowing token windows.
    3. MkDocs and Mermaid Scaffolding: Generates the complete mkdocs.yml configuration schema, recursive multi-level YAML navigation structures (nav), and custom JavaScript hooks (mermaid-init.js). It specifically configures fences and theme initializers to resolve rendering conflicts between Material for MkDocs and Mermaid diagrams.

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Constructs an LLM prompt that instructs the model to inspect an indexed file manifest and filter out non-executable code assets (e.g., UI layout files, configuration files, static media, documentation, and build scripts). It enforces a strict output format by requiring the model to return a YAML array containing only the zero-indexed integer positions corresponding to genuine code modules containing business logic, functions, classes, or API definitions.

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The prompt isolates executable code from auxiliary files by specifying explicit exclusion categories (.xaml, .storyboard, .html, .xml, .json, .manifest, .ini, .csproj, .sln). By requesting indices rather than file paths, the prompt minimizes output token consumption and avoids path normalization errors across operating systems. The resulting YAML block is consumed and parsed by the upstream node to slice the ingested repository's file list.

    Parameters: * project_name (str): The name or identifier of the repository being analyzed. * file_listing (str): An indexed, line-separated string listing candidate file paths.

    Returns: * str: A formatted prompt string containing task rules, exclusion criteria, and a sample YAML return format.

    Raises: * This function does not raise exceptions.

    Example: 

    # Extracted from build_code_file_filter_prompt implementation
prompt = build_code_file_filter_prompt(
    project_name="Codebase-Knowledge-Builder",
    file_listing="0: utils/call_llm.py\n1: utils/output.py\n2: README.md\n3: package.json"
)

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Generates a prompt requesting a 4-point structured technical brief of a newly written documentation chapter. The resulting summary captures the chapter's technical domain, components, design patterns, and cross-module dependencies. This output is injected into downstream chapter generation prompts to maintain cross-document cohesion without exceeding token limits.

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.

    The summary captures 4 technical dimensions with 3-5 sentences each:
    1. Component scope & responsibility
    2. Key classes/services/functions and their roles
    3. Implementation patterns & architectural decisions
    4. Inter-component interfaces & dependencies
    """
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The function checks the language argument to inject an optional target-language instruction prefix (Write the entire summary in <Language>.) for non-English outputs. The prompt constrains the model to provide exactly 3-5 sentences across four specific analytical dimensions: (1) Component Scope & Responsibility, (2) Key Technical Elements, (3) Implementation Patterns & Architecture, and (4) System Integration & Dependencies. This structured format provides downstream generation nodes with consistent context across execution cycles.

    Parameters: * chapter_num (int): The sequence number of the generated chapter. * abstraction_name (str): The title, module name, or architectural layer represented in the chapter. * chapter_content (str): The raw markdown text of the completed chapter. * language (str, optional): The target natural language for the output summary. Defaults to "english".

    Returns: * str: The assembled prompt ready for LLM inference.

    Raises: * This function does not raise exceptions.

    Example: 

    # Extracted from build_chapter_summary_prompt implementation
prompt = build_chapter_summary_prompt(
    chapter_num=1,
    abstraction_name="LLM Gateway",
    chapter_content="# LLM Gateway\nHandles model routing and caching.",
    language="english"
)

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description:
    Assembles a complete, standalone mkdocs.yml configuration file string configured for the material theme. It sets up code block features, search plugins, PyMdown Extensions, custom Mermaid fence definitions, pan-zoom capabilities, and navigation mappings.

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    """Build a complete mkdocs.yml for local --mkdocs output.

    Generates a ready-to-use MkDocs Material config with:
    - Material theme with code copy buttons
    - Syntax highlighting (pymdownx.highlight + inlinehilite)
    - Mermaid diagram rendering via custom 'mermaid-raw' class (bypasses
      Material's Mermaid color overrides so diagrams use Mermaid's default theme)
    - Panzoom plugin for interactive Mermaid diagram zoom/pan
    - Navigation from the generated nav_snippet

    Users can run `mkdocs serve` or `mkdocs build` directly in the output dir.
    """
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"    - navigation.indexes\n"
        f"  palette:\n"
        f"    - scheme: default\n"
        f"      toggle:\n"
        f"        icon: material/brightness-7\n"
        f"        name: Switch to dark mode\n"
        f"    - scheme: slate\n"
        f"      toggle:\n"
        f"        icon: material/brightness-4\n"
        f"        name: Switch to light mode\n"
        f"plugins:\n"
        f"  - search\n"
        f"  - panzoom:\n"
        f"      include_selectors:\n"
        f"        - '.mermaid-raw'\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid-raw\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"extra_javascript:\n"
        f"  - https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.min.js\n"
        f"  - javascripts/mermaid-init.js\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The function processes the nav_yaml string by stripping any top-level nav: header and embedding the remaining navigation lines under a standardized Home: index.md entry. To prevent Material for MkDocs from overriding Mermaid's native color schemes (such as yellow subgraph boundaries and lavender node fills), it configures pymdownx.superfences to assign the custom CSS class mermaid-raw to mermaid fence blocks. It also hooks the panzoom plugin into .mermaid-raw selectors and links the external Mermaid 11 CDN along with a local javascripts/mermaid-init.js initialization script.

    Parameters: * site_name (str): The display title for the documentation site. * nav_yaml (str): The YAML navigation string, either formatted with a nav: header or as raw indented list items.

    Returns: * str: The complete YAML text content for mkdocs.yml.

    Raises: * This function does not raise exceptions.

    Example: 

    # Extracted from build_mkdocs_config implementation
nav_snippet = "nav:\n  - Chapter 1: chapter1.md\n  - Chapter 2: chapter2.md"
config_content = build_mkdocs_config(site_name="My Project API", nav_yaml=nav_snippet)

    Visibility: Public
    Signature: def build_mermaid_init_js() -> str:

    Description:
    Generates the JavaScript code for javascripts/mermaid-init.js. This script runs on the browser's DOMContentLoaded event to manually initialize Mermaid.js on all DOM elements matching the .mermaid-raw selector.

    def build_mermaid_init_js() -> str:
    """Build JS to initialize Mermaid on .mermaid-raw elements.

    Material for MkDocs applies its own color overrides to elements with
    class 'mermaid'. By using class 'mermaid-raw' in superfences config
    and initializing Mermaid manually, diagrams render with Mermaid's
    built-in default theme: yellow subgraph backgrounds, lavender nodes,
    clean rectangles — matching how GitHub renders Mermaid natively.
    """
    return """\
// Initialize Mermaid on .mermaid-raw elements (bypasses Material theme override)
// Material for MkDocs targets .mermaid class for its own color overrides.
// By using .mermaid-raw, diagrams render with Mermaid's default theme:
// yellow subgraph backgrounds, lavender nodes, clean rectangles.
document.addEventListener('DOMContentLoaded', function() {
  if (typeof mermaid !== 'undefined') {
    mermaid.initialize({ startOnLoad: false, theme: 'default' });
    mermaid.run({ querySelector: '.mermaid-raw' });
  }
});
"""

    Material for MkDocs applies theme CSS overrides to standard .mermaid classes, which can alter custom subgraph and node styling. This function returns an initialization script that targets .mermaid-raw elements instead, configuring Mermaid with { startOnLoad: false, theme: 'default' } and rendering them via mermaid.run({ querySelector: '.mermaid-raw' }). This approach maintains consistent diagram rendering matching GitHub's default layout.

    Parameters: * None.

    Returns: * str: A JavaScript snippet ready to be written to javascripts/mermaid-init.js.

    Raises: * This function does not raise exceptions.

    Example: 

    # Extracted from build_mermaid_init_js implementation
js_content = build_mermaid_init_js()

    build_grouped_nav()

    Visibility: Public
    Signature: def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:

    Description:
    Recursively constructs MkDocs navigation YAML lines from an LLM-generated section tree, mapping logical module names to their physical markdown output files. When a section contains modules originating from multiple repository directories, it automatically introduces an intermediate directory layer to organize the paths cleanly.

    def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:
    """Recursively build MkDocs nav YAML lines from LLM section grouping.

    Handles arbitrary nesting depth via the ``children`` key.
    Each leaf module is matched against *chapter_files* by ``module_name``.
    When a functional group spans multiple directories, files are auto-sub-grouped
    by their full directory path (deterministic, no extra LLM call).
    Single-directory groups remain flat (no useless nesting).
    """
    lines = []
    pad = " " * indent
    for section in sections:
        lines.append(f"{pad}- {section['name']}:")
        if "children" in section:
            lines.extend(build_grouped_nav(section["children"], chapter_files, indent + 2))

        # Collect matched modules with directory info
        matched = []
        for mod_name in section.get("modules", []):
            match = next((cf for cf in chapter_files if cf["module_name"] == mod_name), None)
            if match:
                dir_path = os.path.dirname(match.get("original_path", "")) or ""
                matched.append((dir_path, mod_name, match))

        # Group by directory
        from collections import defaultdict

        dir_groups = defaultdict(list)
        for dir_path, mod_name, match in matched:
            dir_groups[dir_path].append((mod_name, match))

        if len(dir_groups) > 1:
            # Multiple directories → add dir sub-layer with full path
            for dir_path in sorted(dir_groups.keys()):
                label = dir_path or "(root)"
                lines.append(f"{pad}  - {label}:")
                for mod_name, match in dir_groups[dir_path]:
                    lines.append(f"{pad}    - '{mod_name}': 'api/{match['filename']}'")
        else:
            # Single directory or no original_path → flat list
            for _dir_path, mod_name, match in matched:
                lines.append(f"{pad}  - '{mod_name}': 'api/{match['filename']}'")

    return lines

    The algorithm walks through the sections hierarchy using recursion to handle arbitrary sub-trees defined under children. Within each section node, it matches module names against chapter_files by checking cf["module_name"]. It then uses os.path.dirname on match["original_path"] to resolve the originating folder:

    Returns: * list[str]: A list of formatted YAML navigation lines.

    Raises: * This function does not raise exceptions directly; missing optional dictionary keys are handled with default empty fallbacks (.get(), or "").

    collect_all_modules()

    Visibility: Public
    Signature: def collect_all_modules(sections: list) -> set:

    Description:
    Traverses an arbitrary-depth section tree and collects all unique module names referenced across all sections and nested child branches.

    def collect_all_modules(sections: list) -> set:
    """Recursively collect all module names referenced in a sections tree."""
    result = set()
    for section in sections:
        result.update(section.get("modules", []))
        if "children" in section:
            result.update(collect_all_modules(section["children"]))
    return result

    The function iterates over the top-level section list, extracting the modules array from each section dictionary and adding its values to an in-memory set. When a section dictionary contains a children array, the function calls itself recursively, merging the returned child sets via set.update(). This utility is primarily used by pipeline validators to detect missing or unassigned modules prior to building the navigation tree.

    Parameters: * sections (list[dict]): A list of section hierarchy dictionaries, which may contain nested children lists.

    Returns: * set: A deduplicated set containing all module name strings discovered across the entire tree.

    Raises: * This function does not raise exceptions.

    Example: 

    # Extracted from collect_all_modules implementation
section_tree = [
    {"name": "Root", "modules": ["main"], "children": [
        {"name": "Utils", "modules": ["call_llm", "token_utils"]}
    ]}
]
all_mods = collect_all_modules(section_tree)
# all_mods contains {'main', 'call_llm', 'token_utils'}

    Architectural & Integration Context

    Prompt Construction Strategy

    prompts.py isolates programmatic, algorithmic, and inline prompt assembly logic from file-based prompt templates (which are loaded from external .md files). This separation provides several architectural benefits:

    1. Context Window Protection: build_chapter_summary_prompt() constrains LLM responses to a four-point brief (Scope, Key Elements, Patterns, Integration), preventing unbounded growth in iterative context loops across multi-chapter documentation runs.
    2. Compact Parsing Contracts: build_code_file_filter_prompt() requests a minimal YAML integer array rather than repeating full paths. This design reduces JSON/YAML parsing errors and minimizes output token usage during the file mapping phase.
    3. Automated Structural Organization: build_grouped_nav() uses a deterministic fallback to group multi-directory sections without requiring additional LLM calls, keeping navigation trees organized while avoiding extra API latency.
