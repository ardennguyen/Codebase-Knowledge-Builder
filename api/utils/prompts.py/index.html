    prompts.py

    Source: utils/prompts.py

    Technical Overview

    While the presentation and diagnostic subsystem in output.py orchestrates terminal formatting, file logging, and dynamic catalog translation, utils/prompts.py acts as the deterministic template generator and documentation asset builder for internal LLM workflows. Rather than reading user-customizable prompt files from disk templates (such as those residing under prompts/{mode}/), this module provides specialized, hardcoded inline prompt factories and static configuration generators required by graph execution nodes during code analysis and documentation assembly.

    The module operates across two distinct domains within the pipeline. First, it standardizes prompt engineering for LLM-directed semantic operations, specifically file-type classification in API reference generation and four-dimensional chapter summarization for cross-chapter context propagation. Second, it serves as a site infrastructure generator, building complete, production-ready mkdocs.yml configurations, injecting JavaScript workarounds for Mermaid diagram styling, and deterministically assembling nested navigation trees from LLM-grouped abstraction hierarchies.

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Generates a zero-shot filtering prompt consumed by the DeterministicFileMapper execution node in api-reference mode. The prompt directs the language model to analyze a provided index-mapped file listing of the target codebase and isolate true source code modules—specifically files containing API endpoints, classes, callable functions, and core business logic. It provides explicit exclusion directives for UI markup, declarative configurations, static binaries, build scripts, and documentation files, constraining the model's output to a strictly formatted YAML list of integer indices.

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The resulting prompt string enforces strict output compliance by appending an explicit YAML code fence example (- 0\n- 1\n- 3). This constrains downstream inference models to emit parseable lists of integer offsets rather than verbose conversational explanations. Downstream graph nodes parse these emitted indices directly to slice the repository file list down to relevant compilation units, discarding peripheral configuration and visual assets before token counting or graph synthesis.

    Parameters: * project_name (str): The human-readable name or directory identifier of the target codebase under evaluation. * file_listing (str): A pre-formatted string containing numbered or index-delimited repository relative paths.

    Returns: * str: A fully compiled instruction prompt ready to be dispatched to call_llm().

    Raises: * This function does not raise internal exceptions.

    Example: 

    # Extracted from DeterministicFileMapper execution logic in nodes.py
prompt = build_code_file_filter_prompt(
    project_name="Codebase-Knowledge-Builder",
    file_listing="0: src/core.py\n1: README.md\n2: config.json\n3: src/utils.py"

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Constructs the instruction prompt utilized immediately following chapter generation to synthesize a dense, standardized technical brief. This brief serves as cross-chapter context in multi-pass documentation generation: by feeding structured summaries of previously written chapters into subsequent LLM prompts, the orchestrator preserves architectural coherence across large documents without saturating the model's context window. The prompt enforces four mandatory technical dimensions with an explicit 3–5 sentence density constraint per dimension, and optionally prefixes an internationalization directive when generating non-English documentation.

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.

    The summary captures 4 technical dimensions with 3-5 sentences each:
    1. Component scope & responsibility
    2. Key classes/services/functions and their roles
    3. Implementation patterns & architectural decisions
    4. Inter-component interfaces & dependencies
    """
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The function normalizes the language argument by evaluating language.lower() != "english", prepending a capitalized instruction prefix (Write the entire summary in {language.capitalize()}.) only when non-default localization is requested. The body of the prompt establishes four invariant dimensions covering scope, key technical elements, implementation patterns, and system integration. This strict quad-axis schema guarantees that downstream nodes in nodes.py ingest predictable, information-dense summaries regardless of which underlying LLM synthesized the original chapter.

    Parameters: * chapter_num (int): The 1-based sequential chapter number within the overall document outline. * abstraction_name (str): The semantic title or subsystem name designated for the chapter. * chapter_content (str): The raw Markdown text output generated for the chapter. * language (str, optional): Target language for the output summary. Defaults to "english".

    Returns: * str: The prompt payload directing the model to summarize the chapter across the four architectural dimensions.

    Raises: * This function does not raise internal exceptions.

    Example: 

    # Extracted from chapter generation post-processing in nodes.py
summary_prompt = build_chapter_summary_prompt(
    chapter_num=1,
    abstraction_name="call_llm.py",
    chapter_content="# call_llm.py\n\nCentralized inference gateway...",
    language="english"
)

    build_mermaid_init_js()

    Visibility: Public
    Signature: def build_mermaid_init_js() -> str:

    Description:
    Emits an immediately invoked function expression (IIFE) in JavaScript that handles client-side rendering of Mermaid diagrams within generated MkDocs sites. Standard Material for MkDocs installations automatically hijack standard <pre class="mermaid"> tags and apply destructive CSS overrides that alter subgraph fills, connector colors, and border shapes. To preserve native GitHub-like Mermaid styling (yellow subgraph backgrounds, lavender node containers, crisp edges), the configuration targets .mermaid-raw elements instead.

    def build_mermaid_init_js() -> str:
    """Build JS to initialize Mermaid on .mermaid-raw elements.

    Material for MkDocs applies its own color overrides to elements with
    class 'mermaid'. By using class 'mermaid-raw' in superfences config
    and initializing Mermaid manually, diagrams render with Mermaid's
    built-in default theme: yellow subgraph backgrounds, lavender nodes,
    clean rectangles — matching how GitHub renders Mermaid natively.
    """
    return """\
// Initialize Mermaid on .mermaid-raw elements (bypasses Material theme override)
// Material for MkDocs targets .mermaid class for its own color overrides.
// By using .mermaid-raw, diagrams render with Mermaid's default theme:
// yellow subgraph backgrounds, lavender nodes, clean rectangles.
//
// pymdownx.superfences fence_code_format wraps content as:
//   <pre class="mermaid-raw"><code>flowchart TD ...</code></pre>
// Mermaid expects the diagram text directly in the target element,
// so we unwrap the <code> child before calling mermaid.run().
(function() {
  function initMermaid() {
    if (typeof mermaid === 'undefined') return;
    try {
      // Unwrap: move <code> text content up to <pre> and remove <code>
      document.querySelectorAll('pre.mermaid-raw > code').forEach(function(code) {
        var pre = code.parentElement;
        pre.textContent = code.textContent;
      });
      mermaid.initialize({
        startOnLoad: false,
        theme: 'default',
        securityLevel: 'loose'
      });
      mermaid.run({ querySelector: '.mermaid-raw' }).catch(function(err) {
        console.warn('Mermaid render error:', err);
      });
    } catch (e) {
      console.warn('Mermaid init error:', e);
    }
  }
  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initMermaid);
  } else {
    initMermaid();
  }
})();
"""

    Because pymdownx.superfences wraps custom fence blocks into nested structures (<pre class="mermaid-raw"><code>...</code></pre>), the Mermaid runtime will fail if invoked directly upon the container. The generated JavaScript traverses all pre.mermaid-raw > code DOM elements, elevates the inner text content up to the parent <pre> container, and deletes the <code> element. It then initializes the global mermaid client with { startOnLoad: false, theme: 'default', securityLevel: 'loose' } and executes mermaid.run(). Initialization is attached to DOMContentLoaded if the document is still loading, or invoked immediately if the script executes post-load.

    Parameters: * None.

    Returns: * str: The raw JavaScript source code ready to be serialized to docs/javascripts/mermaid-init.js.

    Raises: * This function does not raise internal exceptions.

    Example: 

    # Extracted from static site asset serialization in nodes.py
js_content = build_mermaid_init_js()
os.makedirs("output/docs/javascripts", exist_ok=True)
with open("output/docs/javascripts/mermaid-init.js", "w", encoding="utf-8") as f:
    f.write(js_content)

    build_grouped_nav()

    Visibility: Public
    Signature: def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:

    Description:
    Recursively compiles a hierarchical section outline generated by LLM analysis into formatted YAML navigation lines suitable for mkdocs.yml. The function handles arbitrary nesting depths, matches leaf module names against concrete generated chapter files, and applies deterministic directory-based sub-grouping for modules located within subdirectories without requiring additional LLM calls.

    Recursive Section and Children Processing

        lines = []
    pad = " " * indent
    for section in sections:
        lines.append(f"{pad}- {section['name']}:")
        if "children" in section:
            lines.extend(build_grouped_nav(section["children"], chapter_files, indent + 2))
    The algorithm iterates through each section dictionary, rendering an indented YAML list item using pad (" " * indent). If the section declares a children list, it immediately recurses down the tree, increasing the indentation padding by two spaces (indent + 2) and appending the resulting child lines into the linear collection.

    Module Matching and Path Resolution

            # Collect matched modules with directory info
        matched = []
        for mod_name in section.get("modules", []):
            match = next((cf for cf in chapter_files if cf["module_name"] == mod_name), None)
            if match:
                dir_path = os.path.dirname(match.get("original_path", "")) or ""
                matched.append((dir_path, mod_name, match))

        # Group by directory
        from collections import defaultdict

        dir_groups = defaultdict(list)
        for dir_path, mod_name, match in matched:
            dir_groups[dir_path].append((mod_name, match))
    For modules assigned directly to the current section via section.get("modules", []), the function scans chapter_files using next(...) to locate the corresponding metadata dictionary where cf["module_name"] == mod_name. For each match, it calculates the parent directory path using os.path.dirname(match.get("original_path", "")) or "". It then buckets the matches into a collections.defaultdict(list) indexed by directory path.

    Navigation Line Emission

            # Emit dir sub-layers for non-root dirs, flat for root files
        has_non_root = any(d for d in dir_groups)
        if has_non_root:
            for dir_path in sorted(dir_groups.keys()):
                if dir_path:
                    # Non-root: add directory sub-layer with bare module names
                    lines.append(f"{pad}  - {dir_path}:")
                    for mod_name, match in dir_groups[dir_path]:
                        lines.append(f"{pad}    - '{mod_name}': 'api/{match['filename']}'")
                else:
                    # Root files: flat (no sub-layer)
                    for mod_name, match in dir_groups[dir_path]:
                        lines.append(f"{pad}  - '{mod_name}': 'api/{match['filename']}'")
        else:
            # All root files → flat list
            for _dir_path, mod_name, match in matched:
                lines.append(f"{pad}  - '{mod_name}': 'api/{match['filename']}'")

    return lines
    During line emission, the function evaluates whether any resolved modules reside in non-root directories via has_non_root. If non-root directories are present, directory sub-layers are synthesized: non-empty directories receive their own indented sub-heading ({pad} - {dir_path}:) containing bare module entries, while root-level files (dir_path == "") are emitted flat without intermediate directory wrappers. If all files are root-level, they are rendered as a simple list.

    Parameters: * sections (list): A list of dictionaries representing the LLM-derived hierarchical document plan. Each dictionary contains a 'name' string, optional 'modules' list of strings, and optional 'children' list of sub-section dictionaries. * chapter_files (list): A list of metadata dictionaries representing generated documentation chapters, requiring keys 'module_name', 'original_path', and 'filename'. * indent (int, optional): Number of leading spaces applied for YAML indentation. Defaults to 4.

    Returns: * list[str]: A list of formatted YAML navigation strings that can be joined with "\n" into a complete navigation tree.

    Raises: * This function does not raise internal exceptions. Unmatched module names are ignored safely.

    Example:

    Visibility: Public
    Signature: def collect_all_modules(sections: list) -> set:

    Description:
    Recursively inspects a section grouping hierarchy and extracts all module names referenced across all tree levels. This utility allows graph execution nodes to perform set-difference validation against the complete catalog of generated chapters, detecting orphaned modules that were omitted by the LLM during structural grouping.

    def collect_all_modules(sections: list) -> set:
    """Recursively collect all module names referenced in a sections tree."""
    result = set()
    for section in sections:
        result.update(section.get("modules", []))
        if "children" in section:
            result.update(collect_all_modules(section["children"]))
    return result

    The function instantiates an empty set and iterates through the input section dictionaries. It calls result.update() using section.get("modules", []), safely handling section nodes that omit the 'modules' key. If a child branch is encountered ("children" in section), the function recurses into collect_all_modules(section["children"]) and updates the set with the returned leaf elements.

    Parameters: * sections (list): A list of dictionaries representing the nested section hierarchy.

    Returns: * set: A deduplicated set containing all module names declared across the entire tree.

    Raises: * This function does not raise internal exceptions.

    Example:

    Internal Helpers

    This module does not declare any private helper functions (symbols prefixed with _) or internal utility closures. All prompt builders, configuration compilers, and navigation tree routines are designed for direct consumption by graph execution nodes and are exposed as part of the module's public interface.

    Chapter Technical Summary Schema

    Output structure enforced by the prompt generated in build_chapter_summary_prompt(). The language model is constrained to generate four distinct sections with 3–5 sentences each.

    Dimension Key Identifier Description
    Dimension 1 (1) **Component Scope & Responsibility** Defines the technical domain, core problem solved, and overall system role.
    Dimension 2 (2) **Key Technical Elements** Enumerates specific classes, services, functions, schemas, or protocols.
    Dimension 3 (3) **Implementation Patterns & Architecture** Details design patterns, data flows, error handling, and security mechanisms.
    Dimension 4 (4) **System Integration & Dependencies** Outlines consumed/provided interfaces, integration points, and upstream/downstream callers.

    Error Handling

    utils/prompts.py relies on defensive data retrieval and graceful degradation rather than explicit exception raising:

    • Missing Key Resilience in Nav Construction: build_grouped_nav() avoids raising KeyError when parsing partial LLM dictionaries by using section.get("modules", []) and match.get("original_path", "").
    • Safe Unmatched Module Handling: When a module declared in section["modules"] does not exist in chapter_files, next((cf for cf in chapter_files if cf["module_name"] == mod_name), None) resolves to None. The loop condition if match: silently skips unmatched elements without interrupting the recursion.
    • Empty YAML Navigation Safety: In build_mkdocs_config(), splitting empty or single-line strings is handled safely via "\n".join(nav_lines[1:]) if nav_lines else "", preventing IndexError exceptions.
    • Client-Side JavaScript Isolation: The script generated by build_mermaid_init_js() wraps all DOM node extraction and Mermaid execution inside try ... catch (e) blocks. If the Mermaid library is blocked by content security policies or fails to parse a diagram syntax tree, the error is caught and logged via console.warn rather than halting other client-side page scripts.
