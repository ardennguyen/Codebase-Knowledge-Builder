    prompts.py

    Source: utils/prompts.py

    This module provides internal programmatic prompt generation utilities, configuration templates, and navigation tree builders for the Codebase-Knowledge-Builder documentation pipeline. While standard chapter authoring workflows rely on external Jinja2 or file-based prompt templates, utils/prompts.py centralizes hardcoded, deterministic prompt routines and MkDocs asset generation logic required by pipeline coordination nodes.

    Following the logging and diagnostic formatting capabilities provided by output.py and the low-level inference mechanisms in call_llm.py, this module supplies specialized prompt builders for codebase file filtering and cross-chapter technical summarization. It also encapsulates the structural logic for converting abstract documentation outlines into hierarchical MkDocs navigation trees (mkdocs.yml) and JavaScript harnesses for rendering Mermaid diagrams.

    Architectural Role & Execution Flow

    The functions in utils/prompts.py operate across two distinct phases of the documentation generation lifecycle:

    1. LLM Task Construction (Inference Phase): Constructing deterministic, structured prompts for LLM execution tasks that do not require external template files. This includes filtering raw repository file trees down to core business logic modules (build_code_file_filter_prompt) and generating structured technical briefs after each chapter is written (build_chapter_summary_prompt) to maintain context across execution boundaries.
    2. Site Generation & Navigation Structuring (Post-Processing Phase): Transforming LLM-derived document taxonomies into recursive navigation structures (build_grouped_nav, collect_all_modules), emitting standardized Material for MkDocs configuration files (build_mkdocs_config), and injecting browser-side runtime scripts (build_mermaid_init_js) to ensure diagram styling parity with native GitHub rendering.

    Module-Level Functions

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Constructs an inline prompt string instructing the LLM to act as a deterministic file mapper. This prompt is utilized primarily in api-reference documentation mode to filter out non-code assets (such as UI markups, build manifests, configuration scripts, and documentation) from the discovered file listing, isolating files that contain core business logic, APIs, functions, and data structures. It enforces a strict output format by requiring the LLM to return only a YAML list containing the integer indices corresponding to valid code modules.

    Parameters: * project_name (str): The name of the project or repository being analyzed. * file_listing (str): A formatted string containing the numbered index list of all files discovered in the codebase.

    Returns: * str: A formatted prompt containing the task description, exclusion criteria, input file listing, and a target YAML code block template.

    Raises: * This function does not raise exceptions internally; string formatting handles all standard input types.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The string produced by build_code_file_filter_prompt provides explicit negative constraints to prevent downstream documentation overhead on build manifests (such as .csproj and .sln) and static UI assets (.xaml, .storyboard, .html). By directing the model to output a strictly indexed YAML block (- 0\n- 1), the pipeline in nodes.py can deterministically parse the integer array via standard YAML deserializers and map it directly back to file list indices without fuzzy string matching.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Generates the prompt used to synthesize a structured technical brief from a newly generated documentation chapter. The resulting summary captures four standardized dimensions: component scope, technical elements, implementation patterns, and system integration points. This summary is injected into subsequent chapter generation contexts to ensure architectural continuity and terminology consistency across long-form multi-chapter runs.

    Parameters: * chapter_num (int): The numeric sequence index of the chapter being summarized. * abstraction_name (str): The title or high-level architectural abstraction represented by the chapter. * chapter_content (str): The full Markdown text content of the generated chapter. * language (str, optional): The target natural language for the summary output. Defaults to "english".

    Returns: * str: The prompt directing the LLM to generate the 4-part structured technical brief.

    Raises: * This function does not raise exceptions internally.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The prompt enforces a four-part structural template where each section requires 3 to 5 concise technical sentences. This constraint prevents conversational degradation and bounds the token budget consumed when earlier summaries are concatenated into the prompt contexts of later chapters. When a non-English language is passed, the function prefixes an explicit directive (Write the entire summary in {language.capitalize()}.) ensuring multilingual synthesis remains uniform across the pipeline.

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description:
    Assembles a complete, production-ready mkdocs.yml configuration string for rendering documentation using Material for MkDocs. The configuration enables clipboard copy buttons, dark/light theme switching, code syntax highlighting, pan-and-zoom controls for diagrams, and superfences custom fence parsing targeting the .mermaid-raw CSS class.

    Parameters: * site_name (str): The documentation title displayed in the header and metadata. * nav_yaml (str): A YAML-formatted string representing the navigation tree, typically emitted by build_grouped_nav.

    Returns: * str: A valid, self-contained mkdocs.yml file content string.

    Raises: * This function does not raise exceptions internally.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"    - navigation.indexes\n"
        f"  palette:\n"
        f"    - scheme: default\n"
        f"      toggle:\n"
        f"        icon: material/brightness-7\n"
        f"        name: Switch to dark mode\n"
        f"    - scheme: slate\n"
        f"      toggle:\n"
        f"        icon: material/brightness-4\n"
        f"        name: Switch to light mode\n"
        f"plugins:\n"
        f"  - search\n"
        f"  - panzoom:\n"
        f"      include_selectors:\n"
        f"        - '.mermaid-raw'\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid-raw\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"extra_javascript:\n"
        f"  - https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.min.js\n"
        f"  - javascripts/mermaid-init.js\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The function processes nav_yaml by stripping any leading nav: declaration to prevent duplicate top-level YAML keys before concatenating the navigation body underneath - Home: index.md. It explicitly configures pymdownx.superfences to route Mermaid code blocks into a custom CSS class named mermaid-raw. This mechanism bypasses Material for MkDocs' built-in Mermaid color overrides, allowing diagrams to render with Mermaid's default palette via CDN-loaded Mermaid 11 and a companion initialization script.

    build_mermaid_init_js()

    Visibility: Public
    Signature: def build_mermaid_init_js() -> str:

    Description:
    Generates the browser-side JavaScript runtime script used to initialize Mermaid diagrams. Because pymdownx.superfences wraps custom fence blocks inside <pre class="mermaid-raw"><code>...</code></pre>, standard Mermaid rendering engines fail to parse the inner block directly. This script unwraps the nested <code> text content into the parent <pre> node, initializes Mermaid with default theme settings and loose security levels, and triggers dynamic rendering against all .mermaid-raw selectors.

    Parameters: * None.

    Returns: * str: The complete JavaScript source code to be written to javascripts/mermaid-init.js.

    Raises: * This function does not raise exceptions.

    Example: 

    def build_mermaid_init_js() -> str:
    return """\
// Initialize Mermaid on .mermaid-raw elements (bypasses Material theme override)
// Material for MkDocs targets .mermaid class for its own color overrides.
// By using .mermaid-raw, diagrams render with Mermaid's default theme:
// yellow subgraph backgrounds, lavender nodes, clean rectangles.
//
// pymdownx.superfences fence_code_format wraps content as:
//   <pre class="mermaid-raw"><code>flowchart TD ...</code></pre>
// Mermaid expects the diagram text directly in the target element,
// so we unwrap the <code> child before calling mermaid.run().
(function() {
  function initMermaid() {
    if (typeof mermaid === 'undefined') return;
    try {
      // Unwrap: move <code> text content up to <pre> and remove <code>
      document.querySelectorAll('pre.mermaid-raw > code').forEach(function(code) {
        var pre = code.parentElement;
        pre.textContent = code.textContent;
      });
      mermaid.initialize({
        startOnLoad: false,
        theme: 'default',
        securityLevel: 'loose'
      });
      mermaid.run({ querySelector: '.mermaid-raw' }).catch(function(err) {
        console.warn('Mermaid render error:', err);
      });
    } catch (e) {
      console.warn('Mermaid init error:', e);
    }
  }
  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', initMermaid);
  } else {
    initMermaid();
  }
})();
"""

    The script implements defensive DOM lifecycle handling: if the document is currently in a 'loading' state, it binds execution to the DOMContentLoaded event; otherwise, it executes initMermaid() synchronously. Inside the initialization handler, it wraps DOM transformations and calls to mermaid.run() within try/catch blocks and Promise rejections, ensuring that syntax errors in LLM-generated diagrams log non-fatal warnings to the browser console rather than interrupting other client-side documentation features.

    build_grouped_nav()

    Visibility: Public
    Signature: def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:

    Description:
    Recursively builds MkDocs navigation YAML lines from a structured section hierarchy. The function handles arbitrary nesting depths via recursive traversal of section children nodes. For leaf modules, it matches module names against chapter_files metadata to determine physical directory paths. Files residing within subdirectories are deterministically grouped into directory sub-layers with bare module names, while root-level files remain flat under their section heading.

    Parameters: * sections (list): A list of dictionaries representing the hierarchical section outline. Each dictionary may contain "name", "modules" (list of module identifiers), and "children" (nested section dictionaries). * chapter_files (list): A list of metadata dictionaries for generated chapter files, containing keys such as "module_name", "original_path", and "filename". * indent (int, optional): The base indentation level (in spaces) for the current YAML nesting depth. Defaults to 4.

    Returns: * list[str]: A list of properly indented YAML string lines representing the navigation tree.

    Raises: * This function does not raise exceptions internally.

    Example: 

    def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:
    lines = []
    pad = " " * indent
    for section in sections:
        lines.append(f"{pad}- {section['name']}:")
        if "children" in section:
            lines.extend(build_grouped_nav(section["children"], chapter_files, indent + 2))

        # Collect matched modules with directory info
        matched = []
        for mod_name in section.get("modules", []):
            match = next((cf for cf in chapter_files if cf["module_name"] == mod_name), None)
            if match:
                dir_path = os.path.dirname(match.get("original_path", "")) or ""
                matched.append((dir_path, mod_name, match))

        # Group by directory
        from collections import defaultdict

        dir_groups = defaultdict(list)
        for dir_path, mod_name, match in matched:
            dir_groups[dir_path].append((mod_name, match))

        # Emit dir sub-layers for non-root dirs, flat for root files
        has_non_root = any(d for d in dir_groups)
        if has_non_root:
            for dir_path in sorted(dir_groups.keys()):
                if dir_path:
                    # Non-root: add directory sub-layer with bare module names
                    lines.append(f"{pad}  - {dir_path}:")
                    for mod_name, match in dir_groups[dir_path]:
                        lines.append(f"{pad}    - '{mod_name}': 'api/{match['filename']}'")
                else:
                    # Root files: flat (no sub-layer)
                    for mod_name, match in dir_groups[dir_path]:
                        lines.append(f"{pad}  - '{mod_name}': 'api/{match['filename']}'")
        else:
            # All root files → flat list
            for _dir_path, mod_name, match in matched:
                lines.append(f"{pad}  - '{mod_name}': 'api/{match['filename']}'")

    return lines

    build_grouped_nav coordinates path resolution by inspecting os.path.dirname(match.get("original_path", "")). It isolates module paths using collections.defaultdict(list) to partition files across directories without requiring additional LLM calls. If non-root directories are present (has_non_root is True), sorted directory headings are emitted at an intermediate indent level (pad + " "), and their child modules are nested underneath (pad + " "). If all files belong to the root level, the directory grouping step is bypassed, rendering an unnested list under the section heading.

    collect_all_modules()

    Visibility: Public
    Signature: def collect_all_modules(sections: list) -> set:

    Description:
    Performs a recursive traversal over a nested section dictionary tree to extract a deduplicated set of all referenced module names. This utility enables validation checks ensuring that every documented chapter is accounted for in the structural navigation outline.

    Parameters: * sections (list): A list of dictionaries representing the hierarchical section outline, where dictionaries may contain a "modules" list and a nested "children" list.

    Returns: * set: A Python set containing all unique module identifier strings extracted from the tree.

    Raises: * This function does not raise exceptions internally.

    Example: 

    def collect_all_modules(sections: list) -> set:
    """Recursively collect all module names referenced in a sections tree."""
    result = set()
    for section in sections:
        result.update(section.get("modules", []))
        if "children" in section:
            result.update(collect_all_modules(section["children"]))
    return result

    The function initializes an empty set and iterates through each section dictionary, updating the accumulator set with the contents of the current section's "modules" list (defaulting to an empty list via .get("modules", []) if the key is missing). If the section contains a "children" key, collect_all_modules calls itself recursively on the child array and unions the resulting set using result.update(), guaranteeing complete coverage regardless of tree depth.

    Data Structures & Navigation Hierarchy

    The navigation utilities (build_grouped_nav and collect_all_modules) operate over standardized JSON/YAML schema trees generated by the LLM during architecture decomposition:

    # Conceptual Schema for `sections` input:
- name: "Core Engine"
  modules:
    - "call_llm.py"
    - "flow.py"
  children:
    - name: "File Ingestion"
      modules:
        - "crawl_github_files.py"
        - "crawl_local_files.py"

    The matching chapter_files array supplies the metadata needed to bridge logical module names to generated Markdown artifacts:

    # Conceptual Schema for `chapter_files` entries:
{
    "module_name": "crawl_github_files.py",
    "original_path": "utils/crawl_github_files.py",
    "filename": "utils_crawl_github_files.py.md"
}

    When rendered through build_grouped_nav(), this structure is converted into the following formatted YAML layout:

        - Core Engine:
      - 'call_llm.py': 'api/call_llm.py.md'
      - 'flow.py': 'api/flow.py.md'
      - File Ingestion:
        - utils:
          - 'crawl_github_files.py': 'api/utils_crawl_github_files.py.md'
          - 'crawl_local_files.py': 'api/utils_crawl_local_files.py.md'
