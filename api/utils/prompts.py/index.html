    prompts.py

    Source: utils/prompts.py

    Following the console telemetry and localization mechanics documented in output.py, the prompts.py module serves as the programmatic prompt construction and static documentation configuration layer for the Codebase-Knowledge-Builder system. While static markdown templates located under prompts/{mode}/ define the high-level generation instructions for chapters, prompts.py encapsulates dynamic, inline prompt builders and structural serialization logic required across orchestration workflows and site compilation phases.

    Specifically, the module provides targeted prompt assembly routines for deterministic file filtering and iterative cross-chapter technical brief generation. Additionally, it contains the MkDocs site configuration and navigation generator, which translates hierarchical AST/module group structures into compliant YAML navigation trees and custom JavaScript assets for diagram rendering.

    Architecture and Execution Flows

    The functions in prompts.py participate in two distinct operational phases: 1. Dynamic LLM Prompt Synthesis: Constructing parameterized instruction strings for downstream execution via call_llm.py within orchestration nodes defined in nodes.py. 2. Static Site and Navigation Compilation: Transforming hierarchical section trees into valid mkdocs.yml configurations, directory-aware navigation trees, and custom Mermaid initialization scripts for documentation artifact output.

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Constructs an inline LLM prompt designed for DeterministicFileMapper in api-reference documentation mode. The prompt instructs the model to inspect an indexed repository file list and isolate true source code modules—such as APIs, service classes, function declarations, and business logic—from non-code artifacts including UI markup (.xaml, .storyboard, .html), configuration manifests (.xml, .json, .ini), build system definitions (.csproj, .sln), static assets, and pre-existing documentation. It enforces a strict output contract requiring the model to return exclusively a YAML-formatted list of integer indices corresponding to the accepted code files.

    Parameters: * project_name (str): The name of the target repository or software project being analyzed. * file_listing (str): A pre-formatted, numbered string listing all crawled candidate file paths in the codebase.

    Returns: * str: The fully populated prompt string ready for submission to the LLM backend.

    Raises: * No explicit exceptions raised; standard string interpolation semantics apply.

    Implementation: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The function executes zero-copy f-string formatting, embedding the target repository identifier and raw index list directly into the prompt template. By enforcing a constrained YAML schema with an explicit few-shot code block example (- 0\n- 1\n- 3), the prompt prevents conversational drift, markdown explanations, or parsing errors when deserialized downstream by workflow nodes.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Assembles the prompt responsible for synthesizing a dense technical summary of a newly generated documentation chapter. This summary is injected into subsequent chapter generation prompts as rolling cross-chapter context, preventing semantic drift, redundancy, and terminology mismatch across long documentation generation runs. The prompt requires the model to structure the summary into four concrete technical dimensions (Component Scope & Responsibility, Key Technical Elements, Implementation Patterns & Architecture, and System Integration & Dependencies), allocating 3 to 5 sentences per dimension. If a non-English target language is configured, it prepends an explicit localization directive.

    Parameters: * chapter_num (int): The ordinal sequence number of the chapter within the documentation outline. * abstraction_name (str): The title, module name, or conceptual abstraction covered by the chapter. * chapter_content (str): The complete markdown text of the generated chapter to be summarized. * language (str, optional): Target language for the summary output. Defaults to "english".

    Returns: * str: The prompt string formatted with technical analysis requirements, chapter metadata, and content body.

    Raises: * No explicit exceptions raised.

    Implementation: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.

    The summary captures 4 technical dimensions with 3-5 sentences each:
    1. Component scope & responsibility
    2. Key classes/services/functions and their roles
    3. Implementation patterns & architectural decisions
    4. Inter-component interfaces & dependencies
    """
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The function handles dynamic multilingual support by evaluating language.lower(). If the requested language is not English, it synthesizes a prefix instruction (Write the entire summary in <Language>.) with normalized casing via capitalize(). The prompt explicitly dictates the four-part section headers, ensuring consistent structural parity across generated briefs so downstream parsers and prompts can rely on uniform headings.

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description:
    Generates a complete, standalone mkdocs.yml configuration file string tailored for local static documentation sites rendered with the Material for MkDocs theme. The configuration enables syntax highlighting via pymdownx.highlight, inline code highlighting, custom superfences for Mermaid diagrams utilizing the .mermaid-raw CSS class, search indexing, and interactive zoom/pan capabilities via the panzoom plugin. It strips the root nav: key from the input YAML snippet and nests the navigation body beneath the default Home: index.md landing page entry.

    Parameters: * site_name (str): The human-readable title of the project to display in the MkDocs header and page metadata. * nav_yaml (str): A multi-line YAML string defining the navigation hierarchy (typically generated by build_grouped_nav() or an outline mapper).

    Returns: * str: The complete YAML configuration string ready to be written to disk as mkdocs.yml.

    Raises: * No explicit exceptions raised; handles empty or malformed strings gracefully.

    Implementation: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    """Build a complete mkdocs.yml for local --mkdocs output.

    Generates a ready-to-use MkDocs Material config with:
    - Material theme with code copy buttons
    - Syntax highlighting (pymdownx.highlight + inlinehilite)
    - Mermaid diagram rendering via custom 'mermaid-raw' class (bypasses
      Material's Mermaid color overrides so diagrams use Mermaid's default theme)
    - Panzoom plugin for interactive Mermaid diagram zoom/pan
    - Navigation from the generated nav_snippet

    Users can run `mkdocs serve` or `mkdocs build` directly in the output dir.
    """
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"    - navigation.indexes\n"
        f"  palette:\n"
        f"    - scheme: default\n"
        f"      toggle:\n"
        f"        icon: material/brightness-7\n"
        f"        name: Switch to dark mode\n"
        f"    - scheme: slate\n"
        f"      toggle:\n"
        f"        icon: material/brightness-4\n"
        f"        name: Switch to light mode\n"
        f"plugins:\n"
        f"  - search\n"
        f"  - panzoom:\n"
        f"      include_selectors:\n"
        f"        - '.mermaid-raw'\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid-raw\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"extra_javascript:\n"
        f"  - https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.min.js\n"
        f"  - javascripts/mermaid-init.js\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The function isolates the navigation hierarchy by splitting nav_yaml across newline boundaries and slicing past the first line (nav_lines[1:]), stripping away any redundant top-level nav: token before appending the items under the explicit Home: index.md root. It registers custom superfences under markdown_extensions.pymdownx.superfences that map mermaid code blocks to the .mermaid-raw CSS class using PyMdown's Python callback fence_code_format. This allows the custom initializer script generated by build_mermaid_init_js() to handle diagram lifecycle without interfering with Material theme defaults.

    build_mermaid_init_js()

    Visibility: Public
    Signature: def build_mermaid_init_js() -> str:

    Description:
    Generates a raw JavaScript snippet designed to initialize and render Mermaid diagrams that use the .mermaid-raw class. MkDocs Material applies aggressive CSS variable overrides to standard .mermaid elements, often leading to unreadable diagrams, altered edge styles, or distorted color palettes. By configuring pymdownx.superfences to emit .mermaid-raw instead, and loading this script via extra_javascript, Mermaid renders with its native default theme (yellow subgraph backgrounds, lavender entity nodes, and sharp rectangular containers), mirroring the standard rendering behavior of GitHub markdown previews.

    Parameters: * None.

    Returns: * str: The complete JavaScript source code string to be written to javascripts/mermaid-init.js.

    Raises: * No explicit exceptions raised.

    Implementation: 

    def build_mermaid_init_js() -> str:
    """Build JS to initialize Mermaid on .mermaid-raw elements.

    Material for MkDocs targets .mermaid class for its own color overrides.
    By using .mermaid-raw, diagrams render with Mermaid's default theme:
    yellow subgraph backgrounds, lavender nodes, clean rectangles.
    """
    return """\
// Initialize Mermaid on .mermaid-raw elements (bypasses Material theme override)
// Material for MkDocs targets .mermaid class for its own color overrides.
// By using .mermaid-raw, diagrams render with Mermaid's default theme:
// yellow subgraph backgrounds, lavender nodes, clean rectangles.
document.addEventListener('DOMContentLoaded', function() {
  if (typeof mermaid !== 'undefined') {
    mermaid.initialize({ startOnLoad: false, theme: 'default' });
    mermaid.run({ querySelector: '.mermaid-raw' });
  }
});
"""

    The returned JavaScript hooks into the browser's DOMContentLoaded lifecycle event. It defensively checks for the existence of the global mermaid runtime (loaded via CDN), disables automated load-time processing (startOnLoad: false), sets the active theme to default, and calls mermaid.run() targeting the .mermaid-raw selector. This architecture decouples diagram layout from MkDocs Material's built-in theme scripts.

    build_grouped_nav()

    Visibility: Public
    Signature: def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:

    Description:
    Recursively constructs a list of indented YAML navigation lines from a hierarchical section group definition produced by LLM clustering nodes. It traverses arbitrary nesting levels via the children list attribute. For leaf nodes, it matches module names against chapter_files by module_name and determines each file's containing directory using os.path.dirname(match.get("original_path", "")). If modules within a functional section originate from multiple distinct directory paths, the function dynamically introduces an intermediate directory sub-grouping layer sorted alphabetically. If all modules originate from a single directory (or have no directory path), it produces a flat list to prevent unnecessary navigation nesting.

    Parameters: * sections (list): A list of dictionary objects representing functional sections. Each section dictionary may contain name (str), children (list[dict]), and modules (list[str]). * chapter_files (list): A list of metadata dictionaries for generated chapters. Each entry must contain module_name (str), filename (str), and optionally original_path (str). * indent (int, optional): The indentation spacing (number of spaces) for the current YAML level. Defaults to 4.

    Returns: * list[str]: An ordered list of formatted YAML strings representing the navigation hierarchy.

    Raises: * No explicit exceptions raised; missing section keys degrade gracefully via .get().

    Implementation: 

    def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:
    """Recursively build MkDocs nav YAML lines from LLM section grouping.

    Handles arbitrary nesting depth via the ``children`` key.
    Each leaf module is matched against *chapter_files* by ``module_name``.
    When a functional group spans multiple directories, files are auto-sub-grouped
    by their full directory path (deterministic, no extra LLM call).
    Single-directory groups remain flat (no useless nesting).
    """
    lines = []
    pad = " " * indent
    for section in sections:
        lines.append(f"{pad}- {section['name']}:")
        if "children" in section:
            lines.extend(build_grouped_nav(section["children"], chapter_files, indent + 2))

        # Collect matched modules with directory info
        matched = []
        for mod_name in section.get("modules", []):
            match = next((cf for cf in chapter_files if cf["module_name"] == mod_name), None)
            if match:
                dir_path = os.path.dirname(match.get("original_path", "")) or ""
                matched.append((dir_path, mod_name, match))

        # Group by directory
        from collections import defaultdict

        dir_groups = defaultdict(list)
        for dir_path, mod_name, match in matched:
            dir_groups[dir_path].append((mod_name, match))

        if len(dir_groups) > 1:
            # Multiple directories → add dir sub-layer with full path
            for dir_path in sorted(dir_groups.keys()):
                label = dir_path or "(root)"
                lines.append(f"{pad}  - {label}:")
                for mod_name, match in dir_groups[dir_path]:
                    lines.append(f"{pad}    - '{mod_name}': 'api/{match['filename']}'")
        else:
            # Single directory or no original_path → flat list
            for mod_name, match in matched:
                lines.append(f"{pad}  - '{mod_name}': 'api/{match['filename']}'")

    return lines

    The algorithm evaluates the multi-directory threshold by checking len(dir_groups) > 1. When true, it sorts the directory keys, assigns (root) to empty top-level paths, and creates a nested level (pad + " ") before listing the individual files with relative targets mapped to 'api/{filename}'. When false, it bypasses the directory layer entirely, keeping the YAML tree shallow. The recursive step increments indent by 2 for nested section containers, guaranteeing strict structural indentation compliance required by YAML parsers.

    collect_all_modules()

    Visibility: Public
    Signature: def collect_all_modules(sections: list) -> set:

    Description:
    Recursively inspects a hierarchical section tree and aggregates all declared module names into a flat set. It processes the modules list of each section at the current depth and recursively traverses any nested subsections defined in the children key.

    Parameters: * sections (list): A list of section dictionary structures containing modules (list[str]) and optional children (list[dict]).

    Returns: * set: An unordered set containing all unique module name strings discovered across the entire tree.

    Raises: * No explicit exceptions raised; missing modules keys default safely to empty lists via .get().

    Implementation: 

    def collect_all_modules(sections: list) -> set:
    """Recursively collect all module names referenced in a sections tree."""
    result = set()
    for section in sections:
        result.update(section.get("modules", []))
        if "children" in section:
            result.update(collect_all_modules(section["children"]))
    return result

    The function initializes an empty set and uses result.update() to absorb module entries without creating duplicates. When it encounters a children key in a section dictionary, it invokes itself recursively and merges the returned set into result. This utility is primarily used by validation routines to verify that all discovered codebase modules have been assigned to sections prior to site generation.
