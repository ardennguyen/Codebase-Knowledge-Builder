    utils.token_utils

    File Path: utils/token_utils.py

    Technical Overview

    The utils.token_utils module provides token counting, estimation, and diagnostic logging utilities for the Codebase-Knowledge-Builder pipeline. When orchestrating multi-stage Large Language Model (LLM) workflows across complex codebases, monitoring prompt token consumption is essential to prevent exceeding model context windows and to profile pipeline stage resource usage.

    The module manages a lazy-loaded singleton instance of the cl100k_base BPE (Byte Pair Encoding) tokenizer via tiktoken. It provides fallback heuristics (character count division) if tokenizer initialization fails or if tiktoken encounters unexpected environments. In addition, it formats and emits granular, colorized terminal metrics alongside structured single-line logs into the shared application logger (llm_logger).

    Token Estimation Architecture

    flowchart TD
    A[Input Text / Prompt] --> B{Is text empty?}
    B -- Yes --> C[Return 0 Tokens]
    B -- No --> D[_get_encoding]
    D --> E{Encoding Loaded?}
    E -- Yes --> F[enc.encode text without special tokens]
    F --> G[Return token count]
    E -- No --> H[Fallback: len text // 4]
    H --> G
    G --> I[log_token_estimation]
    I --> J[Compute capacity percentage]
    I --> K[Format optional token_usage breakdown]
    I --> L[ANSI Yellow Console Print]
    I --> M[llm_logger.info Structured Log]

    Module Variables

    logger

    • Type: logging.Logger
    • Description: Module-level logger bound to the "llm_logger" namespace. Reuses the shared logging channel configured by utils.call_llm to record execution diagnostics and token capacity measurements across nodes.

    _encoding

    • Type: tiktoken.Encoding | None
    • Description: Module-level private singleton cache storing the lazily evaluated tiktoken encoding instance. Initialized to None and resolved on demand by _get_encoding().

    Module-Level Functions

    _get_encoding()

    Visibility: Private
    Signature: def _get_encoding() -> tiktoken.Encoding | None:

    Description: Retrieves or lazily initializes the cl100k_base tokenizer encoding. It manages a module-scoped singleton cache variable _encoding. If the encoder has not yet been initialized, it attempts to load cl100k_base via tiktoken.get_encoding(). If an exception is raised (e.g., missing tokenizer data files or environment constraints), it catches all standard exceptions, resets _encoding to None, and returns None to enable graceful fallback counting.

    Parameters: * None.

    Returns: * tiktoken.Encoding | None: The initialized cl100k_base encoding object if successful, or None if initialization failed.

    Raises: * No exceptions are raised; internal initialization errors are caught and suppressed to allow fallback behavior.

    Example: 

    def _get_encoding():
    global _encoding
    if _encoding is None:
        try:
            _encoding = tiktoken.get_encoding("cl100k_base")
        except Exception:
            _encoding = None
    return _encoding

    The _get_encoding function implements a thread-compatible lazy initialization pattern. By deferring the load of cl100k_base until the first token counting invocation, module import overhead is minimized. When tokenizer initialization fails, setting _encoding = None guarantees that downstream callers such as count_tokens can seamlessly switch to fallback character-heuristic estimation without interrupting runtime execution.

    count_tokens()

    Visibility: Public
    Signature: def count_tokens(text: str) -> int:

    Description: Calculates the number of tokens required to encode a given string. If text is empty or falsy, it immediately returns 0. When text is present, it attempts to obtain a tiktoken encoder via _get_encoding(). If an encoder is available, it encodes the string with disallowed_special=() (disabling special token checks so raw code containing tokens like <|endoftext|> is parsed safely as regular text) and returns the length of the token list. If no encoder is available, it estimates token usage using the standard heuristic formula len(text) // 4.

    Parameters: * text (str): The input string or prompt content to measure.

    Returns: * int: The exact or estimated token count.

    Raises: * No exceptions are raised directly by this function.

    Example: 

    def count_tokens(text: str) -> int:
    """Count tokens using tiktoken, with fallback to chars/4."""
    if not text:
        return 0
    enc = _get_encoding()
    if enc:
        return len(enc.encode(text, disallowed_special=()))
    return len(text) // 4

    The count_tokens function serves as the core token accounting utility throughout the pipeline. Disallowing special token restrictions (disallowed_special=()) is critical when parsing raw codebase source files, which may inadvertently contain strings matching reserved OpenAI special tokens. The fallback calculation len(text) // 4 ensures continuous operation in offline environments or environments where external network access to fetch tokenizer tables is blocked.

    log_token_estimation()

    Visibility: Public
    Signature: def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:

    Description: Calculates token metrics for a specific pipeline execution node and emits both human-readable terminal output and machine-parseable log entries. It measures prompt_content using count_tokens, computes the percentage of the node's maximum token budget (max_tokens), and optionally breaks down token allocations if a dictionary of named token segments (token_usage) is supplied.

    The console output is formatted using ANSI yellow escape sequences (\033[93m ... \033[0m) with aligned columns for breakdown metrics. The file log is written to logger.info as a single-line record prefixed with NODE EXEC to facilitate structured log parsing and log ingestion pipelines.

    Parameters: * node_name (str): Identifier of the executing workflow node (e.g., "file_analysis", "architecture_overview"). * prompt_content (str): The full rendered prompt payload passed to the LLM. * max_tokens (int): Maximum context window or token ceiling configured for the node. * token_usage (dict | None, optional): A mapping of sub-component labels (e.g., "System Prompt", "File Context") to their respective integer token counts for granular usage breakdown. Defaults to None.

    Returns: * None

    Raises: * No exceptions are raised; zero-division is guarded for max_tokens=0 and token_count=0.

    Example: 

    def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:
    token_count = count_tokens(prompt_content)
    percentage = (token_count / max_tokens) * 100 if max_tokens else 0

    # Build token usage string if provided
    usage_str = ""
    usage_log_str = ""
    if token_usage:
        # Find the longest label for alignment
        max_label_len = max(len(label) for label in token_usage)
        lines = []
        log_parts = []
        for label, value in token_usage.items():
            pct = (value / token_count * 100) if token_count else 0
            padded_label = label.ljust(max_label_len)
            lines.append(f"\t{padded_label} : {value:,} ({pct:.0f}%)")
            log_parts.append(f"{label}={value:,} ({pct:.0f}%)")
        usage_str = "\n" + "\n".join(lines)
        usage_log_str = " | " + " | ".join(log_parts)

    # Console output (yellow) with token usage on separate lines
    print(f"\033[93m[Token Analytics] {node_name}: {token_count:,} / {max_tokens:,} tokens ({percentage:.1f}% capacity){usage_str}\033[0m")

    # File log stays single-line for parseability
    logger.info(f"NODE EXEC | node={node_name} | prompt_tokens={token_count:,} / {max_tokens:,} ({percentage:.1f}% capacity){usage_log_str}")

    log_token_estimation provides real-time observability into the context window utilization of individual pipeline nodes. When token_usage mappings are provided, it dynamically calculates field padding using max(len(label) for label in token_usage) and computes relative percentage allocations. The dual-destination logging approach decouples immediate developer terminal feedback from automated log aggregation systems.
