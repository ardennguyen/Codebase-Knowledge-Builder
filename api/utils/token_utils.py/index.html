    token_utils.py

    Source: utils/token_utils.py

    Technical Overview

    Operating downstream from the cognitive allocation framework established in thinking.py—which assigns granular reasoning budgets across pipeline execution nodes—token_utils.py serves as the centralized token calculation, context sizing, and prompt capacity management engine for the Codebase-Knowledge-Builder architecture. Large-scale codebase analysis tasks require prompt packing near context ceilings, creating risks of prompt truncation, silent buffer overflow, or API rejections due to unreserved output space. This module isolates the mechanics of token counting, model-specific token ratio scaling, context window resolution, and telemetry logging to ensure pipeline nodes operate safely within provider boundaries.

    The component interfaces directly with OpenAI's tiktoken library using the cl100k_base BPE (Byte Pair Encoding) tokenizer as a reference metric. Because importing vendor-specific tokenizers (such as Anthropic Claude or Google Gemini tokenizers) introduces heavy native dependencies and latency overhead, token_utils.py pairs tiktoken with calibrated scaling multipliers sourced from llm_config.py via get_token_ratio(). For resilience against missing native C-bindings or system architecture incompatibilities, the module incorporates a deterministic fallback heuristic (len(text) // 4). Context window bounds are dynamically computed through provider-aware reservation algorithms: models sharing unified prompt-and-output contexts reserve planned thinking and completion space alongside flat margins, while decoupled architectures (such as Google Gemini) apply isolated margins.

    Telemetry and operational visibility are integrated directly into prompt sizing operations. The module interfaces with output.py and Python's standard logging infrastructure to emit real-time token capacity metrics, styled ANSI console warnings, and structured log records detailing prompt payload compositions. This telemetry allows upstream pipeline drivers in nodes.py and flow.py to audit memory consumption and token distributions before initiating model inference.

    Public API

    resolve_max_tokens()

    Visibility: Public
    Signature: def resolve_max_tokens(shared: dict) -> int:

    Description: Resolves the maximum context window token limit for the current execution cycle. It first checks the shared workflow dictionary for an explicitly configured "max_tokens" override. If no override exists, it queries the active LLM provider configuration via resolve_llm_settings() and resolves the context window length using get_model_context_length(). It records a debug entry to the persistent log via emit_raw() before returning the integer limit.

    Parameters: * shared (dict): The central execution state dictionary shared across pipeline workflow nodes, potentially containing runtime user overrides.

    Returns: * int: The maximum token limit of the active model context window.

    Raises: * Does not explicitly raise exceptions; errors encountered during configuration resolution propagate from llm_config.py.

    Example: 

    def resolve_max_tokens(shared):
    """Resolve max_tokens from shared store or auto-detect from the active provider."""
    max_tokens = shared.get("max_tokens")
    if max_tokens is not None:
        return max_tokens
    _, model_name, endpoint, api_key = resolve_llm_settings()
    max_tokens_val = get_model_context_length(endpoint, model_name, api_key)
    from utils.output import emit_raw

    emit_raw("DEBUG", f"resolve_max_tokens | resolved max_tokens={max_tokens_val:,}", dest="LOG")
    return max_tokens_val

    The function prioritizes values present in the pipeline's runtime dictionary, enabling user-supplied CLI flags or test harnesses to constrain model contexts deterministically. When falling back to automatic detection, it coordinates settings resolution without modifying the shared dictionary in place, maintaining pure read-only semantics. Sourcing the context ceiling directly from catalog lookups prevents hardcoded limit drift across vendor updates.

    input_token_budget()

    Visibility: Public
    Signature: def input_token_budget(max_tokens: int, thinking_level: str | None = None) -> int:

    Description: Calculates the maximum permissible prompt size (in count_tokens() units) that guarantees adequate context space for model generation and reasoning traces. For unified context architectures (Anthropic and OpenRouter), it reserves the planned output tokens derived from context_output_reserve() plus CONTEXT_MARGIN. For separated context architectures (such as Google Gemini) or unrecognized providers, it reserves 5% of the total context window clamped between 8,192 and 64,000 tokens. The function enforces an absolute minimum floor of half the total context window (max_tokens // 2).

    Parameters: * max_tokens (int): The total context window limit of the target model. * thinking_level (str | None, optional): The reasoning effort intensity (e.g., "low", "medium", "high") applied to the request. Defaults to None.

    Returns: * int: The maximum token count available for the input prompt payload.

    Raises: * Does not raise exceptions.

    Example: 

    def input_token_budget(max_tokens: int, thinking_level: str | None = None) -> int:
    """Largest prompt size (in count_tokens() units) that still leaves room for the response."""
    planned = context_output_reserve(thinking_level)
    if planned is not None:
        reserve = planned + CONTEXT_MARGIN
    else:
        reserve = min(max(int(max_tokens * 0.05), MIN_OUTPUT_RESERVE), MAX_OUTPUT_RESERVE)
    return max(max_tokens - reserve, max_tokens // 2)

    The algorithm dynamically accounts for vendor-specific architectural differences in token management. Anthropic Claude and OpenRouter models share a single memory pool across input prompt, chain-of-thought tokens, and emitted text, necessitating an explicit reservation that accommodates thinking depth. In contrast, Google Gemini models isolate input ceilings from output limits, requiring only the static margin. Clamping the fallback reserve between MIN_OUTPUT_RESERVE (8,192 tokens) and MAX_OUTPUT_RESERVE (64,000 tokens) protects large-context models from excessively large reserves while preserving room on smaller models.

    count_tokens_raw()

    Visibility: Public
    Signature: def count_tokens_raw(text: str) -> int:

    Description: Computes the baseline token count of a given string using tiktoken's cl100k_base BPE encoding. To prevent parsing failures on source code payloads containing special substrings, it explicitly sets disallowed_special=(). If tiktoken is unavailable or fails to initialize, the function falls back to a standard integer division heuristic (len(text) // 4).

    Parameters: * text (str): The raw text or source code payload to evaluate.

    Returns: * int: The raw estimated token count without provider-specific ratio adjustments.

    Raises: * Does not raise exceptions; all internal initialization and encoding errors fallback to character heuristics.

    Example: 

    def count_tokens_raw(text: str) -> int:
    """Count tokens with tiktoken (cl100k_base), with fallback to chars/4. No model calibration."""
    if not text:
        return 0
    enc = _get_encoding()
    if enc:
        return len(enc.encode(text, disallowed_special=()))
    return len(text) // 4

    This function forms the uncalibrated token counting baseline for the application. Setting disallowed_special=() is critical when processing code repositories, as identifiers such as <|endoftext|> or custom prompt markers would otherwise trigger an immediate DisallowedSpecialToken exception from tiktoken. Returning 0 for falsy or empty strings prevents downstream calculations from executing redundant encoding routines.

    count_tokens()

    Visibility: Public
    Signature: def count_tokens(text: str) -> int:

    Description: Estimates the token footprint for a string tailored to the active model family. It first calculates the raw BPE token count using count_tokens_raw() and then scales the result by the ratio retrieved from llm_config.get_token_ratio(). The ratio is resolved once and cached in the module singleton _token_ratio.

    Parameters: * text (str): The text or prompt content to measure.

    Returns: * int: The calibrated token estimate reflecting the active model's tokenization density.

    Raises: * Does not raise exceptions.

    Example: 

    def count_tokens(text: str) -> int:
    """Estimate tokens for the active model: tiktoken count x llm_config.get_token_ratio() (per model family)."""
    global _token_ratio
    raw = count_tokens_raw(text)
    if not raw:
        return 0
    if _token_ratio is None:
        _token_ratio = get_token_ratio()
    return int(raw * _token_ratio) if _token_ratio != 1.0 else raw

    Because different model families employ distinct token vocabularies (e.g., Anthropic's Claude tokenizer yields different token densities than OpenAI's cl100k_base on dense programming languages), direct raw counts can underestimate prompt size. By caching _token_ratio as a module singleton, this function avoids repeated configuration parsing across the thousands of token counting passes executed during codebase indexing.

    log_token_estimation()

    Visibility: Public
    Signature: def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:

    Description: Computes prompt capacity metrics, formats sub-component usage breakdowns, and dispatches telemetry to both the interactive terminal and structured log files.

    Parameters: * node_name (str): The identifier of the executing pipeline graph node (e.g., "draft_chapters", "map_abstractions"). * prompt_content (str): The assembled prompt string to measure. * max_tokens (int): The maximum context window ceiling used to calculate capacity percentage. * token_usage (dict | None, optional): An optional dictionary mapping prompt sub-component labels to their respective token counts. Defaults to None.

    Returns: * None

    Raises: * Does not raise exceptions; handles division-by-zero defensively if max_tokens or token_count is zero.

    Phase 1: Capacity Calculation

        token_count = count_tokens(prompt_content)
    percentage = (token_count / max_tokens) * 100 if max_tokens else 0
    The first phase evaluates the calibrated token count of the prompt payload using count_tokens(). It then computes the percentage of total model capacity consumed by the prompt, defensively guarding against division by zero if max_tokens is passed as 0.

    Phase 2: Usage Breakdown Formatting

        # Build token usage breakdown suffix for stdout display
    suffix = ""
    usage_log_str = ""
    if token_usage:
        max_label_len = max(len(label) for label in token_usage)
        lines = []
        log_parts = []
        for label, value in token_usage.items():
            pct = (value / token_count * 100) if token_count else 0
            padded_label = label.ljust(max_label_len)
            lines.append(f"\t{padded_label} : {value:,} ({pct:.0f}%)")
            log_parts.append(f"{label}={value:,} ({pct:.0f}%)")
        suffix = "\n" + "\n".join(lines)
        usage_log_str = " | " + " | ".join(log_parts)
    When a token_usage mapping is provided, the function aligns labels using ljust() based on the longest key length. For each component, it computes the fraction of total prompt tokens consumed and builds two distinct string representations: a multi-line, tab-indented suffix for human-readable terminal rendering, and a compact, pipe-delimited segment string for flat log file persistence.

    Phase 3: Telemetry Dispatch

        # Console output via emit (styled by CSV LEVEL=WARNING → yellow)
    emit(
        "TOKEN_ANALYTICS",
        suffix=suffix,
        node_name=node_name,
        token_count=f"{token_count:,}",
        max_tokens=f"{max_tokens:,}",
        percentage=f"{percentage:.1f}",
    )

    # File log stays single-line for parseability (structured, not translatable)
    logger.info(f"NODE EXEC | node={node_name} | prompt_tokens={token_count:,} / {max_tokens:,} ({percentage:.1f}% capacity){usage_log_str}")
    The final phase emits telemetry across two segregated channels. It calls emit() using the "TOKEN_ANALYTICS" event key to display formatted output to the terminal, and writes a single-line structured record containing prompt tokens, context limits, capacity percentage, and sub-breakdowns to logger.info().

    Internal Helpers

    _get_encoding()

    Visibility: Private
    Signature: def _get_encoding() -> tiktoken.Encoding | None:

    Description: Lazily loads and returns the singleton tiktoken encoding instance for cl100k_base. If the encoding has not yet been initialized, it attempts retrieval inside an exception guard. If initialization fails due to missing byte-pair encoding data files or environment constraints, _encoding is set to None and cached to bypass repeated import overhead on subsequent invocations.

    Parameters: * None

    Returns: * tiktoken.Encoding | None: The initialized cl100k_base tokenizer instance, or None if initialization failed.

    Raises: * Does not raise exceptions; all errors during encoding acquisition are trapped and handled.

    Example: 

    def _get_encoding():
    global _encoding
    if _encoding is None:
        try:
            _encoding = tiktoken.get_encoding("cl100k_base")
        except Exception:
            _encoding = None
    return _encoding

    Lazy instantiation eliminates startup latency during pipeline bootstrap when token counting may not be immediately required. Catching generic Exception ensures that environments lacking internet access or local cache access for tiktoken BPE files fail gracefully to heuristic estimation rather than terminating the pipeline.

    Data Structures

    Module Singletons and Limits

    The module defines shared state variables and reserve boundaries governing context allocations:

    Identifier Type Scope Description
    logger logging.Logger Module Dedicated logger retrieved via logging.getLogger("llm_logger").
    MIN_OUTPUT_RESERVE int Public Constant Lower bound on fallback output reservations, set to 8_192 tokens.
    MAX_OUTPUT_RESERVE int Public Constant Upper bound on fallback output reservations, set to 64_000 tokens.
    _encoding tiktoken.Encoding \| None Private State Cached singleton holding the active cl100k_base encoding object.
    _token_ratio float \| None Private State Cached scaling multiplier mapping raw tiktoken counts to target model counts.

    token_usage Breakdown Mapping

    Functions such as log_token_estimation() accept a structured mapping representing component-level token distributions within an assembled prompt payload.

    Key Type Description Example
    "<Component Label>" int Token count consumed by an individual prompt segment (e.g., AST tree, system instruction, code content). {"System Prompt": 1200, "Code Context": 18450}

    TOKEN_ANALYTICS Payload Schema

    When dispatching telemetry to the presentation subsystem via utils.output.emit(), the function constructs a dictionary of string-formatted arguments:

    Field Name Type Description Sample Value
    suffix str Tab-delimited multi-line string containing indented usage component percentages. "\n\tCode Context : 18,450 (94%)"
    node_name str Name of the executing graph node emitting the telemetry. "draft_chapters"
    token_count str Formatted comma-separated integer string of estimated prompt tokens. "19,650"
    max_tokens str Formatted comma-separated integer string of the model context limit. "200,000"
    percentage str Single-decimal formatted percentage of context window consumption. "9.8"

    Structured Log Record Format

    File-backed audit logs written to logger.info() conform to a standardized, single-line format:

    NODE EXEC | node=<node_name> | prompt_tokens=<count> / <limit> (<percentage>% capacity)[ | <label>=<count> (<pct>%) ...]

    Example output: 

    NODE EXEC | node=identify_abstractions | prompt_tokens=14,250 / 128,000 (11.1% capacity) | System Prompt=850 (6%) | File Tree=13,400 (94%)

    Error Handling

    The module implements defensive design patterns to guarantee that token sizing and logging errors never crash upstream synthesis nodes:

    • Tokenizer Initialization Protection: In _get_encoding(), any runtime failure (such as network unavailability or missing BPE assets) is caught via except Exception:. The module sets _encoding = None and silently falls back to character division heuristic estimation (len(text) // 4).
    • Special Token Escaping: count_tokens_raw() invokes enc.encode(text, disallowed_special=()), preventing unescaped control tokens in ingested source files (e.g., <|endoftext|>, <|fim_prefix|>) from triggering runtime tokenization exceptions.
    • Division-by-Zero Guards: log_token_estimation() guards all percentage calculations with conditional fallbacks (... if max_tokens else 0 and ... if token_count else 0), preventing ZeroDivisionError when measuring empty strings or uninitialized model contexts.
    • Context Reservation Floor Bounds: input_token_budget() enforces max(max_tokens - reserve, max_tokens // 2). If output reservations and safety margins exceed the total context window, the prompt budget is guaranteed at least 50% of the model ceiling, preventing negative budget calculations.
