    token_utils.py

    Source: utils/token_utils.py

    Following the prompt construction and template deserialization workflows established in prompts.py, token_utils.py governs the volumetric profiling and context limit enforcement layer of the Codebase-Knowledge-Builder architecture. Once prompts are synthesized, the system must verify that total prompt and context token counts respect upstream Large Language Model (LLM) window limits prior to dispatching HTTP or SDK inference requests in call_llm.py.

    Technical Overview

    The token_utils.py module provides unified token estimation, provider context resolution, and real-time capacity telemetry. Large-scale codebase analysis tasks—such as AST ingestion, hierarchical directory mapping, and multi-file synthesis—frequently risk overflowing model context limits or exhausting API tier budgets. This module mitigates context exhaustion by calculating prompt sizes using the standard Byte Pair Encoding (BPE) algorithm, determining runtime context limits dynamically, and emitting execution telemetry before inference calls are initiated.

    Architecturally, the module employs a singleton-backed BPE tokenizer initialized with the cl100k_base vocabulary via the tiktoken library. To guard against execution halts in resource-constrained, offline, or embedded environments where C-extensions or network-loaded BPE dictionaries fail to initialize, token_utils.py implements a graceful heuristic fallback calculating $\lfloor \text{characters} / 4 \rfloor$. For context ceiling detection, the module queries the execution pipeline's shared state or delegator logic in llm_config.py to inspect model identifiers and base endpoints.

    The module interfaces directly with output.py to log structured execution telemetry. When nodes throughout flow.py and nodes.py evaluate candidate prompts, token_utils.py provides formatted diagnostic breakdowns across stdout and persistent file logs. These breakdowns track individual components—such as system instructions, file contents, and reasoning traces—against total token ceilings, allowing developers to inspect context saturation across pipeline runs.

    Public API

    create_token_counter()

    Visibility: Public
    Signature: def create_token_counter() -> Callable[[str], int]:

    Description: Constructs and returns a standalone, reusable token-counting closure. The closure attempts to initialize the tiktoken encoder using the "cl100k_base" encoding schema. If initialization succeeds, it returns an anonymous function that accepts a string and returns the integer count of BPE tokens, disabling special token parsing to prevent delimiter injection exceptions. If initialization raises an exception (e.g., missing dependencies, uncompiled C-extensions, or filesystem permissions issues accessing local token caches), it issues a diagnostic warning through emit_raw() and returns an alternative lambda expression that calculates token volume using the standard character-to-token heuristic (len(text) // 4).

    Parameters: * None.

    Returns: * Callable[[str], int]: A unary function mapping an arbitrary input string to an estimated or exact token count integer.

    Raises: * No exceptions are propagated. Any exception encountered during tiktoken.get_encoding() is intercepted internally.

    Example: 

    # Extracted from utils/token_utils.py
def create_token_counter():
    """Create a token counting function using tiktoken with char-count fallback."""
    try:
        enc = tiktoken.get_encoding("cl100k_base")
        return lambda text: len(enc.encode(text, disallowed_special=()))
    except Exception:
        from utils.output import emit_raw

        emit_raw("WARNING", "Tiktoken initialization failed, falling back to char count / 4", dest="LOG")
        return lambda text: len(text) // 4

    The factory pattern implemented by create_token_counter() allows callers to obtain an isolated token counter instance without maintaining direct coupling to the module-level encoding singleton. When the tiktoken engine fails, it routes warning output directly to the logging channel (dest="LOG") using a scoped lazy import of emit_raw, preventing circular dependency initialization issues with utils.output. The resulting closure safely neutralizes special token syntax by passing disallowed_special=(), ensuring that untrusted codebase inputs containing strings like <|endoftext|> do not trigger tokenizer exceptions.

    resolve_max_tokens()

    Visibility: Public
    Signature: def resolve_max_tokens(shared: dict) -> int:

    Description: Determines the operational token capacity limit for downstream LLM prompts by inspecting the shared state store or resolving provider context limits from environment configurations.

    Phase 1: Shared Store Inspection

    def resolve_max_tokens(shared):
    """Resolve max_tokens from shared store or auto-detect from provider env vars."""
    max_tokens = shared.get("max_tokens")
    if max_tokens is not None:
        return max_tokens
    The function queries the provided shared dictionary for a pre-configured "max_tokens" entry. If a caller or upstream node has explicitly set this value, the function bypasses environment checks and immediately returns the cached integer.

    Phase 2: Provider Environment Resolution

        provider = os.environ.get("LLM_PROVIDER")
    if provider == "GEMINI" or not provider:
        endpoint = "https://generativelanguage.googleapis.com"
        model_name = os.getenv("GEMINI_MODEL", "gemini-3.7-flash")
        api_key = os.getenv("GEMINI_API_KEY", "")
    else:
        endpoint = os.environ.get(f"{provider}_BASE_URL", "")
        model_name = os.environ.get(f"{provider}_MODEL", "")
        api_key = os.environ.get(f"{provider}_API_KEY", "")
    If no limit is present in the shared dictionary, the function determines the active provider via LLM_PROVIDER. When configured for Google Gemini (or if the variable is unset), it defaults to Google AI Studio endpoints and the standard gemini-3.7-flash model. For alternative providers (e.g., OpenRouter, Ollama, custom OpenAI-compatible endpoints), it dynamically queries namespaced environment variables ({PROVIDER}_BASE_URL, {PROVIDER}_MODEL, and {PROVIDER}_API_KEY).

    Phase 3: Dynamic Model Context Lookup and Diagnostic Telemetry

        max_tokens_val = get_model_context_length(endpoint, model_name, api_key)
    from utils.output import emit_raw

    emit_raw("DEBUG", f"resolve_max_tokens | resolved max_tokens={max_tokens_val:,}", dest="LOG")
    return max_tokens_val
    The extracted connection parameters are dispatched to get_model_context_length() from llm_config.py, which returns the token context limit via static tables, dynamic OpenRouter catalog lookups, or fallback defaults. The resolved capacity integer is logged to the debug sink via emit_raw(), and the final value is returned to the caller.

    Parameters: * shared (dict): The global workflow execution context dictionary that may contain a pre-computed "max_tokens" integer.

    Returns: * int: The maximum token ceiling allocated for the active model context window.

    Raises: * No exceptions are raised directly. Potential I/O or network failures within get_model_context_length are handled gracefully upstream in utils.llm_config.

    Example: 

    # Implementation call site within utils/token_utils.py
max_tokens_val = get_model_context_length(endpoint, model_name, api_key)
from utils.output import emit_raw

emit_raw("DEBUG", f"resolve_max_tokens | resolved max_tokens={max_tokens_val:,}", dest="LOG")
return max_tokens_val

    count_tokens()

    Visibility: Public
    Signature: def count_tokens(text: str) -> int:

    Description: Calculates the total token count of a given text string using the cached _encoding singleton. If the input string is empty or evaluates to a falsy value, the function immediately returns 0. When the tiktoken encoding singleton is initialized, it executes BPE tokenization with disallowed_special=(), allowing literal evaluation of control strings without raising ValueError. If the tokenizer singleton cannot be loaded, it falls back to estimating the token count as one-fourth of the total character length (len(text) // 4).

    Parameters: * text (str): The raw text payload (e.g., prompt instruction, formatted directory tree, or source code chunk) to evaluate.

    Returns: * int: The estimated or exact token count.

    Raises: * No exceptions are propagated out of this function.

    Example: 

    # Extracted from utils/token_utils.py
def count_tokens(text: str) -> int:
    """Count tokens using tiktoken, with fallback to chars/4."""
    if not text:
        return 0
    enc = _get_encoding()
    if enc:
        return len(enc.encode(text, disallowed_special=()))
    return len(text) // 4

    This function serves as the primary counting utility across the entire documentation framework, invoked repeatedly by log_token_estimation(), chunking pipelines, and inference gateways. By centralizing the empty-string boundary check, it short-circuits empty prompt buffers before invoking underlying C-extensions. Setting disallowed_special=() ensures raw source code containing internal LLM instruction markers (such as <|fim_prefix|>) does not trigger parsing exceptions during tokenization.

    log_token_estimation()

    Visibility: Public
    Signature: def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:

    Description: Profiles the token volume of a prompt string against a node's capacity ceiling, formats granular breakdown statistics if provided, and emits telemetry to both the interactive console and persistent log files.

    Phase 1: Token Profiling and Capacity Calculation

    def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:
    token_count = count_tokens(prompt_content)
    percentage = (token_count / max_tokens) * 100 if max_tokens else 0
    The function evaluates prompt_content using count_tokens(). It guards against zero-division errors when evaluating percentage by validating that max_tokens is greater than zero, expressing consumption as a percentage of overall window capacity.

    Phase 2: Granular Usage Breakdown Formatting

        # Build token usage breakdown suffix for stdout display
    suffix = ""
    usage_log_str = ""
    if token_usage:
        max_label_len = max(len(label) for label in token_usage)
        lines = []
        log_parts = []
        for label, value in token_usage.items():
            pct = (value / token_count * 100) if token_count else 0
            padded_label = label.ljust(max_label_len)
            lines.append(f"\t{padded_label} : {value:,} ({pct:.0f}%)")
            log_parts.append(f"{label}={value:,} ({pct:.0f}%)")
        suffix = "\n" + "\n".join(lines)
        usage_log_str = " | " + " | ".join(log_parts)
    When callers provide a token_usage dictionary, the function formats the data into two representations: 1. An aligned, tab-indented multi-line breakdown string (suffix) for interactive terminal display. 2. A compact, pipe-delimited single-line summary (usage_log_str) for persistent log files.

    Labels are dynamically padded using ljust() based on the longest key, and percentage calculations guard against division by zero if token_count is zero.

    Phase 3: Dual-Channel Telemetry Dispatch

        # Console output via emit (styled by CSV LEVEL=WARNING → yellow)
    emit(
        "TOKEN_ANALYTICS",
        suffix=suffix,
        node_name=node_name,
        token_count=f"{token_count:,}",
        max_tokens=f"{max_tokens:,}",
        percentage=f"{percentage:.1f}",
    )

    # File log stays single-line for parseability (structured, not translatable)
    logger.info(f"NODE EXEC | node={node_name} | prompt_tokens={token_count:,} / {max_tokens:,} ({percentage:.1f}% capacity){usage_log_str}")
    Telemetry is dispatched across two distinct channels: 1. Terminal output via emit() with key "TOKEN_ANALYTICS", routing formatted counts, total capacity, and percentage values through output.py. 2. Structured output via the shared logger (llm_logger), recording execution metrics in a single line to ensure log files remain easy to parse.

    Parameters: * node_name (str): The identifier of the executing pipeline stage (e.g., "ContextRouter", "MapAbstractions"). * prompt_content (str): The serialized prompt string dispatched to the LLM. * max_tokens (int): The maximum context window ceiling resolved for the current model. * token_usage (dict | None, optional): A mapping of sub-component names to token count integers, enabling granular prompt usage breakdowns. Defaults to None.

    Returns: * None.

    Raises: * No exceptions are raised directly.

    Example: 

    # Real usage from log_token_estimation in utils/token_utils.py
emit(
    "TOKEN_ANALYTICS",
    suffix=suffix,
    node_name=node_name,
    token_count=f"{token_count:,}",
    max_tokens=f"{max_tokens:,}",
    percentage=f"{percentage:.1f}",
)

# File log stays single-line for parseability (structured, not translatable)

    Internal Helpers

    _get_encoding()

    Visibility: Private / Internal
    Signature: def _get_encoding() -> tiktoken.Encoding | None:

    Description: Manages the lazy instantiation of the module-level _encoding singleton. Upon its initial invocation, the function attempts to retrieve the "cl100k_base" encoding specification from the tiktoken library. If retrieval fails due to environment or missing dependency constraints, it caches None into _encoding. Subsequent calls return the cached state directly, eliminating the overhead of repeated dictionary initialization or repeated exception handling.

    Parameters: * None.

    Returns: * tiktoken.Encoding | None: The loaded tiktoken BPE encoding object, or None if initialization failed.

    Raises: * Intercepts all standard Exception instances during initialization, preventing failures from bubbling up to callers.

    Example: 

    # Extracted from utils/token_utils.py
_encoding = None


def _get_encoding():
    global _encoding
    if _encoding is None:
        try:
            _encoding = tiktoken.get_encoding("cl100k_base")
        except Exception:
            _encoding = None
    return _encoding

    The singleton caching mechanism in _get_encoding() optimizes performance across the documentation workflow. Codebase ingestion frequently evaluates thousands of individual code snippets, AST chunks, and prompt templates. By memoizing the BPE encoding instance in the module-level _encoding variable, the application avoids the CPU overhead of re-instantiating the tokenizer vocabulary on every call.

    Error Handling

    The token_utils.py module applies defensive programming practices to ensure token quantification and diagnostic logging never halt workflow execution:

    1. Graceful Tokenizer Fallback: In constrained runtime environments (such as Docker containers without network access or pre-built wheels for tiktoken), the module intercepts exceptions during encoding initialization. In both create_token_counter() and _get_encoding(), failures revert to a character-based heuristic: $$\text{Estimated Tokens} = \left\lfloor \frac{\text{len}(\text{text})}{4} \right\rfloor$$ This fallback ensures prompt chunking and scheduling continue uninterrupted, even if tokenizer dependencies are missing.

    2. Special Token Sanitization: The BPE encoder is called with disallowed_special=(). By default, tiktoken.encode() raises a ValueError when encountering special control sequences like <|endoftext|>. Ingested codebases frequently contain these literal strings in comments, tests, or documentation. Disabling special token restrictions ensures raw source files are tokenized without exceptions.

    3. Arithmetic Zero-Division Defense: In log_token_estimation(), relative percentage computations are protected against zero denominators: 

      percentage = (token_count / max_tokens) * 100 if max_tokens else 0
pct = (value / token_count * 100) if token_count else 0
      This prevents crashes when evaluating empty files (token_count = 0) or models with uninitialized context limits (max_tokens = 0).
