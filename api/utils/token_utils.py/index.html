    token_utils.py

    Source: utils/token_utils.py

    Following the prompt synthesis and static site generation infrastructure defined in prompts.py, token_utils.py provides the token estimation, telemetry, and context-window capacity validation utilities for the Codebase-Knowledge-Builder system. It computes prompt token weights across the repository ingestion and analysis pipeline, enabling pre-flight validation against provider context limits and formatting telemetry metrics for console and log output.

    Technical Overview

    The token_utils.py module delivers a lightweight, fault-tolerant token counting and logging framework tailored for large-scale source code processing. When ingesting large codebases, orchestrators must measure payload token volumes before dispatching them to downstream inference APIs to prevent context window overflow, unexpected rate limiting, and request truncation.

    Key Functional Responsibilities

    1. Lazy-Loaded BPE Tokenizer Management: Manages a cached singleton instance of the cl100k_base Byte Pair Encoding (BPE) tokenizer via tiktoken. By deferring initialization until the first counting request, the module eliminates startup latency and avoids memory overhead during non-LLM operations.
    2. Resilient Token Estimation: Implements robust token counting with transparent fallback mechanisms. If the native tokenizer cannot be initialized (for example, in environments lacking pre-compiled binary wheels or network access to download vocabulary files), it gracefully degrades to a standard 4-characters-per-token heuristic (len(text) // 4).
    3. Special Token Sanitization: Explicitly disables special token parsing rules (disallowed_special=()) during encoding. This ensures that raw source code containing literal control tokens (such as <|endoftext|>, <|fim_prefix|>, or <|im_start|>) is counted as ordinary text rather than raising tokenizer runtime exceptions.
    4. Structured Pre-Flight Telemetry: Calculates node-level context consumption against maximum configured window limits (max_tokens), formats granular sub-component token usage breakdowns, and dispatches structured telemetry to both interactive console sinks via output.py and persistent execution logs.

    Module-Level Functions

    _get_encoding()

    Visibility: Private (Internal Helper)
    Signature: def _get_encoding() -> tiktoken.Encoding | None

    Description:
    Initializes and returns the module-level singleton _encoding using tiktoken's cl100k_base vocabulary. If the encoding has already been instantiated, it returns the cached object immediately. If tiktoken raises an exception during vocabulary retrieval (such as network access failure, missing data files, or environment constraints), the function catches the exception, ensures _encoding is set to None, and returns None to trigger downstream heuristic fallbacks without terminating execution.

    Parameters:
    * None.

    Returns:
    * tiktoken.Encoding | None: The initialized cl100k_base tokenizer instance if available; otherwise, None.

    Raises:
    * No exceptions are raised. All internal exceptions during tiktoken.get_encoding() execution are captured defensively.

    Example: 

    def _get_encoding():
    global _encoding
    if _encoding is None:
        try:
            _encoding = tiktoken.get_encoding("cl100k_base")
        except Exception:
            _encoding = None
    return _encoding

    _get_encoding() guarantees that tokenizer initialization happens on demand rather than at import time. This lazy loading avoids blocking application startup during CLI initialization in main.py. The global singleton pattern prevents redundant disk and memory operations when processing hundreds of source files across iterative workflow nodes.

    count_tokens()

    Visibility: Public
    Signature: def count_tokens(text: str) -> int

    Description:
    Calculates the total token count of a given text string. If the input string is empty or evaluates to a falsy value, it returns 0 immediately. When an active tiktoken encoding instance is available from _get_encoding(), the string is encoded using enc.encode(text, disallowed_special=()). Setting disallowed_special=() disables the default behavior of treating special tokens as syntax errors, allowing raw source code containing strings like <|endoftext|> or <|fim_prefix|> to be safely tokenized as standard text. If tokenizer initialization fails or is unavailable, the function falls back to integer division of string length by four (len(text) // 4).

    Parameters:
    * text (str): The raw text or source code payload to be tokenized.

    Returns:
    * int: Total estimated token count.

    Raises:
    * No exceptions are raised.

    Example: 

    def count_tokens(text: str) -> int:
    """Count tokens using tiktoken, with fallback to chars/4."""
    if not text:
        return 0
    enc = _get_encoding()
    if enc:
        return len(enc.encode(text, disallowed_special=()))
    return len(text) // 4

    count_tokens() serves as the primary counting interface consumed throughout the pipeline, notably within call_llm.py prior to dispatching prompts to remote inference endpoints. The disallowed_special=() argument is a critical design requirement for codebase analysis: without it, any repository file containing LLM prompt delimiters or tokenizer control sequences would raise a DisallowedSpecialTokenError and crash the extraction workflow. The fallback heuristic of 4 characters per token aligns with standard natural language and programming language statistical averages.

    log_token_estimation()

    Visibility: Public
    Signature: def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None

    Description:
    Calculates, formats, and logs token consumption metrics for a specific workflow node before LLM execution. It computes total tokens using count_tokens(prompt_content) and derives the percentage of context capacity utilized ((token_count / max_tokens) * 100). If a granular token_usage dictionary is provided (mapping section labels to individual token counts), the function dynamically calculates column widths, aligns label strings using .ljust(), and appends formatted percentage breakdowns to both console output and log entries. Telemetry is emitted via output.emit() using the "TOKEN_ANALYTICS" template and recorded to the single-line structured logger.

    Parameters:
    * node_name (str): Identifier of the workflow node executing the request (e.g., "system_architecture", "extract_modules"). * prompt_content (str): Complete formatted prompt payload about to be transmitted to the LLM. * max_tokens (int): Maximum context window size supported by the active model configuration. * token_usage (dict | None, optional): Key-value mapping of sub-component names to their respective token counts (e.g., {"AST Context": 1200, "Source Code": 4500}). Defaults to None.

    Returns:
    * None

    Raises:
    * No exceptions are raised.

    Example: 

    def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:
    token_count = count_tokens(prompt_content)
    percentage = (token_count / max_tokens) * 100 if max_tokens else 0

    # Build token usage breakdown suffix for stdout display
    suffix = ""
    usage_log_str = ""
    if token_usage:
        max_label_len = max(len(label) for label in token_usage)
        lines = []
        log_parts = []
        for label, value in token_usage.items():
            pct = (value / token_count * 100) if token_count else 0
            padded_label = label.ljust(max_label_len)
            lines.append(f"\t{padded_label} : {value:,} ({pct:.0f}%)")
            log_parts.append(f"{label}={value:,} ({pct:.0f}%)")
        suffix = "\n" + "\n".join(lines)
        usage_log_str = " | " + " | ".join(log_parts)

    # Console output via emit (styled by CSV LEVEL=WARNING → yellow)
    emit(
        "TOKEN_ANALYTICS",
        suffix=suffix,
        node_name=node_name,
        token_count=f"{token_count:,}",
        max_tokens=f"{max_tokens:,}",
        percentage=f"{percentage:.1f}",
    )

    # File log stays single-line for parseability (structured, not translatable)
    logger.info(f"NODE EXEC | node={node_name} | prompt_tokens={token_count:,} / {max_tokens:,} ({percentage:.1f}% capacity){usage_log_str}")

    log_token_estimation() provides unified observability across all generation stages. By separating the multi-line human-readable breakdown sent to standard output from the single-line delimited format written to logger.info, it satisfies both real-time monitoring and post-execution automated parsing requirements. The console output leverages the TOKEN_ANALYTICS format defined in utils/strings.csv (styled yellow under WARNING level), providing visual feedback when large context payloads approach model boundaries.

    Detailed Telemetry & Output Formatting

    The telemetry logic in log_token_estimation() coordinates dual output sinks with distinct structural formats:

    +-----------------------------------------------------------------------------------------+
| Interactive Console Output (via emit -> STDOUT)                                         |
+-----------------------------------------------------------------------------------------+
| [WARN] [TOKEN_ANALYTICS] Node: module_overview | 45,210 / 128,000 (35.3% capacity)      |
|        File Summaries : 30,140 (67%)                                                    |
|        Dependencies   : 10,050 (22%)                                                    |
|        Prompt Schema  : 5,020 (11%)                                                     |
+-----------------------------------------------------------------------------------------+
                                             |
                                             v
+-----------------------------------------------------------------------------------------+
| Persistent Log File Output (via logger.info -> llm_cache/run_*.log)                     |
+-----------------------------------------------------------------------------------------+
| NODE EXEC | node=module_overview | prompt_tokens=45,210 / 128,000 (35.3% capacity) |    |
| File Summaries=30,140 (67%) | Dependencies=10,050 (22%) | Prompt Schema=5,020 (11%)     |
+-----------------------------------------------------------------------------------------+

    Breakdown Construction Rules

    1. Label Width Dynamic Padding: Calculates max_label_len = max(len(label) for label in token_usage) across all keys in token_usage and applies .ljust(max_label_len) to align colons across lines.
    2. Sub-Item Percentage Calculation: Computes pct = (value / token_count * 100) if token_count else 0 for each component to display its relative weight within the overall prompt payload.
    3. Number Formatting: Applies thousand separators ({value:,}) to both absolute counts and capacity limits for readability.
    4. Log Line Linearization: Joins structured sub-components using pipe delimiters (" | "), preserving single-line grep-friendly integrity in log files.
