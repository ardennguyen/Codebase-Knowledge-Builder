    token_utils.py

    Source: utils/token_utils.py

    Following the prompt construction and site configuration routines defined in prompts.py, the system must measure, budget, and log token consumption across prompt payloads before dispatching inference requests or persisting artifacts. The utils/token_utils.py module provides the centralized token estimation, context window budgeting, and telemetry logging layer for the Codebase-Knowledge-Builder system.

    Technical Overview

    The primary responsibility of utils/token_utils.py is to calculate prompt token volume accurately while ensuring zero runtime interruption if external tokenizer components fail. It acts as an operational bridge between workflow orchestration nodes in nodes.py, the LLM inference gateway in call_llm.py, and the terminal/log dispatch system in output.py. The module wraps OpenAI's tiktoken library with lazy-loaded singleton initialization and a fallback heuristic calculation based on character count.

    Beyond scalar token counting, the module provides multi-channel telemetry through log_token_estimation(). It computes the prompt's percentage utilization against the target model's configured context window ceiling, formats granular per-component breakdowns (e.g., system instructions, repository file slices, chapter summaries), and simultaneously dispatches formatted terminal notifications via emit() and structured, single-line log entries to the llm_logger file stream.

    Public API

    count_tokens()

    Visibility: Public
    Signature: def count_tokens(text: str) -> int:

    Description:
    Calculates the exact or estimated token count for an arbitrary input text string. It queries the lazy-loaded cl100k_base BPE (Byte Pair Encoding) tokenizer from tiktoken. To prevent runtime exceptions when processing arbitrary repository source code containing raw control tokens (such as <|endoftext|> or special syntax markers), the tokenizer is explicitly instructed to bypass special token parsing by setting disallowed_special=(). If the encoding object cannot be initialized (e.g., missing tokenizer files or environment limitations), the function falls back to a deterministic 4-character-per-token heuristic (len(text) // 4).

    Parameters: * text (str): The raw text string, source code chunk, or assembled prompt payload to measure.

    Returns: * int: Total calculated or estimated tokens. Returns 0 if the input text is empty or evaluated to false.

    Raises: * No exceptions are propagated. All tokenizer initialization and encoding errors are caught or bypassed internally.

    Example: 

    def count_tokens(text: str) -> int:
    """Count tokens using tiktoken, with fallback to chars/4."""
    if not text:
        return 0
    enc = _get_encoding()
    if enc:
        return len(enc.encode(text, disallowed_special=()))
    return len(text) // 4

    The function enforces an early return of 0 when evaluated against empty strings, None, or empty buffers, preventing unnecessary tokenizer lookups. When an active tokenizer instance is available via _get_encoding(), enc.encode(text, disallowed_special=()) processes the full string safely by disabling special token restrictions that would otherwise raise a ValueError on encountering LLM delimiter syntax embedded inside target codebase files. If the encoding backend is unavailable, the integer floor division len(text) // 4 provides an approximate token estimate standard across English and Latin-character source code.

    log_token_estimation()

    Visibility: Public
    Signature: def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:

    Description:
    Orchestrates context capacity calculation, terminal formatting, and diagnostic file logging for workflow execution nodes prior to invoking model inference. It calculates the prompt's total token volume using count_tokens(), determines the percentage consumption against the model's maximum context length, and constructs an aligned visual breakdown if component-level token usage metrics are supplied. The formatted output is routed to stdout via emit("TOKEN_ANALYTICS", ...) and appended to the shared logger llm_logger as a structured, machine-parseable single-line audit record.

    Parameters: * node_name (str): The identifier of the active workflow graph node (e.g., "analyze_module", "summarize_chapter"). * prompt_content (str): The complete, serialized prompt string about to be sent to the LLM backend. * max_tokens (int): The maximum context window size configured for the target model. * token_usage (dict | None, optional): A key-value dictionary mapping sub-component labels (e.g., "System Prompt", "File Context") to their respective token counts. Defaults to None.

    Returns: * None: Dispatches metrics directly to standard output and log handlers without returning values.

    Raises: * No exceptions are propagated. Formatting and emission operations handle potential zero-division or missing dictionary entries defensively.

    Phase 1: Context Utilization and Percentage Computation

        token_count = count_tokens(prompt_content)
    percentage = (token_count / max_tokens) * 100 if max_tokens else 0
    In this phase, log_token_estimation() evaluates the overall token volume of the prompt payload by delegating to count_tokens(). It computes the percentage of the model's total context window occupied by this specific request. The calculation incorporates a ternary condition (if max_tokens else 0) to guard against division-by-zero errors in scenarios where model metadata lacks an explicit context length or when running against mock providers with unbounded limits.

    Phase 2: Breakdown Assembly and Text Alignment

        # Build token usage breakdown suffix for stdout display
    suffix = ""
    usage_log_str = ""
    if token_usage:
        max_label_len = max(len(label) for label in token_usage)
        lines = []
        log_parts = []
        for label, value in token_usage.items():
            pct = (value / token_count * 100) if token_count else 0
            padded_label = label.ljust(max_label_len)
            lines.append(f"\t{padded_label} : {value:,} ({pct:.0f}%)")
            log_parts.append(f"{label}={value:,} ({pct:.0f}%)")
        suffix = "\n" + "\n".join(lines)
        usage_log_str = " | " + " | ".join(log_parts)
    When a token_usage dictionary is provided, this phase builds two synchronized representations of the component metrics. It first calculates max_label_len across all keys to ensure clean columnar padding using str.ljust(). It iterates through each key-value pair, computing each component's individual share relative to token_count while guarding against division by zero if the prompt is empty. The multi-line formatted string suffix is assembled with leading tabs and comma-formatted integers for terminal display, while usage_log_str compiles a flattened, pipe-separated key-value sequence suitable for single-line log aggregation.

    Phase 3: Multi-Channel Dispatch and Audit Logging

        # Console output via emit (styled by CSV LEVEL=WARNING → yellow)
    emit(
        "TOKEN_ANALYTICS",
        suffix=suffix,
        node_name=node_name,
        token_count=f"{token_count:,}",
        max_tokens=f"{max_tokens:,}",
        percentage=f"{percentage:.1f}",
    )

    # File log stays single-line for parseability (structured, not translatable)
    logger.info(f"NODE EXEC | node={node_name} | prompt_tokens={token_count:,} / {max_tokens:,} ({percentage:.1f}% capacity){usage_log_str}")
    The final phase handles dual telemetry emission. It calls emit() from utils.output with the key "TOKEN_ANALYTICS", passing the pre-computed metrics and the formatted breakdown suffix as dynamic template arguments. This produces a colorized (warning/yellow) notice in the user's terminal window according to configuration rules in strings.csv. Concurrently, it invokes logger.info() on the shared llm_logger instance, writing a rigid, single-line record (NODE EXEC | node=... | prompt_tokens=...) that enables log indexers and monitoring scripts to parse execution history without handling multiline breaks.

    Internal Helpers

    _get_encoding()

    Visibility: Private / Internal Helper
    Signature: def _get_encoding() -> tiktoken.core.Encoding | None:

    Description:
    Implements a lazy-loading singleton pattern for the tiktoken BPE encoding instance. Tokenizer initialization carries a non-trivial file I/O and dictionary parsing cost; caching the instance in the global _encoding variable ensures that tiktoken.get_encoding() executes at most once across the entire lifecycle of the application. The function wraps the lookup in a broad exception handler, ensuring that missing network caches, binary incompatibilities, or missing tokenizer assets fail gracefully by setting _encoding to None.

    Parameters: * None.

    Returns: * tiktoken.core.Encoding | None: The initialized cl100k_base encoding object, or None if initialization fails.

    Raises: * Catches all exceptions (Exception) during encoding resolution and suppresses them.

    Example: 

    # Lazy-loaded tiktoken encoding (singleton)
_encoding = None


def _get_encoding():
    global _encoding
    if _encoding is None:
        try:
            _encoding = tiktoken.get_encoding("cl100k_base")
        except Exception:
            _encoding = None
    return _encoding

    The function accesses the module-scoped _encoding variable via the global keyword. If the variable is unset (None), it attempts to load the standard OpenAI cl100k_base vocabulary, which serves as a standard approximation for modern LLM tokenizers (including GPT-4, GPT-3.5-Turbo, and compatible embedding models). If an exception is encountered—such as a missing local cache or corrupted tokenizer installation—the error is suppressed, _encoding is explicitly assigned None, and downstream token counting seamlessly falls back to character-based heuristic estimation.

    Data Structures

    token_usage Breakdown Mapping

    The token_usage parameter accepted by log_token_estimation() is an optional dictionary structure that maps granular prompt segments to their respective integer token counts.

    Field / Key Type Description
    <Component Label> str A human-readable identifier for the prompt subsection (e.g., "System Prompt", "Context Chunks", "File Index", "Target File").
    <Token Count> int The measured or estimated token count corresponding to that specific subsection.

    Example Schema Structure: 

    token_usage = {
    "System Instructions": 450,
    "Repository Map": 1280,
    "Source Files": 8420,
    "Chapter History": 1100,
}

    TOKEN_ANALYTICS Dynamic Parameter Schema

    When emitting telemetry through utils.output.emit(), log_token_estimation() supplies the following template interpolation dictionary to resolve the localized "TOKEN_ANALYTICS" template from utils/strings.csv.

    Parameter Key Type Formatted Example Description
    node_name str "crawl_repo_node" Name of the active workflow graph node.
    token_count str "11,250" Total prompt token count formatted with thousands separators.
    max_tokens str "128,000" Model context capacity formatted with thousands separators.
    percentage str "8.8" Context window capacity utilization formatted to 1 decimal place.
    suffix str "\n\tSystem Prompt : 450 (4%)\n\tFiles : 10,800 (96%)" Column-padded multiline breakdown string, or empty string if omitted.

    Structured Log Record Schema

    When logging to the file-based logger logger.info(), the module writes a standardized string adhering to the following structural format:

    NODE EXEC | node={node_name} | prompt_tokens={token_count} / {max_tokens} ({percentage}% capacity)[ | {breakdown_part_1} | {breakdown_part_2} ...]

    Example Log Entries: 

    NODE EXEC | node=filter_code_files | prompt_tokens=3,421 / 128,000 (2.7% capacity)
NODE EXEC | node=analyze_code_chapter | prompt_tokens=45,210 / 200,000 (22.6% capacity) | System Prompt=1,200 (3%) | Chapter Docs=4,010 (9%) | Source Slices=40,000 (88%)

    Error Handling

    The module implements defensive error handling strategies to ensure that token telemetry never interrupts workflow execution:

    1. Tokenizer Initialization Resilience: The _get_encoding() helper encapsulates the call to tiktoken.get_encoding("cl100k_base") inside a broad try...except Exception block. If tiktoken cannot download or open its vocabulary asset, the module falls back to _encoding = None without raising an exception.
    2. Special Token Bypass: Raw source code ingested from repositories frequently contains syntax that mirrors special LLM control sequences (such as <|endoftext|>, <|im_start|>, or <|fim_prefix|>). By default, tiktoken.encode() raises a ValueError when encountering these strings. The module passes disallowed_special=() to disable this restriction, forcing tiktoken to tokenize all text as ordinary subwords.
    3. Graceful Heuristic Fallback: If _encoding is unavailable or tiktoken fails at runtime, count_tokens() computes len(text) // 4. This integer arithmetic avoids floating-point overhead and guarantees a valid non-negative integer return value.
    4. Zero-Division Safeguards: Both percentage calculation in log_token_estimation() and per-item breakdown percentage calculations (pct = (value / token_count * 100) if token_count else 0) verify denominators before performing division, preventing runtime ZeroDivisionError crashes when processing empty prompts or unbounded context limits.
