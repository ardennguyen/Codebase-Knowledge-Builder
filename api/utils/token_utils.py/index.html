    token_utils.py

    Source: utils/token_utils.py

    Technical Overview

    Following the prompt management and structured decoding mechanics documented in utils/prompts.py, the utils/token_utils.py module provides token budgeting, context window resolution, and execution telemetry for the pipeline. In Large Language Model (LLM) documentation pipelines, unbounded prompt assembly risks exceeding provider context windows, resulting in costly HTTP 400 errors, silent payload truncation, or mid-generation failures. This module establishes a unified metering and budgeting layer that operates upstream of the execution gateway documented in utils/call_llm.py.

    The component operates as a standalone utility service designed around three core functions: lazy-loaded Byte Pair Encoding (BPE) tokenization, dynamic context capacity resolution, and structured multi-channel telemetry emission. It wraps OpenAI's cl100k_base BPE tokenizer through the tiktoken library, providing a fallback mechanism that approximates token counts using character-length heuristics (len(text) // 4) when binary wheels or encoding assets fail to load. In addition to measuring strings, the module determines active model context boundaries by inspecting execution runtimes or querying external provider metadata endpoints.

    Telemetry tracking is integrated through a dual-channel reporting mechanism. When execution nodes in nodes.py construct prompts, token_utils.py measures prompt size against model thresholds and breaks down composite prompts (such as system instructions, file contents, and dependency graphs) into per-component allocations. It routes human-readable summaries to the terminal using localized string emission in utils/output.py, while appending structured single-line execution records to the shared persistent log file.

    Public API

    count_tokens()

    Visibility: Public
    Signature: def count_tokens(text: str) -> int:

    Description:
    Measures the token count of a given string using the cl100k_base BPE tokenizer. If the input text is falsy (empty string or None), it immediately returns 0 without attempting tokenization. The function resolves the encoding instance by querying the internal lazy singleton _get_encoding(). If the tokenizer is unavailable due to missing dependencies, environment constraints, or initialization failures, the function falls back to a deterministic heuristic calculation: the total string length divided by 4 using integer division (len(text) // 4). When encoding through tiktoken, it explicitly disables special token constraints (disallowed_special=()), preventing runtime crashes when source code snippets contain literal token strings such as <|endoftext|>.

    Parameters: * text (str): The raw text or prompt content to measure.

    Returns: * int: The computed or estimated token count.

    Raises: * This function does not raise exceptions. Any internal failures during encoding retrieval degrade to character-count heuristics.

    Example: 

    # Implementation extraction from utils/token_utils.py
def count_tokens(text: str) -> int:
    """Count tokens using tiktoken, with fallback to chars/4."""
    if not text:
        return 0
    enc = _get_encoding()
    if enc:
        return len(enc.encode(text, disallowed_special=()))
    return len(text) // 4

    The underlying tokenization relies on _get_encoding(), which guarantees that the BPE byte-pair encoding table is compiled once per process lifecycle. The use of disallowed_special=() is essential for source code ingestion pipelines: codebases frequently contain strings that match OpenAI special token structures, and omitting this argument causes tiktoken to raise a ValueError. The fallback len(text) // 4 provides an approximation based on the standard English heuristic of roughly 4 characters per token, maintaining pipeline continuity even in restricted runtime environments where native C extensions cannot be executed.

    create_token_counter()

    Visibility: Public
    Signature: def create_token_counter() -> Callable[[str], int]:

    Description:
    A factory function that constructs and returns an isolated token counting callable. It attempts to load the cl100k_base encoding from tiktoken. If initialization succeeds, it returns a closure that executes len(enc.encode(text, disallowed_special=())). If an exception occurs during instantiation (such as an environment missing network access for downloading tokenizer data or unsupported system architectures), it captures the exception, logs a warning message to the execution log via emit_raw(), and returns a fallback lambda calculating len(text) // 4.

    Parameters: * None.

    Returns: * Callable[[str], int]: A self-contained function accepting a string and returning its integer token count.

    Raises: * This function does not raise exceptions. All initialization errors are caught and trigger the heuristic fallback callable.

    Example: 

    # Implementation extraction from utils/token_utils.py
def create_token_counter():
    """Create a token counting function using tiktoken with char-count fallback."""
    try:
        enc = tiktoken.get_encoding("cl100k_base")
        return lambda text: len(enc.encode(text, disallowed_special=()))
    except Exception:
        from utils.output import emit_raw

        emit_raw("WARNING", "Tiktoken initialization failed, falling back to char count / 4", dest="LOG")
        return lambda text: len(text) // 4

    create_token_counter acts as a factory pattern for components that require an independent counter instance rather than relying on the module-level singleton count_tokens(). By isolating tiktoken.get_encoding() inside an explicit try-except block, it guarantees that any filesystem, network, or binary incompatibility error encountered during tokenizer setup is intercepted before pipeline execution begins. Notice that from utils.output import emit_raw is imported lazily inside the exception handler to prevent circular import chains during early interpreter bootstrapping.

    resolve_max_tokens()

    Visibility: Public
    Signature: def resolve_max_tokens(shared: dict) -> int:

    Description:
    Resolves the maximum context token limit for the currently configured LLM provider and model. The resolution operates via a cascading fallback strategy: it first inspects the pipeline's shared state dictionary for an existing max_tokens configuration. If missing, it inspects environment variables to determine the active provider (LLM_PROVIDER), normalizes API endpoint addresses, model identifiers, and credentials, and delegates to get_model_context_length() from utils/call_llm.py. Finally, it records the resolved context boundary to the system log via emit_raw().

    Phase 1: Shared Store Query

        max_tokens = shared.get("max_tokens")
    if max_tokens is not None:
        return max_tokens
    The function queries the pipeline's mutable state dictionary shared. If a prior stage (such as command-line argument parsing in main.py or workflow setup in flow.py) has explicitly configured a token ceiling, this value takes precedence and is returned immediately, bypassing external queries or environment variable lookups.

    Phase 2: Provider Environment Resolution

        provider = os.environ.get("LLM_PROVIDER")
    if provider == "GEMINI" or not provider:
        endpoint = "https://generativelanguage.googleapis.com"
        model_name = os.getenv("GEMINI_MODEL", "gemini-3.7-flash")
        api_key = os.getenv("GEMINI_API_KEY", "")
    else:
        endpoint = os.environ.get(f"{provider}_BASE_URL", "")
        model_name = os.environ.get(f"{provider}_MODEL", "")
        api_key = os.environ.get(f"{provider}_API_KEY", "")
    If the token limit is not defined in shared, the function inspects os.environ to construct provider configuration tuples. When LLM_PROVIDER is set to "GEMINI" or left unset, it defaults to the official Google Generative Language endpoint, using the default model gemini-3.7-flash and reading GEMINI_API_KEY. For custom or OpenAI-compatible backends (such as OpenRouter, DeepSeek, or Ollama), it dynamically interpolates the provider prefix into environment keys: {provider}_BASE_URL, {provider}_MODEL, and {provider}_API_KEY.

    Phase 3: Remote Context Ingestion and Telemetry Logging

        max_tokens_val = get_model_context_length(endpoint, model_name, api_key)
    from utils.output import emit_raw

    emit_raw("DEBUG", f"resolve_max_tokens | resolved max_tokens={max_tokens_val:,}", dest="LOG")
    return max_tokens_val
    Once provider credentials and endpoints are resolved, the function calls get_model_context_length(), which determines the token window limit using hardcoded provider mappings or by querying remote model metadata endpoints (e.g., OpenRouter /api/v1/models). The resolved integer boundary is then written directly to the logging channel with DEBUG severity using a lazy-imported emit_raw() dispatcher, leaving standard output uncluttered while preserving diagnostic traces on disk.

    Parameters: * shared (dict): The global workflow execution store shared across graph nodes.

    Returns: * int: The maximum token context limit available for prompt assembly.

    Raises: * This function does not raise exceptions directly; any network errors encountered during remote capability inspection in get_model_context_length() are caught within utils/call_llm.py and fall back to safe context defaults.

    Example: 

    # Calling pattern from pipeline orchestrators
context_window = resolve_max_tokens(shared_state)

    log_token_estimation()

    Visibility: Public
    Signature: def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:

    Description:
    Generates and broadcasts token analytics for an LLM prompt prior to dispatch. It measures the aggregate token count of the prompt string, computes the percentage of the model's total context window consumed, formats an optional itemized breakdown of prompt sub-components, and broadcasts the resulting diagnostics through both the user-facing console and the persistent system log.

    Phase 1: Token Measurement and Percentage Calculation

        token_count = count_tokens(prompt_content)
    percentage = (token_count / max_tokens) * 100 if max_tokens else 0
    The routine passes the complete prompt content to count_tokens(). It then calculates capacity consumption against max_tokens. To avoid runtime ZeroDivisionError exceptions when operating against uninitialized context limits, the division is guarded by a conditional ternary check (if max_tokens else 0).

    Phase 2: Component Breakdown Formatting

        # Build token usage breakdown suffix for stdout display
    suffix = ""
    usage_log_str = ""
    if token_usage:
        max_label_len = max(len(label) for label in token_usage)
        lines = []
        log_parts = []
        for label, value in token_usage.items():
            pct = (value / token_count * 100) if token_count else 0
            padded_label = label.ljust(max_label_len)
            lines.append(f"\t{padded_label} : {value:,} ({pct:.0f}%)")
            log_parts.append(f"{label}={value:,} ({pct:.0f}%)")
        suffix = "\n" + "\n".join(lines)
        usage_log_str = " | " + " | ".join(log_parts)
    When callers provide the optional token_usage dictionary mapping semantic sub-sections (e.g., "system_prompt", "repo_tree", "source_files") to their respective token counts, the function formats two separate breakdown representations: 1. suffix: A multiline, tab-indented, column-padded block designed for clean terminal alignment. 2. usage_log_str: A compact, single-line, pipe-delimited string designed for structured ingestion by log aggregators.

    Phase 3: Dual Telemetry Emission

        # Console output via emit (styled by CSV LEVEL=WARNING → yellow)
    emit(
        "TOKEN_ANALYTICS",
        suffix=suffix,
        node_name=node_name,
        token_count=f"{token_count:,}",
        max_tokens=f"{max_tokens:,}",
        percentage=f"{percentage:.1f}",
    )

    # File log stays single-line for parseability (structured, not translatable)
    logger.info(f"NODE EXEC | node={node_name} | prompt_tokens={token_count:,} / {max_tokens:,} ({percentage:.1f}% capacity){usage_log_str}")
    Output dispatch uses two distinct pathways. For terminal users, emit() formats the TOKEN_ANALYTICS template registered in utils/strings.csv, applying ANSI yellow styling (LEVEL=WARNING) to highlight token overhead and rendering the padded breakdown suffix. Simultaneously, it uses logger.info() via the shared "llm_logger" instance to append a parseable, single-line record containing the node name, token counts, capacity percentage, and itemized component parts to disk.

    Parameters: * node_name (str): The identifier of the calling pipeline execution node (e.g., "ContextRouter", "GenerateChapter"). * prompt_content (str): The complete serialized prompt string passed to the LLM. * max_tokens (int): The maximum context window capacity of the target model. * token_usage (dict | None, optional): A key-value mapping of sub-component labels (str) to individual token measurements (int). Defaults to None.

    Returns: * None

    Raises: * This function does not raise exceptions. Formatting calculations defensively guard against division by zero and handle missing dictionaries gracefully.

    Example: 

    # Calling pattern from execution nodes in nodes.py
log_token_estimation(
    node_name="ContextRouter",
    prompt_content=composed_prompt,
    max_tokens=1048576,
    token_usage={
        "system_instruction": 450,
        "directory_tree": 12800,
        "target_task": 120,
    }
)

    Internal Helpers

    _get_encoding()

    Visibility: Private / Internal
    Signature: def _get_encoding() -> tiktoken.Encoding | None:

    Description:
    Manages lazy initialization and caching for the module-level singleton _encoding. The first time tokenization is requested, the function intercepts control, checks if _encoding is uninitialized (None), and attempts to load the cl100k_base model dictionary via tiktoken.get_encoding("cl100k_base"). If loading fails for any reason (e.g., missing tokenizer data files or environment issues), it traps the exception, leaves _encoding set to None, and returns. Subsequent calls bypass initialization and return the cached state immediately.

    Parameters: * None.

    Returns: * tiktoken.Encoding | None: The initialized Tiktoken BPE encoding instance if successful, or None if initialization failed.

    Raises: * This function does not raise exceptions; all exceptions during tokenizer initialization are caught internally.

    Example: 

    # Implementation extraction from utils/token_utils.py
# Lazy-loaded tiktoken encoding (singleton)
_encoding = None


def _get_encoding():
    global _encoding
    if _encoding is None:
        try:
            _encoding = tiktoken.get_encoding("cl100k_base")
        except Exception:
            _encoding = None
    return _encoding

    _get_encoding() implements a lazy-loaded singleton pattern. Compiling BPE vocabulary maps and regex splits is an expensive operation that incurs noticeable memory and CPU initialization overhead. By deferring this until count_tokens() is first invoked, module import remains lightweight. If the runtime environment lacks internet connectivity to download vocabulary files or cannot load native compiled extensions, setting _encoding = None guarantees that subsequent calls to count_tokens() fall back to character division without repeated failed initialization attempts.

    Data Structures

    The module does not define custom classes or data models. Instead, it operates over standard Python primitives, closures, and structural dictionaries:

    ... Any Additional arbitrary pipeline context stored in the shared workflow dictionary.

    Key Type Description

    Error Handling

    The module implements defensive error handling to prevent token counting errors from interrupting documentation generation:

    1. Tokenizer Initialization Interception:
      Native BPE libraries can encounter environment-specific failures (such as missing pre-compiled wheels, incompatible architectures, or restricted environments without access to vocabulary files). Both create_token_counter() and _get_encoding() enclose tiktoken.get_encoding("cl100k_base") in try-except Exception blocks. Failures are caught and logged as warnings via emit_raw(), and the module switches to a heuristic character-count fallback (len(text) // 4).

    2. Special Token Sanitization:
      LLM tokenizers often treat strings like <|endoftext|> or <|fim_prefix|> as reserved control tokens, raising a ValueError if they appear in raw input text. Because this pipeline ingests arbitrary third-party source code, count_tokens() and create_token_counter() explicitly configure disallowed_special=(). This instructs tiktoken to treat all input strings as literal text, preventing crashes on source files that contain these sequences.

    3. Division by Zero Protection:
      In log_token_estimation(), capacity percentage calculations evaluate (token_count / max_tokens) * 100 and component breakdowns evaluate (value / token_count * 100). Both operations include explicit ternary guards (if max_tokens else 0 and if token_count else 0), preventing ZeroDivisionError when measuring empty strings or operating against uninitialized context ceilings.

    4. Circular Import Mitigation:
      To prevent circular import issues when loaded alongside utils/output.py and utils/call_llm.py, the module defers the import of emit_raw inside create_token_counter() and resolve_max_tokens(). It imports emit_raw locally within the function body only when warning or debug paths are executed.
