    token_utils.py

    Source: utils/token_utils.py

    Technical Overview

    Following the deterministic prompt synthesis and static infrastructure compilation defined in prompts.py, the pipeline requires rigorous accounting of prompt volume prior to dispatching inference requests through call_llm.py. The token_utils.py module serves as the centralized token counting, context budgeting, and telemetry logging utility within the Codebase-Knowledge-Builder architecture. Because repository analysis pipelines ingest large volumes of arbitrary source code, automated systems risk exceeding model context windows or generating unexpected cost overruns. This module mitigates those operational hazards by calculating exact or heuristic token counts and logging structural capacity utilization across every pipeline node.

    The component implements a two-tier quantification strategy. At its core, it relies on OpenAI's tiktoken library using the cl100k_base Byte-Pair Encoding (BPE) tokenizer scheme. To maintain continuous operation in constrained, offline, or misconfigured environments where tokenizer assets cannot be initialized, the module features a graceful degradation fallback to a character-based heuristic (len(text) // 4). Special token validation is explicitly suppressed using disallowed_special=() during BPE encoding passes, ensuring that raw code snippets containing literal delimiter sequences (such as <|endoftext|> or <|im_start|>) are parsed safely as standard text without raising encoding exceptions.

    In addition to token measurement, token_utils.py coordinates observability metrics for prompt payloads. The module evaluates active token counts against maximum model window boundaries (max_tokens), computes relative capacity percentages, and parses nested token allocation breakdowns across individual prompt segments (such as system guidelines, repository trees, and source code bodies). Formatted diagnostic summaries are broadcast synchronously through two distinct egress channels: styled visual output via output.py using the centralized emit() interface, and structured, machine-parseable execution records dispatched to the shared llm_logger.

    Public API

    count_tokens()

    Visibility: Public
    Signature: def count_tokens(text: str) -> int:

    Description:
    Calculates the exact or estimated token count of an input text string. The function first validates that the payload is not empty. It then attempts to obtain the cached tiktoken BPE tokenizer configured for the cl100k_base vocabulary. When available, the text is tokenized with disallowed_special=() passed to enc.encode(), ensuring that any special tokens natively embedded in raw source code (such as <|endoftext|> or formatting control markers) are treated as regular literal text rather than throwing a ValueError. If the tokenizer cannot be retrieved (e.g., in environments without external network access or pre-built tokenizer wheels), the function falls back gracefully to a standard heuristic calculation of integer division by four (len(text) // 4).

    Parameters: * text (str): The raw text or prompt content whose token count needs to be calculated.

    Returns: * int: The total number of tokens identified by the BPE tokenizer or estimated by the character heuristic. Returns 0 if text is empty or evaluates to a falsy value.

    Raises: * No exceptions are raised directly. Underlying tokenizer initialization failures and encoding exceptions are intercepted or mitigated via defensive parameters.

    Example: 

    def count_tokens(text: str) -> int:
    """Count tokens using tiktoken, with fallback to chars/4."""
    if not text:
        return 0
    enc = _get_encoding()
    if enc:
        return len(enc.encode(text, disallowed_special=()))
    return len(text) // 4

    The function serves as the foundational token counter used across the entire workflow, invoked directly by log_token_estimation() as well as upstream graph orchestrators. By passing disallowed_special=(), it bypasses tiktoken's default behavior of raising an error when encountering OpenAI special tokens within raw text. The fallback calculation len(text) // 4 reflects standard industry metrics where four English alphanumeric characters roughly equal one token, ensuring that pipeline monitoring functions even in resource-constrained environments.

    log_token_estimation()

    Visibility: Public
    Signature: def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:

    Description:
    Calculates, formats, and logs token consumption and context capacity metrics for a pipeline execution node. The function computes the total tokens present in prompt_content using count_tokens() and determines the percentage of context saturation relative to max_tokens. If a sub-component breakdown dictionary (token_usage) is supplied, it calculates the percentage share for each prompt section and creates aligned, human-readable terminal output alongside single-line structured logging payloads. Finally, it dispatches the metrics simultaneously to the terminal UI via emit() and to the shared persistent log via logger.info().

    Phase 1: Metric Quantification and Saturation Calculation

    def log_token_estimation(node_name: str, prompt_content: str, max_tokens: int, token_usage: dict | None = None) -> None:
    token_count = count_tokens(prompt_content)
    percentage = (token_count / max_tokens) * 100 if max_tokens else 0
    In this initial phase, the function determines the overall size of the prompt by delegating to count_tokens(prompt_content). It then calculates the capacity percentage by dividing the measured token count by max_tokens. To avoid runtime crashes caused by unconfigured or unbounded context limits, the division operation contains a zero-check guard (if max_tokens else 0), defaulting the saturation percentage to zero when max_tokens is unset or zero.

    Phase 2: Breakdown Formatting

        # Build token usage breakdown suffix for stdout display
    suffix = ""
    usage_log_str = ""
    if token_usage:
        max_label_len = max(len(label) for label in token_usage)
        lines = []
        log_parts = []
        for label, value in token_usage.items():
            pct = (value / token_count * 100) if token_count else 0
            padded_label = label.ljust(max_label_len)
            lines.append(f"\t{padded_label} : {value:,} ({pct:.0f}%)")
            log_parts.append(f"{label}={value:,} ({pct:.0f}%)")
        suffix = "\n" + "\n".join(lines)
        usage_log_str = " | " + " | ".join(log_parts)
    When a token_usage breakdown mapping is provided, the function processes each constituent component (such as system instructions, file contexts, or reasoning guidelines). It determines the maximum string length across all component keys to ensure proper alignment using .ljust(max_label_len). For each component, it computes the proportion of the overall prompt that it occupies, guarding against division-by-zero errors when token_count is zero. It builds two output formats: a multiline tab-indented string (suffix) for clean terminal display, and a pipe-delimited key-value string (usage_log_str) suitable for machine-readable log files.

    Phase 3: Telemetry Dispatch

        # Console output via emit (styled by CSV LEVEL=WARNING → yellow)
    emit(
        "TOKEN_ANALYTICS",
        suffix=suffix,
        node_name=node_name,
        token_count=f"{token_count:,}",
        max_tokens=f"{max_tokens:,}",
        percentage=f"{percentage:.1f}",
    )

    # File log stays single-line for parseability (structured, not translatable)
    logger.info(f"NODE EXEC | node={node_name} | prompt_tokens={token_count:,} / {max_tokens:,} ({percentage:.1f}% capacity){usage_log_str}")
    In the final phase, the function emits telemetry across dual output channels. For interactive terminal reporting, it calls emit() using the message key "TOKEN_ANALYTICS", which passes formatted numeric tokens, percentages, and the optional suffix block into the centralized formatting framework in output.py. Simultaneously, it writes a single-line, structured log entry directly to logger.info(). This single-line design guarantees clean parsing by automated log ingestion agents without line breaks corrupting the execution trace.

    Parameters: * node_name (str): The identifier or human-readable name of the execution node invoking the estimation (e.g., "CHAPTER_ANALYSIS"). * prompt_content (str): The complete serialized prompt string submitted to the LLM backend. * max_tokens (int): The maximum context window ceiling allowed for the target model or node. * token_usage (dict | None, optional): An optional dictionary mapping descriptive segment names to their respective token counts (dict[str, int]). Defaults to None.

    Returns: * None: This function executes side effects only (terminal emission and file logging).

    Raises: * No exceptions are explicitly raised. Non-standard input combinations (such as zero max_tokens or zero token_count) are handled defensively via ternary expressions.

    Example: 

    # Real usage pattern matching log_token_estimation execution in utils/token_utils.py:
log_token_estimation(
    node_name="GENERATE_CHAPTER_CONTENT",
    prompt_content="Sample prompt containing source code context...",
    max_tokens=32768,
    token_usage={
        "System Prompt": 1200,
        "File Context": 15400,
        "Task Guidelines": 450,
    }
)

    Internal Helpers

    _get_encoding()

    Visibility: Private
    Signature: def _get_encoding():

    Description:
    Implements a lazy-loading singleton pattern for the tiktoken encoding instance. The helper inspects the module-level variable _encoding. If _encoding is uninitialized (None), it attempts to load and compile the standard cl100k_base vocabulary using tiktoken.get_encoding("cl100k_base"). If initialization fails due to missing vocabularies, environment permission restrictions, or uninstalled binary packages, the exception is caught, and _encoding is explicitly assigned None. Subsequent calls reuse the cached instance or immediately return None, preventing redundant initialization overhead and eliminating recurrent exception handling during repetitive counting operations.

    Parameters: * None.

    Returns: * tiktoken.Encoding | None: The initialized tiktoken encoding instance corresponding to cl100k_base, or None if initialization failed.

    Raises: * No exceptions are raised. All exceptions encountered during tiktoken.get_encoding() are suppressed by a generic except Exception: block.

    Example: 

    # Lazy-loaded tiktoken encoding (singleton)
_encoding = None


def _get_encoding():
    global _encoding
    if _encoding is None:
        try:
            _encoding = tiktoken.get_encoding("cl100k_base")
        except Exception:
            _encoding = None
    return _encoding

    This helper ensures that the heavy cost of loading the tokenizer vocabulary is incurred only on the first call to count_tokens(). In serverless or containerized environments where external network requests to fetch BPE dictionaries might time out or fail, catching all exceptions allows the system to continue running by falling back to character-based heuristics without manual intervention.

    Module-Level Attributes

    logger

    • Type: logging.Logger
    • Signature: logger = logging.getLogger("llm_logger")
    • Description: Module-level logger bound to the named logger "llm_logger". This logger is shared with call_llm.py and initialized via main.py and output.py. It ensures that all node execution events and prompt token metrics are recorded to the centralized runtime log file (logs/llm_<timestamp>.log).

    _encoding

    • Type: tiktoken.Encoding | None
    • Signature: _encoding = None
    • Description: Internal global variable holding the memoized tiktoken encoder object. Initialized to None at module load time, it is populated on demand by _get_encoding().

    Data Structures

    The token_utils.py module consumes and constructs several structural data patterns during runtime telemetry processing and output formatting.

    token_usage Breakdown Mapping

    The token_usage parameter accepted by log_token_estimation() is an untyped dictionary representing individual prompt component allocations.

    Key Type Description
    label (dynamic) str A human-readable identifier representing a specific section of the prompt (e.g., "System Prompt", "File Context", "Outline").
    value (dynamic) int The calculated number of tokens consumed by that specific section of the prompt.

    Example Value: 

    {
    "System Prompt": 1420,
    "Context Files": 12850,
    "Task Instruction": 310
}

    TOKEN_ANALYTICS Emit Payload Schema

    When dispatching telemetry to output.py via emit(), the module passes the message identifier "TOKEN_ANALYTICS" along with a set of keyword arguments.

    Field Name Type Value Format / Description Example
    suffix str Multiline string formatted with tab indents and newline breaks containing the itemized token breakdown, or an empty string. "\n\tFile Context : 12,850 (89%)"
    node_name str The execution node identifier passed into log_token_estimation(). "OUTLINE_GENERATOR"
    token_count str Comma-separated representation of the measured prompt token count. "14,580"
    max_tokens str Comma-separated representation of the maximum allowed token capacity. "32,768"
    percentage str Formatted float string rounded to one decimal place representing context utilization. "44.5"

    Structured Log Record Format

    When log_token_estimation() writes to llm_logger, it emits a single-line, pipe-delimited string structured for automated parsing.

    Log Segment Schema / Pattern Description
    Prefix NODE EXEC Constant string identifying the event as a node execution trace.
    Node Name node={node_name} Name of the pipeline node currently executing.
    Token Metrics prompt_tokens={token_count:,} / {max_tokens:,} Human-readable token ratio with comma formatting.
    Capacity Percentage ({percentage:.1f}% capacity) Context window saturation rounded to one decimal point.
    Usage Breakdown \| {label}={value:,} ({pct:.0f}%) ... Repeated pipe-delimited list of prompt segment allocations (only present if token_usage is provided).

    Raw Log Output Example: 

    NODE EXEC | node=DOCS_GENERATOR | prompt_tokens=18,450 / 65,536 (28.2% capacity) | System=1,200 (7%) | Files=17,250 (93%)

    Error Handling

    The module implements defensive design patterns across all token counting and logging operations:

    1. Suppression of Special Token Encoding Errors: By default, tiktoken.Encoding.encode() treats tokens such as <|endoftext|> or <|fim_prefix|> as disallowed special sequences, raising a ValueError if they appear in input text. Because this system analyzes raw source code that may contain these literal sequences, count_tokens() passes disallowed_special=(). This forces the tokenizer to treat all special markers as ordinary strings, preventing encoding crashes during repository crawls.

    2. Tokenizer Initialization Fault Tolerance: In _get_encoding(), the invocation of tiktoken.get_encoding("cl100k_base") is wrapped in a broad try...except Exception: block. If the local machine lacks the necessary pre-downloaded BPE files or cannot compile the underlying Rust extension, the exception is swallowed and _encoding is set to None. This guarantees that tokenizer setup issues will not halt pipeline execution.

    3. Graceful Fallback to Character Heuristics: When _get_encoding() returns None, count_tokens() falls back to len(text) // 4. While this heuristic may differ slightly from exact BPE counts, it provides an approximation sufficient to keep context tracking functional.

    4. Zero-Division Prevention: Both percentage in the root scope and pct within the breakdown loop guard against division-by-zero errors: 

      percentage = (token_count / max_tokens) * 100 if max_tokens else 0
# ...
pct = (value / token_count * 100) if token_count else 0
      If max_tokens is configured as 0 or omitted, or if an empty prompt results in a token_count of 0, the metrics default to zero without raising an exception.
