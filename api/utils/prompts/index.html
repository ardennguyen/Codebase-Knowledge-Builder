    utils.prompts

    utils/prompts.py

    The utils.prompts module provides programmatic prompt construction functions and configuration generators for internal pipeline execution in Codebase-Knowledge-Builder. While major documentation generation modes rely on external prompt templates stored in the prompts/{mode}/ directory, specific internal operations require deterministic, inline prompt structures.

    This module centralizes prompt construction for operations such as code file classification, cross-chapter iterative summarization for context retention, and automated MkDocs configuration synthesis.

    Architectural Role and Workflow

    The prompt utilities in this module serve distinct stages across the generation lifecycle:

    Module-Level Functions

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Constructs an LLM prompt used by the file mapping components (such as DeterministicFileMapper) during api-reference mode. The generated prompt instructs the language model to inspect an indexed list of repository files and identify which files represent actual executable code modules (defining APIs, functions, classes, and business logic) versus non-code artifacts such as UI markup, configuration, static assets, and build system manifests. The prompt explicitly demands output formatted strictly as a YAML list of file indices.

    Parameters: * project_name (str): The name of the target repository or project being documented. * file_listing (str): A pre-formatted, indexed list of all discovered files in the project codebase (e.g., lines containing index numbers and file paths).

    Returns: * str: A formatted prompt ready to be dispatched to an LLM via the model execution utilities.

    Raises: * None.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The prompt generated by build_code_file_filter_prompt guides the LLM to output pure YAML arrays of integer indices corresponding to the input file_listing. By establishing strict exclusion criteria (e.g., eliminating .xaml, .storyboard, .xml, .json, .csproj, and .sln files), it optimizes token utilization and prevents non-logic files from consuming generation budget in downstream API reference passes. Downstream callers parse the returned fenced YAML block directly into a list of integers to slice the master file collection.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Assembles a structured prompt to generate a technical summary of a newly generated documentation chapter. This summary is injected into subsequent chapter prompts to maintain cross-chapter coherence and track architectural state across large document generations. The prompt enforces a uniform 4-dimension technical brief (Scope & Responsibility, Key Technical Elements, Implementation Patterns & Architecture, System Integration & Dependencies), requiring 3 to 5 concise technical sentences per dimension.

    Parameters: * chapter_num (int): The sequence number of the chapter currently being summarized. * abstraction_name (str): The title or architectural abstraction represented by the chapter. * chapter_content (str): The raw Markdown content generated for the chapter. * language (str, optional): The target natural language for the summary output. Defaults to "english".

    Returns: * str: The fully populated prompt string instructing the LLM to summarize the chapter across the 4 technical dimensions.

    Raises: * None.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.

    The summary captures 4 technical dimensions with 3-5 sentences each:
    1. Component scope & responsibility
    2. Key classes/services/functions and their roles
    3. Implementation patterns & architectural decisions
    4. Inter-component interfaces & dependencies
    """
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    build_chapter_summary_prompt enforces a standardized schema for inter-chapter memory. When handling multi-language documentation pipelines, the language argument prefixes the prompt with an explicit localization directive (Write the entire summary in <Language>.) whenever the selected language differs from English. The resulting 4-point structure guarantees that downstream chapter generations receive concise, high-density architectural summaries covering domain scope, concrete identifiers, implementation patterns, and dependency graphs without context overflow.

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description:
    Generates a complete mkdocs.yml configuration file string configured for the mkdocs-material theme. The configuration includes code block copy buttons, Pygments syntax highlighting with line anchors, inline code highlights, and Python Markdown SuperFences configured to render Mermaid diagram definitions natively. It parses the incoming navigation YAML block and merges it under the primary nav: tree starting with Home: index.md.

    Parameters: * site_name (str): The title displayed in the MkDocs header and metadata. * nav_yaml (str): A YAML snippet representing navigation items. Can include a leading nav: line, which is stripped automatically.

    Returns: * str: A valid, multi-line YAML document ready to be written directly to mkdocs.yml.

    Raises: * None.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    """Build a complete mkdocs.yml for local --mkdocs output.

    Generates a ready-to-use MkDocs Material config with:
    - Material theme with code copy buttons
    - Syntax highlighting (pymdownx.highlight + inlinehilite)
    - Mermaid diagram rendering via pymdownx.superfences custom fences
    - Navigation from the generated nav_snippet

    Users can run `mkdocs serve` or `mkdocs build` directly in the output dir.
    """
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The function handles YAML formatting quirks by splitting nav_yaml on newline boundaries and stripping the initial line (assuming it starts with nav:), subsequently indenting the remaining navigation structure under nav: alongside - Home: index.md. The configuration enables pymdownx.superfences with Python object resolution for fence_code_format, allowing MkDocs to natively interpret fenced ```mermaid blocks generated across the documentation pipeline.
