    utils.prompts

    Original File Path: utils/prompts.py

    The utils.prompts module provides reusable inline prompt construction functions and configuration generators for the Codebase-Knowledge-Builder pipeline. While primary document generation in different execution modes relies on template files loaded from prompts/{mode}/, certain internal processing nodes require fixed, programmatic prompt schemas or static configuration artifacts. This module centralizes non-template prompt engineering and configuration formatting logic to ensure consistency, testability, and maintainability across workflow steps.

    Key capabilities provided by this module include: 1. Source Code File Classification: Constructing prompts for LLM-based deterministic file mapping to isolate functional code modules from UI assets, configurations, and build artifacts. 2. Progressive Cross-Chapter Summarization: Formulating structured prompts to extract multi-dimensional technical summaries across written documentation chapters to sustain long-term LLM context windows. 3. MkDocs Configuration Assembly: Assembling complete, deployment-ready mkdocs.yml configuration manifests containing syntax highlighting, code copy widgets, navigation trees, and Mermaid diagram renderers.

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description: Constructs an LLM prompt that instructs the model to inspect a flat codebase directory listing and filter out non-code assets. In api-reference mode, documentation targets must be restricted to genuine code modules (such as APIs, functions, classes, and business logic) rather than UI layouts, data configurations, static assets, or project files. The prompt enforces a strict YAML list output containing the numerical indices corresponding to valid code modules.

    Parameters: * project_name (str): The name of the project or repository being analyzed. * file_listing (str): A formatted string containing indexed file paths (e.g., 0: path/to/file.py).

    Returns: * str: A formatted prompt ready to be dispatched to an LLM completion endpoint.

    Raises: * This function does not raise exceptions internally; string interpolation is performed on the provided arguments.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The prompt generated by build_code_file_filter_prompt sets explicit boundary conditions on what constitutes documentation-worthy source files. By providing a strict exclusion list covering UI markups (.xaml, .storyboard, .html), configurations (.xml, .json, .manifest, .ini), build system definitions (.csproj, .sln), and standalone documentation, it minimizes token waste in subsequent generation passes. The return specification constrains the model response to a clean YAML sequence of numeric integer indices matching the provided listing, enabling deterministic parsing by regex or YAML loaders in upstream graph nodes such as nodes.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description: Constructs a structured prompt instructing the LLM to summarize a newly generated documentation chapter. This summary is injected into future chapter prompts to provide running architectural context across iterative LLM invocations. The prompt guides the model to produce 3 to 5 sentences across four technical dimensions: component scope, key technical elements, implementation patterns, and system integration dependencies. It also supports localization by dynamically prefixing a language directive if a non-English language is specified.

    Parameters: * chapter_num (int): The numerical index of the chapter being summarized. * abstraction_name (str): The title or high-level abstraction name of the chapter. * chapter_content (str): The raw Markdown text of the generated chapter. * language (str, optional): Target language for the summary output. Defaults to "english".

    Returns: * str: A formatted prompt ready to be evaluated by the LLM summarizer.

    Raises: * This function does not raise exceptions internally.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str,
                                  chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.
    """
    lang_instruction = (
        f"Write the entire summary in {language.capitalize()}. "
        if language.lower() != "english" else ""
    )
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The prompt built by build_chapter_summary_prompt enforces an information-dense format across four explicit technical dimensions, preventing the LLM from generating vague or superficial summaries. By segregating the evaluation into component scope, concrete elements, architectural design patterns, and cross-system integration points, the resulting summary captures critical interface boundaries and state models needed by subsequent chapter generation nodes. The helper conditionally prepends a language enforcement directive if language is not set to "english", ensuring multi-lingual documentation runs maintain consistent target language outputs across chapter briefs.

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description: Generates the complete text content of an mkdocs.yml configuration file for projects built with the MkDocs Material theme. It parses a partial YAML navigation snippet, extracts child navigation entries, injects a default home landing page (Home: index.md), and configures essential Markdown extensions, including PyMdown Extensions for code copy buttons, Pygments syntax highlighting, inline highlighting, and Mermaid diagram code block fences.

    Parameters: * site_name (str): The display title for the MkDocs documentation site. * nav_yaml (str): A YAML block representing navigation structure, beginning with a nav: header line followed by indented navigation entries.

    Returns: * str: The complete YAML configuration content formatted for an mkdocs.yml manifest file.

    Raises: * This function does not raise exceptions internally.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    """Build a complete mkdocs.yml for local --mkdocs output.

    Generates a ready-to-use MkDocs Material config with:
    - Material theme with code copy buttons
    - Syntax highlighting (pymdownx.highlight + inlinehilite)
    - Mermaid diagram rendering via pymdownx.superfences custom fences
    - Navigation from the generated nav_snippet
    """
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    build_mkdocs_config handles the transition between AI-generated navigation snippets and static site generator configuration files. When nav_yaml is passed in, the function splits the string by newlines and drops the first line (nav:) to avoid duplicate YAML keys, rejoining the remaining indented body underneath the base Home: index.md root item. The output configuration includes pymdownx.superfences custom fences mapped to !!python/name:pymdownx.superfences.fence_code_format, which allows browsers to dynamically render Mermaid sequence, flowchart, and class diagrams without requiring external precompilation tools.
