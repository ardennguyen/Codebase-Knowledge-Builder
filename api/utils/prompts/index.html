    utils.prompts

    Original File Path: utils/prompts.py

    Overview

    The utils.prompts module provides reusable inline prompt builders and configuration formatters for the Codebase-Knowledge-Builder engine. Unlike mode-specific templates loaded dynamically from the prompts/{mode}/ directory, the builders in this module generate specialized system instructions, cross-chapter context summaries, and static site configuration files required during internal pipeline execution.

    The module encapsulates three primary capabilities: 1. Source Code Filtering: Assembles prompts that direct an LLM to distinguish core code modules from configuration, UI layouts, and assets during deterministic file mapping in API reference mode. 2. Context Summarization: Generates structured prompts to produce technical chapter summaries, capturing component scope, technical elements, architecture patterns, and integration dependencies to maintain inter-chapter coherence. 3. MkDocs Configuration Generation: Generates standard mkdocs.yml configurations with pre-configured themes (Material for MkDocs), search plugins, code copy functionality, and Mermaid diagram renderers using pymdownx.superfences.

    Module-Level Functions

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description: Constructs the raw string prompt evaluated by the LLM (typically in DeterministicFileMapper within nodes) to filter out non-code assets. It instructs the language model to analyze a provided index of file paths and return a strict YAML list containing only the integer indices corresponding to functional code modules (such as APIs, business logic, classes, and helper functions) while explicitly discarding UI layouts, project manifests, and static documentation.

    Parameters: * project_name (str): The name or identifier of the project being documented. * file_listing (str): A pre-formatted, indexed list of candidate files within the repository.

    Returns: * str: A formatted prompt containing instructions, project name, candidate file listing, and output schema requirements (YAML index array).

    Raises: * No explicit exceptions raised internally.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The returned prompt specifies rigid negative constraints (e.g., excluding .xaml, .json, .csproj, and documentation files) to prevent the documentation pipeline from attempting to generate API reference chapters for non-executable or declarative files. By requesting output in a strict yaml ... code block containing integer indices, the downstream parser can reliably extract and map the valid file indices back to the source inventory.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description: Constructs a structured prompt instructing an LLM to generate a concise, multi-dimensional technical brief for an already generated chapter. The resulting brief acts as cross-chapter context in sequential pipeline executions, enabling subsequent chapter generation nodes to reference concepts, models, and boundaries established in previous chapters without exceeding context token limits.

    The generated prompt enforces a 4-dimensional extraction model where each dimension is answered in 3 to 5 sentences: 1. Component scope and technical domain responsibilities. 2. Concrete classes, functions, interfaces, and service models. 3. Design patterns, architectural decisions, and error-handling strategies. 4. Inter-component boundaries, dependencies, and integration touchpoints.

    Parameters: * chapter_num (int): The sequence index of the target chapter. * abstraction_name (str): The semantic title or abstraction name of the chapter component. * chapter_content (str): The full markdown text of the generated documentation chapter. * language (str, optional): The target output language. Defaults to "english". If a non-English string is provided, a localization instruction is prepended.

    Returns: * str: The assembled prompt text including localization prefixes, the 4-part analytical rubric, and the chapter content payload.

    Raises: * No explicit exceptions raised internally.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.

    The summary captures 4 technical dimensions with 3-5 sentences each:
    1. Component scope & responsibility
    2. Key classes/services/functions and their roles
    3. Implementation patterns & architectural decisions
    4. Inter-component interfaces & dependencies
    """
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The function handles dynamic localization by conditionally prefixing the prompt with Write the entire summary in {language.capitalize()}. when language is not set to "english". The structured 4-part rubric prevents vague summaries by forcing concrete naming of classes, services, and integration points, ensuring downstream LLM calls in nodes receive high-density technical context.

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description: Formats and returns a complete mkdocs.yml configuration string. It configures the MkDocs Material theme, clipboard copy buttons, search plugins, inline syntax highlighting, and custom Mermaid fence handlers (pymdownx.superfences configured with fence_code_format).

    The function splits the supplied nav_yaml input string to strip any leading nav: header line and embeds the remaining hierarchy under a root - Home: index.md navigation entry.

    Parameters: * site_name (str): The documentation site title displayed in the header and navigation bar. * nav_yaml (str): A YAML-formatted navigation hierarchy string generated during documentation compilation.

    Returns: * str: The serialized YAML configuration file content ready to be written to mkdocs.yml.

    Raises: * No explicit exceptions raised internally.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    """Build a complete mkdocs.yml for local --mkdocs output.

    Generates a ready-to-use MkDocs Material config with:
    - Material theme with code copy buttons
    - Syntax highlighting (pymdownx.highlight + inlinehilite)
    - Mermaid diagram rendering via pymdownx.superfences custom fences
    - Navigation from the generated nav_snippet

    Users can run `mkdocs serve` or `mkdocs build` directly in the output dir.
    """
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"plugins:\n"
        f"  - search\n"
        f"  - panzoom\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The navigation normalization logic inspects nav_yaml line-by-line using split("\n"). By taking nav_lines[1:], it safely discards redundant top-level nav: tags emitted by language models or navigation builders, splicing the clean YAML child tree directly below the default root page (- Home: index.md). The returned YAML string allows users to immediately run mkdocs serve or mkdocs build on the generated output directory.
