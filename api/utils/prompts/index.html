    utils.prompts

    Source File: utils/prompts.py

    The utils.prompts module provides programmatic prompt constructors, site configuration generators, and presentation assets used across the Codebase-Knowledge-Builder pipeline. Unlike mode-specific chapter generation templates loaded dynamically from external filesystem directories (such as prompts/{mode}/), the builders in this module represent inline, structural prompts and configuration builders critical to core graph execution, inter-chapter context synthesis, deterministic file filtering, and static documentation site generation.

    Architectural Role & Pipeline Integration

    The functions within utils.prompts serve three distinct phases of execution within the documentation pipeline:

    1. Deterministic Code Filtering: Generates structured classification instructions for the Large Language Model (LLM) to isolate functional source code modules from non-code assets (e.g., markup, configs, build scripts).
    2. Cross-Chapter Context Maintenance: Constructs structured summarization prompts across four technical dimensions (scope, components, patterns, integration) to maintain context window continuity across long-form multi-chapter generation.
    3. MkDocs Static Site Generation: Synthesizes the runtime mkdocs.yml manifest and custom CSS rules required to render interactive Mermaid diagrams and dark/light navigation themes in the exported documentation.

    Module-Level Functions

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Constructs an LLM classification prompt designed for the DeterministicFileMapper step in api-reference mode. It instructs the language model to analyze a newline-delimited file manifest and separate executable source modules (containing APIs, classes, business logic, or interface definitions) from UI layouts, static configuration files, build definitions, and ancillary assets. The model is constrained to return a strict YAML sequence of integer indices corresponding to valid code files.

    Parameters: * project_name (str): The human-readable name or identifier of the repository/project being processed. * file_listing (str): The formatted, enumerated file manifest representing the repository tree.

    Returns: * str: A fully formatted zero-shot prompt with embedded YAML schema instructions and exclusion rules.

    Raises: * This function does not raise exceptions directly.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The output of build_code_file_filter_prompt() acts as an input filter that prevents non-code files from consuming LLM context window quotas during API documentation runs. By strictly bounding the output format to a YAML sequence of integers (- 0, - 1, etc.), down-stream parser nodes can deterministically deserialize the response using standard YAML or regex loaders without encountering unstructured markdown conversational padding.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Generates a structured prompt to summarize an already-written documentation chapter. The generated summary serves as recursive inter-chapter context fed into successive chapter generation passes. It enforces a 4-dimensional technical structure covering component scope, concrete implementation entities, architectural patterns, and external system integrations. It also supports localization by dynamically prepending language constraints when language is not English.

    Parameters: * chapter_num (int): The numeric index of the chapter being summarized. * abstraction_name (str): The title, abstraction layer, or concept documented in the chapter. * chapter_content (str): The complete markdown text of the generated chapter. * language (str, optional): Target language for the summary output. Defaults to "english".

    Returns: * str: A prompt string instructing the model to produce a 4-point technical brief.

    Raises: * This function does not raise exceptions directly.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The 4-part structure enforced by build_chapter_summary_prompt() prevents context drift across sequential generation passes in large codebases. By isolating scope, concrete identifiers, architectural patterns, and dependency relationships into dense 3-5 sentence blocks, the resulting summaries remain informative while keeping token counts low enough to fit within cumulative context windows for downstream nodes.

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description:
    Assembles the complete YAML configuration string for an MkDocs documentation site using the material theme. It parses and strips header prefixes from the provided navigation snippet, configures light/dark mode toggles, sets up search and panzoom plugins, enables syntax highlighting with line numbering, and registers custom fence formatters to render Mermaid diagrams natively via pymdownx.superfences.

    Parameters: * site_name (str): The title of the documentation project rendered in the site header and metadata. * nav_yaml (str): A YAML-formatted navigation hierarchy, typically containing a nav: root node.

    Returns: * str: The full text content of a valid mkdocs.yml file.

    Raises: * This function does not raise exceptions directly.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"  palette:\n"
        f"    - scheme: default\n"
        f"      toggle:\n"
        f"        icon: material/brightness-7\n"
        f"        name: Switch to dark mode\n"
        f"    - scheme: slate\n"
        f"      toggle:\n"
        f"        icon: material/brightness-4\n"
        f"        name: Switch to light mode\n"
        f"plugins:\n"
        f"  - search\n"
        f"  - panzoom:\n"
        f"      include_selectors:\n"
        f"        - '.mermaid'\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"extra_css:\n"
        f"  - stylesheets/mermaid-vibrant.css\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    This configuration builder automates the generation of local static documentation sites when the --mkdocs CLI flag is supplied. It uses pymdownx.superfences.fence_code_format for Mermaid diagram processing alongside the panzoom plugin, enabling interactive zooming and panning for complex architectural diagrams directly in the rendered browser UI.

    build_mermaid_css()

    Visibility: Public
    Signature: def build_mermaid_css() -> str:

    Description:
    Generates a static CSS stylesheet string that overrides default Material for MkDocs CSS rules on Mermaid diagrams. By default, MkDocs Material strips Mermaid's internal theme directives and applies muted monochromatic colors. This function returns explicit CSS rules that restore vibrant visual styling, including warm yellow cluster backgrounds, lavender node fills, and purple boundary strokes.

    Parameters: * None.

    Returns: * str: Raw CSS string ready to be written to stylesheets/mermaid-vibrant.css.

    Raises: * This function does not raise exceptions directly.

    Example: 

    def build_mermaid_css() -> str:
    return """\
/* Vibrant Mermaid diagram theme — overrides Material's muted colors */
/* Matches Mermaid's built-in 'default' theme (yellow subgraphs, lavender nodes) */

/* Subgraph/cluster backgrounds — warm yellow */
.mermaid .cluster rect {
  fill: #ffffde !important;
  stroke: #aaaa33 !important;
  stroke-width: 1px !important;
}

/* Cluster/subgraph title text */
.mermaid .cluster text {
  fill: #333 !important;
}

/* Node fills — light lavender */
.mermaid .node rect,
.mermaid .node polygon,
.mermaid .node circle {
  fill: #ECECFF !important;
  stroke: #9370DB !important;
  stroke-width: 1px !important;
}

/* Node text */
.mermaid .nodeLabel {
  color: #333 !important;
}

/* Edge label backgrounds */
.mermaid .edgeLabel {
  background-color: #e8e8e8 !important;
  color: #333 !important;
}

/* Edge lines */
.mermaid .edge-pattern-solid {
  stroke: #333 !important;
}
"""

    The CSS rules returned by build_mermaid_css() target specific SVG elements generated by Mermaid (such as .cluster rect, .node rect, and .nodeLabel) with !important declarations. This guarantees consistent visual contrast and readability across both light (default) and dark (slate) MkDocs themes without requiring client-side JavaScript execution.
