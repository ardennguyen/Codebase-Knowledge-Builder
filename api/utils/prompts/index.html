    utils.prompts

    Source File Path: utils/prompts.py

    The utils.prompts module contains reusable, programmatic prompt builders and documentation scaffolding utilities for internal system routines in Codebase-Knowledge-Builder. While mode-specific architectural prompts are loaded from structured external templates (prompts/{mode}/), utils.prompts manages programmatic prompt constructions for deterministic file filtering and cross-chapter contextual summarization, as well as configuration generators for local MkDocs exports (YAML config generation, Mermaid CSS overrides, and recursive navigation hierarchy construction).

    Architectural Role and Workflow

    The functions in utils.prompts are utilized across distinct stages of the documentation pipeline:

    1. Deterministic File Filtering: Pre-generation phase where non-code assets, configurations, and build artifacts are stripped out via zero-shot/few-shot index extraction prompts.
    2. Contextual Chapter Summaries: Intra-generation feedback loop where completed chapters are summarized into structured four-dimensional technical briefs, providing continuous architectural context to subsequent chapter nodes.
    3. MkDocs Site & Navigation Assembly: Post-generation serialization phase where the table of contents hierarchy is parsed, matched to generated markdown files, styled with high-contrast Mermaid CSS rules, and written into a standalone mkdocs.yml.

    Module-Level Functions

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Constructs an LLM prompt string designed for DeterministicFileMapper in API reference extraction pipelines. The prompt instructs the language model to review an indexed list of repository file paths and return a clean YAML array of integer indices corresponding exclusively to source code files (modules containing functions, classes, and business logic). It explicitly specifies exclusion rules for UI layout files, configuration files, build scripts, static assets, and documentation.

    Parameters: * project_name (str): The name of the target repository or codebase being processed. * file_listing (str): Formatted string containing the indexed repository file paths (e.g., 0: src/main.py\n1: config.json).

    Returns: * str: The complete, formatted prompt ready to be dispatched to the LLM via utils.call_llm.

    Raises: * None.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The prompt structure enforces a strict output constraint (Return ONLY a YAML list of the file indices) with a few-shot markdown fence example. By operating on integer indices rather than raw file paths, the prompt minimizes token generation overhead during the LLM filtering pass and guarantees reliable programmatic parsing.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Generates a structured prompt to summarize a previously generated chapter across four standardized technical dimensions. The resulting brief acts as historical memory and is prepended to subsequent chapter generation prompts within nodes to preserve cross-module coherence, maintain terminology consistency, and prevent duplicate explanations. The summary evaluates component scope, key classes/functions, implementation patterns/architectural decisions, and inter-component dependencies.

    Parameters: * chapter_num (int): The ordinal sequence number of the completed chapter. * abstraction_name (str): The chapter's title or architectural component identifier. * chapter_content (str): The full Markdown text generated for the specified chapter. * language (str, optional): The target output natural language. Defaults to "english".

    Returns: * str: A prompt string instructing the model to generate 3–5 technical sentences for each of the four structural dimensions.

    Raises: * None.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The function incorporates conditional prefixing: if language is anything other than "english", a directive is prepended forcing the model to emit the brief in the requested target language. The prompt strictly limits the response length per section (3–5 sentences) to ensure that the accumulated summary context fits comfortably within downstream token budgets managed by utils.token_utils.

    Description:
    Assembles a complete, production-ready mkdocs.yml configuration string for rendering the documentation via Material for MkDocs. Configures the Material theme, dark/light mode toggles, search plugins, panzoom for interactive Mermaid diagram navigation, PyMdown Extensions syntax highlighting, custom super-fences for Mermaid diagram formatting, and extra CSS references.

    Parameters: * site_name (str): The human-readable title displayed in the documentation header and browser tab. * nav_yaml (str): A YAML-formatted navigation block containing the mapped hierarchy of generated files.

    Returns: * str: A valid, multi-line YAML document string ready to be saved to mkdocs.yml.

    Raises: * None.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"    - navigation.indexes\n"
        f"  palette:\n"
        f"    - scheme: default\n"
        f"      toggle:\n"
        f"        icon: material/brightness-7\n"
        f"        name: Switch to dark mode\n"
        f"    - scheme: slate\n"
        f"      toggle:\n"
        f"        icon: material/brightness-4\n"
        f"        name: Switch to light mode\n"
        f"plugins:\n"
        f"  - search\n"
        f"  - panzoom:\n"
        f"      include_selectors:\n"
        f"        - '.mermaid'\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"extra_css:\n"
        f"  - stylesheets/mermaid-vibrant.css\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The function normalizes incoming nav_yaml blocks by removing any leading nav: declaration to prevent duplicate top-level keys in the final YAML configuration. It enforces code block copying (content.code.copy), index navigation (navigation.indexes), and registers !!python/name:pymdownx.superfences.fence_code_format so that Mermaid diagram blocks are rendered as interactive vector graphics rather than raw preformatted code blocks.

    build_mermaid_css()

    Visibility: Public

    Description:
    Returns raw CSS stylesheet content that overrides default Material for MkDocs Mermaid theme color styles. Material for MkDocs suppresses default Mermaid %%{init}%% palette configurations; this stylesheet restores distinct styling featuring yellow cluster/subgraph fills, lavender node rectangles/polygons, purple node borders, and explicit dark text colors.

    Parameters: * None.

    Returns: * str: Raw CSS string containing rules for .mermaid .cluster, .mermaid .node, .mermaid .nodeLabel, .mermaid .edgeLabel, and .mermaid .edge-pattern-solid.

    Raises: * None.

    Example: 

    def build_mermaid_css() -> str:
    """Build CSS overrides for vibrant Mermaid diagrams in MkDocs Material.

    Material for MkDocs forcibly overrides Mermaid's %%{init}%% directives,
    so we use CSS to restore vibrant colors matching Mermaid's default theme:
    - Yellow subgraph backgrounds
    - Lavender node fills
    - Purple node strokes
    """
    return """\
/* Vibrant Mermaid diagram theme — overrides Material's muted colors */
/* Matches Mermaid's built-in 'default' theme (yellow subgraphs, lavender nodes) */

/* Subgraph/cluster backgrounds — warm yellow */
.mermaid .cluster rect {
  fill: #ffffde !important;
  stroke: #aaaa33 !important;
  stroke-width: 1px !important;
}

/* Cluster/subgraph title text */
.mermaid .cluster text {
  fill: #333 !important;
}

/* Node fills — light lavender */
.mermaid .node rect,
.mermaid .node polygon,
.mermaid .node circle {
  fill: #ECECFF !important;
  stroke: #9370DB !important;
  stroke-width: 1px !important;
}

/* Node text */
.mermaid .nodeLabel {
  color: #333 !important;
}

/* Edge label backgrounds */
.mermaid .edgeLabel {
  background-color: #e8e8e8 !important;
  color: #333 !important;
}

/* Edge lines */
.mermaid .edge-pattern-solid {
  stroke: #333 !important;
}
"""

    The returned CSS uses !important declarations to supersede Material's low-contrast CSS variables. This ensures that architectural diagrams generated across chapters remain legible in both light and dark display modes without requiring manual chart-by-chart style declarations.

    build_grouped_nav()

    Visibility: Public
    Signature: def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:

    Description:
    Recursively constructs lines of YAML text representing the MkDocs navigation hierarchy from an arbitrary tree of LLM-generated section structures. For each section, it checks for nested sub-sections under the children key and recurses with increased indentation. For leaf nodes (listed under modules), it searches chapter_files for a matching module_name and formats the entry to point to api/{match['filename']}.

    Parameters: * sections (list): A list of dictionary objects describing sections. Each dictionary may contain "name" (str), "children" (list), and "modules" (list[str]). * chapter_files (list): A list of dictionaries representing generated chapter files, where each dictionary contains at least "module_name" and "filename". * indent (int, optional): Number of leading whitespace characters for the current indentation level. Defaults to 4.

    Returns: * list[str]: A list of properly indented YAML string lines representing the navigation tree.

    Raises: * None.

    Example: 

    def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:
    """Recursively build MkDocs nav YAML lines from LLM section grouping.

    Handles arbitrary nesting depth via the ``children`` key.
    Each leaf module is matched against *chapter_files* by ``module_name``.
    """
    lines = []
    pad = " " * indent
    for section in sections:
        lines.append(f"{pad}- {section['name']}:")
        if "children" in section:
            lines.extend(build_grouped_nav(section["children"], chapter_files, indent + 2))
        for mod_name in section.get("modules", []):
            match = next((cf for cf in chapter_files if cf["module_name"] == mod_name), None)
            if match:
                display = mod_name.split(".")[-1] if "." in mod_name else mod_name
                lines.append(f"{pad}  - '{display}': 'api/{match['filename']}'")
    return lines

    If a module name contains dots (e.g., utils.prompts), build_grouped_nav splits the name by . and uses only the terminal token (prompts) as the visible navigation label, while preserving the full matching path to the physical markdown target file. If a module specified in sections is not present in chapter_files, it is skipped without raising an error.

    collect_all_modules()

    Visibility: Public
    Signature: def collect_all_modules(sections: list) -> set:

    Description:
    Performs a recursive tree traversal over a hierarchical section definition to extract and aggregate all referenced module names into a flat Python set. This utility is used to audit generated sections against discovered source files, identifying unmapped modules or verifying that no duplicate entries exist in the navigation tree.

    Parameters: * sections (list): A list of dictionary trees, where each node contains an optional "modules" list and an optional "children" list of sub-sections.

    Returns: * set: An unordered set containing every distinct module name string found across all depths of the section tree.

    Raises: * None.

    Example: 

    def collect_all_modules(sections: list) -> set:
    """Recursively collect all module names referenced in a sections tree."""
    result = set()
    for section in sections:
        result.update(section.get("modules", []))
        if "children" in section:
            result.update(collect_all_modules(section["children"]))
    return result

    This function traverses nested dictionaries without depth limits, avoiding module name duplication via Python set union operations (set.update). It handles sparse nodes gracefully by using .get("modules", []).
