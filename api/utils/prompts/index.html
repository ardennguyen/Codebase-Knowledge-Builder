    utils.prompts

    Source File: utils/prompts.py

    Overview

    The utils.prompts module provides programmatic prompt constructors, configuration generators, and recursive navigation layout transformers used across the Codebase-Knowledge-Builder execution pipeline. Unlike user-configurable or domain-specific prompt templates located in mode directories (prompts/{mode}/), the utilities in this module generate inline prompts and structural outputs required for deterministic internal nodes.

    Key capabilities implemented in this module include: - Code File Filtering Prompts: Constructing structured, zero-shot classification prompts for DeterministicFileMapper to filter source files containing actionable code logic from static assets, UI templates, build files, and configuration files. - Cross-Chapter Summarization Prompts: Formatting standardized technical brief extraction prompts across four distinct system dimensions (scope, components, architecture, interfaces) to preserve context memory between sequential chapter generations. - Documentation Site Assembly: Generating production-ready mkdocs.yml configurations with code copy buttons, syntax highlighters, Mermaid diagram pan-zoom support, and CSS overrides. - Hierarchical Navigation Transformers: Recursively parsing arbitrarily nested section trees and matching code abstraction units against generated documentation files to produce compliant MkDocs navigation structures.

    Module-Level Functions

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Constructs an inline LLM prompt for the DeterministicFileMapper node during API reference generation. The prompt instructs the model to inspect an indexed list of all candidate project files and identify only the files containing actual program logic (functions, classes, business logic, endpoints) while filtering out configuration, UI layouts, assets, and project files. The output constraint enforces a strict YAML integer list format containing the indices of valid files.

    Parameters: * project_name (str): The name of the codebase or target repository being processed. * file_listing (str): Pre-formatted newline-separated string containing indexed file paths (e.g., 0: src/main.py\n1: config.json).

    Returns: * str: The complete system/user prompt ready for dispatch to an LLM.

    Raises: * No explicit exceptions are raised by this function.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The returned string directly constrains the LLM output format by providing a concrete few-shot YAML sample block (- 0\n- 1\n- 3). This formatting constraint allows caller nodes in nodes to deterministically parse the raw LLM response using standard YAML decoders without requiring complex natural language extraction. If non-code files are included in the codebase, the prompt's exclusion rules prevent extraneous files from bloating the downstream chapter generation stages.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Constructs a prompt that instructs the LLM to summarize a newly generated documentation chapter across four distinct architectural dimensions. The resulting summary serves as rolling context for generating subsequent chapters to maintain architectural coherence and eliminate redundant explanations across the generated documentation suite.

    Parameters: * chapter_num (int): The numeric index of the chapter currently being processed. * abstraction_name (str): The title or conceptual abstraction documented in the chapter. * chapter_content (str): The raw Markdown text of the generated chapter. * language (str, optional): The target output language for the summary. Defaults to "english".

    Returns: * str: The structured summarization prompt string.

    Raises: * No explicit exceptions are raised by this function.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:
    lang_instruction = f"Write the entire summary in {language.capitalize()}. " if language.lower() != "english" else ""
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The prompt specifies an explicit 4-point structure covering (1) Component Scope & Responsibility, (2) Key Technical Elements, (3) Implementation Patterns & Architecture, and (4) System Integration & Dependencies. When a non-English language parameter is provided (such as "chinese" or "spanish"), a language instruction prefix is prepended to ensure the context memory matches the target documentation language configured in main. The input chapter_content is appended at the bottom separated by a horizontal rule to clearly delineate instructions from payload data.

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description:
    Generates a complete, ready-to-use mkdocs.yml configuration string optimized for the Material for MkDocs theme. The generated configuration enables syntax highlighting, copy-to-clipboard functionality on code blocks, dark/light palette toggles, search indexing, Mermaid diagram pan/zoom interactions, custom Mermaid fences via pymdownx.superfences, and an injected custom stylesheet for diagram color vibrancy.

    Parameters: * site_name (str): The display name of the generated documentation site. * nav_yaml (str): A YAML-formatted navigation snippet containing site navigation nodes.

    Returns: * str: The full text contents of an mkdocs.yml file.

    Raises: * No explicit exceptions are raised by this function.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"    - navigation.indexes\n"
        f"  palette:\n"
        f"    - scheme: default\n"
        f"      toggle:\n"
        f"        icon: material/brightness-7\n"
        f"        name: Switch to dark mode\n"
        f"    - scheme: slate\n"
        f"      toggle:\n"
        f"        icon: material/brightness-4\n"
        f"        name: Switch to light mode\n"
        f"plugins:\n"
        f"  - search\n"
        f"  - panzoom:\n"
        f"      include_selectors:\n"
        f"        - '.mermaid'\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"extra_css:\n"
        f"  - stylesheets/mermaid-vibrant.css\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The function parses the incoming nav_yaml string, stripping any leading top-level nav: declaration by splitting on newlines and joining lines from index 1 onward. It then mounts the default Home: index.md landing page followed by the dynamic navigation items. The output ensures that the pymdownx.superfences extension correctly maps ```mermaid fences to the Python callable pymdownx.superfences.fence_code_format for client-side diagram rendering.

    build_mermaid_css()

    Visibility: Public
    Signature: def build_mermaid_css() -> str:

    Description:
    Generates a static CSS stylesheet string that overrides default MkDocs Material styles for Mermaid diagrams. MkDocs Material applies muted grayscale overrides to Mermaid SVG elements, which neutralizes distinct subgraph clustering. This function returns explicit CSS rules that restore vibrant visual distinctions matching Mermaid's default palette (light yellow subgraph clusters, lavender node fills, purple borders, and high-contrast labels).

    Parameters: * None.

    Returns: * str: The complete raw CSS stylesheet contents.

    Raises: * No explicit exceptions are raised by this function.

    Example: 

    def build_mermaid_css() -> str:
    return """\
/* Vibrant Mermaid diagram theme — overrides Material's muted colors */
/* Matches Mermaid's built-in 'default' theme (yellow subgraphs, lavender nodes) */

/* Subgraph/cluster backgrounds — warm yellow */
.mermaid .cluster rect {
  fill: #ffffde !important;
  stroke: #aaaa33 !important;
  stroke-width: 1px !important;
}

/* Cluster/subgraph title text */
.mermaid .cluster text {
  fill: #333 !important;
}

/* Node fills — light lavender */
.mermaid .node rect,
.mermaid .node polygon,
.mermaid .node circle {
  fill: #ECECFF !important;
  stroke: #9370DB !important;
  stroke-width: 1px !important;
}

/* Node text */
.mermaid .nodeLabel {
  color: #333 !important;
}

/* Edge label backgrounds */
.mermaid .edgeLabel {
  background-color: #e8e8e8 !important;
  color: #333 !important;
}

/* Edge lines */
.mermaid .edge-pattern-solid {
  stroke: #333 !important;
}
"""

    The CSS rules utilize !important declarations to supersede Material's high-specificity CSS selectors. Specific target selectors include .mermaid .cluster rect for subgraph background containers, .mermaid .node rect, .mermaid .node polygon, and .mermaid .node circle for varied node geometry shapes, .mermaid .nodeLabel for text color consistency, and .mermaid .edge-pattern-solid for connection links.

    build_grouped_nav()

    Visibility: Public
    Signature: def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:

    Description:
    Recursively traverses an LLM-generated section hierarchy tree and constructs formatted YAML lines for the MkDocs navigation tree. For each section node, it generates section headings and recurses into nested children branches with adjusted indentation. For leaf modules referenced under the modules key, it matches each module name against the chapter_files lookup list to locate the generated filename and appends the properly indented nav link.

    Parameters: * sections (list): A list of dictionaries representing the section hierarchy. Each dictionary may contain "name" (str), optional "children" (list[dict]), and optional "modules" (list[str]). * chapter_files (list): A list of dictionaries mapping generated chapter metadata. Each dictionary must contain "module_name" (str) and "filename" (str). * indent (int, optional): The indentation spacing in characters for the current depth. Defaults to 4.

    Returns: * list[str]: A list of strings, where each string represents a formatted YAML line in the MkDocs navigation hierarchy.

    Raises: * No explicit exceptions are raised by this function.

    Example: 

    def build_grouped_nav(sections: list, chapter_files: list, indent: int = 4) -> list[str]:
    lines = []
    pad = " " * indent
    for section in sections:
        lines.append(f"{pad}- {section['name']}:")
        if "children" in section:
            lines.extend(build_grouped_nav(section["children"], chapter_files, indent + 2))
        for mod_name in section.get("modules", []):
            match = next((cf for cf in chapter_files if cf["module_name"] == mod_name), None)
            if match:
                display = mod_name.split(".")[-1] if "." in mod_name else mod_name
                lines.append(f"{pad}  - '{display}': 'api/{match['filename']}'")
    return lines

    The matching routine extracts leaf display titles by taking the final segment of dot-separated module paths (mod_name.split(".")[-1]), simplifying module names in the UI navigation while retaining absolute target paths pointing to 'api/{match["filename"]}'. If a module in section["modules"] does not exist in chapter_files, match resolves to None and the entry is safely skipped without throwing an exception.

    collect_all_modules()

    Visibility: Public
    Signature: def collect_all_modules(sections: list) -> set:

    Description:
    Recursively traverses a section hierarchy tree and collects all unique module names referenced across all sections and sub-sections into a single Python set. This helper is used by graph orchestration nodes to determine which modules were successfully categorized into the documentation navigation tree versus those left unassigned.

    Parameters: * sections (list): A list of dictionary objects representing the hierarchical section structure, with optional "modules" lists and "children" sub-trees.

    Returns: * set: A set of all unique module name strings found throughout the section tree.

    Raises: * No explicit exceptions are raised by this function.

    Example: 

    def collect_all_modules(sections: list) -> set:
    result = set()
    for section in sections:
        result.update(section.get("modules", []))
        if "children" in section:
            result.update(collect_all_modules(section["children"]))
    return result

    The function handles arbitrary nesting depth by checking for the presence of the "children" key in each section dictionary and recursively calling itself. The base collection step uses set.update() with section.get("modules", []) to avoid KeyError exceptions when sections contain only child branches without direct module assignments.
