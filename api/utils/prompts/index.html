    utils.prompts

    Source File: utils/prompts.py

    Technical Overview

    The utils.prompts module contains reusable, inline prompt-construction routines used across pipeline execution nodes within the Codebase-Knowledge-Builder architecture. Unlike user-facing documentation templates that are loaded dynamically from mode-specific filesystem templates (e.g., prompts/{mode}/), the prompt builders housed in this module support internal orchestration tasks, such as code file classification and inter-chapter summary generation.

    Centralizing programmatic prompt assembly into dedicated factory functions decouples prompt wording and formatting constraints from node logic (such as DeterministicFileMapper or subsequent chapter summarization steps in nodes). This design ensures consistency in expected output formatting (such as requiring explicit YAML blocks for indices) and provides deterministic LLM steering across different documentation generation pipelines.

    Architectural Context

    The functions defined in utils.prompts are utilized at distinct phases in the generation workflow:

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description:
    Constructs an instruction prompt used primarily by DeterministicFileMapper in api-reference mode to filter out non-executable or auxiliary files. The prompt instructs the LLM to analyze a raw codebase file index and identify files that contain actual code modules (APIs, functions, classes, core business logic) while explicitly excluding UI layouts, configuration files, static assets, build configuration files, and documentation. The prompt specifies a strict structured YAML format returning only numeric indices corresponding to the code files.

    Parameters: * project_name (str): The name of the project or repository being analyzed. * file_listing (str): A formatted string representation of indexed codebase files, typically numbered by index.

    Returns: * str: A formatted prompt string containing explicit filtering guidelines and output format constraints.

    Raises: * No explicit exceptions are raised by this function.

    Implementation: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The string interpolation injects project_name and file_listing into a pre-structured template. The prompt enforces negative constraints by explicitly enumerating non-code extensions and categories (such as .xaml, .storyboard, .html, .xml, .json, .manifest, .ini, .csproj, and .sln). It also enforces structural constraint compliance by mandating a markdown YAML block (```yaml\n- 0\n...) containing strictly integer file indices, which allows downstream nodes to parse the response deterministically.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description:
    Constructs a prompt that requests a structured technical summary of a newly generated documentation chapter. This summary is used to maintain cross-chapter context in multi-chapter generation runs, ensuring subsequent chapters have technical visibility into preceding architectural decisions, interfaces, and shared components.

    The prompt requires the LLM to structure its response across four precise technical dimensions, allocating 3–5 concise technical sentences per dimension: 1. Component Scope & Responsibility: Core technical domain, problem space, and role in the system. 2. Key Technical Elements: Specific classes, services, functions, data models, or protocols. 3. Implementation Patterns & Architecture: Design patterns, communication protocols, data flows, error handling, and security mechanisms. 4. System Integration & Dependencies: Inter-component interfaces, consumed and provided services, and integration points.

    If the requested output language is not English, a localization instruction is prepended to enforce language consistency.

    Parameters: * chapter_num (int): The numerical index or chapter number within the overall document outline. * abstraction_name (str): The title or abstraction boundary name covered by the chapter. * chapter_content (str): The full markdown text of the generated chapter to be summarized. * language (str, optional): Target language for the summary output. Defaults to "english".

    Returns: * str: The complete prompt string instructing the LLM to produce a 4-point structured technical summary.

    Raises: * No explicit exceptions are raised by this function.

    Implementation: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str,
                                  chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter.

    Used after each chapter is generated to create a concise technical summary
    for cross-chapter context. The summary is fed into subsequent chapters'
    prompts so the LLM maintains coherence across the full document.

    The summary captures 4 technical dimensions with 3-5 sentences each:
    1. Component scope & responsibility
    2. Key classes/services/functions and their roles  
    3. Implementation patterns & architectural decisions
    4. Inter-component interfaces & dependencies
    """
    lang_instruction = (
        f"Write the entire summary in {language.capitalize()}. "
        if language.lower() != "english" else ""
    )
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The function conditionally builds lang_instruction by checking language.lower() != "english". When non-English output is requested, an explicit command prefix (Write the entire summary in {language.capitalize()}.) is added at the beginning of the prompt. The remainder of the prompt defines the technical rubrics followed by a markdown separator, the chapter header (Chapter {chapter_num}: {abstraction_name}), and the raw chapter_content.
