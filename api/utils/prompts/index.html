    utils.prompts

    File: utils/prompts.py

    The utils.prompts module provides programmatic, inline prompt constructors and configuration generators for internal pipeline nodes within Codebase-Knowledge-Builder. Unlike the dynamic file-based prompt templates loaded from the prompts/{mode}/ directory, the builders in this module generate standardized, deterministic prompt strings and static configuration files required by core nodes during file filtering, chapter summarization, and documentation site generation.

    Architectural Role and Workflow

    The functions in utils.prompts are utilized across different stages of the documentation pipeline:

    1. File Filtering Stage: build_code_file_filter_prompt formats file manifests into structured prompts so that LLM evaluation nodes (e.g., DeterministicFileMapper) can isolate true code modules from configuration, markup, assets, and project scaffolding.
    2. Iterative Summarization Stage: build_chapter_summary_prompt generates four-dimensional technical brief extraction prompts after a chapter is written, producing context injected into subsequent chapter generation passes.
    3. Artifact Generation Stage: build_mkdocs_config transforms hierarchical navigation snippets into a production-ready mkdocs.yml configuration targeting the Material for MkDocs theme.

    Module-Level Functions

    build_code_file_filter_prompt()

    Visibility: Public
    Signature: def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:

    Description: Constructs the system/user instruction prompt passed to language models in api-reference mode to distinguish executable source code modules from non-code project files. The prompt presents the complete codebase file index alongside explicit exclusion rules (filtering out UI layouts, XML/JSON configs, static assets, and build manifests) and commands the model to return strictly a YAML list of numerical file indices.

    Parameters: * project_name (str): The name or identifier of the target codebase. * file_listing (str): A pre-formatted, numbered or indexed manifest of all files discovered in the target repository.

    Returns: * str: A formatted prompt ready for direct submission to an LLM completion API.

    Raises: * This function does not explicitly raise exceptions; standard string formatting operations apply.

    Example: 

    def build_code_file_filter_prompt(project_name: str, file_listing: str) -> str:
    """Build the prompt for DeterministicFileMapper to filter non-code files.

    Used in api-reference mode to identify which files are actual code modules
    (APIs, functions, classes, business logic) vs. UI layouts, configs, assets.
    """
    return (
        f"For the project `{project_name}`, here is the list of all files in the codebase:\n\n"
        f"{file_listing}\n\n"
        f"Your task is to identify WHICH of these files are ACTUAL CODE files that contain "
        f"APIs, functions, classes, or core business logic.\n"
        f"EXCLUDE: UI layouts (like .xaml, .storyboard, .html), configuration files "
        f"(like .xml, .json, .manifest, .ini), static assets, build scripts "
        f"(like .csproj, .sln), and documentation.\n\n"
        f"Return ONLY a YAML list of the file indices that should be documented as code modules.\n\n"
        f"```yaml\n- 0\n- 1\n- 3\n```"
    )

    The function relies on rigid prompt constraints to prevent output hallucinations. By providing a strict YAML template (yaml\n- 0\n- 1\n- 3\n) in the instruction, it enforces machine-parseable outputs that can be deserialized directly into integer indices by calling nodes such as DeterministicFileMapper. It specifically targets common non-code extensions across ecosystems (e.g., .xaml, .storyboard, .html, .xml, .json, .manifest, .ini, .csproj, .sln), ensuring downstream token budgets are not expended on non-executable files.

    build_chapter_summary_prompt()

    Visibility: Public
    Signature: def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str, chapter_content: str, language: str = "english") -> str:

    Description: Constructs an analytical prompt that instructs the LLM to summarize a newly generated documentation chapter into a structured technical brief across four specific architectural dimensions. This brief is subsequently retained in the execution state to maintain inter-chapter context and prevent semantic drift across subsequent chapters.

    Parameters: * chapter_num (int): The numerical index or order of the current chapter. * abstraction_name (str): The title, architectural domain, or abstraction layer represented in the chapter. * chapter_content (str): The full Markdown or text body of the generated chapter. * language (str, optional): The target natural language for the output summary. Defaults to "english".

    Returns: * str: The complete prompt instructing the model to generate a four-part structured technical brief.

    Raises: * This function does not explicitly raise exceptions.

    Example: 

    def build_chapter_summary_prompt(chapter_num: int, abstraction_name: str,
                                  chapter_content: str, language: str = "english") -> str:
    """Build the prompt for generating a technical summary of a written chapter."""
    lang_instruction = (
        f"Write the entire summary in {language.capitalize()}. "
        if language.lower() != "english" else ""
    )
    return (
        f"{lang_instruction}"
        f"Summarize the following documentation chapter as a structured technical brief. "
        f"For EACH of the 4 points below, write 3-5 concise technical sentences:\n\n"
        f"(1) **Component Scope & Responsibility**: What is the main technical domain this "
        f"chapter covers? What problems does it solve and what role does it play in the system?\n\n"
        f"(2) **Key Technical Elements**: What are the specific classes, services, functions, "
        f"data models, or protocols discussed? Name them and describe their concrete roles.\n\n"
        f"(3) **Implementation Patterns & Architecture**: What design patterns, communication "
        f"protocols, data flow strategies, error handling mechanisms, or security measures "
        f"are covered? How are they implemented?\n\n"
        f"(4) **System Integration & Dependencies**: How does this component interface with "
        f"other parts of the system? What does it consume from or provide to other components? "
        f"What are the key integration points?\n\n"
        f"---\n"
        f"Chapter {chapter_num}: {abstraction_name}\n"
        f"{chapter_content}"
    )

    The prompt construction enforces a strict technical taxonomy by segmenting the analysis into: (1) Component Scope & Responsibility, (2) Key Technical Elements, (3) Implementation Patterns & Architecture, and (4) System Integration & Dependencies. When localized documentation generation is requested (i.e., language is not "english"), the function dynamically prepends a localization directive (Write the entire summary in {language.capitalize()}.). The structured output guarantees that key architectural invariants, interface definitions, and dependency contracts remain accessible to subsequent pipeline nodes without exceeding token context limits.

    build_mkdocs_config()

    Visibility: Public
    Signature: def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:

    Description: Generates the text content for a standard mkdocs.yml configuration file supporting Material for MkDocs. It configures code block copy buttons, PyMdown Extensions syntax highlighting with line numbering anchors, inline code highlighting, and Mermaid diagram rendering via custom super-fences.

    Parameters: * site_name (str): The title of the documentation website displayed in the navigation header. * nav_yaml (str): A YAML-formatted string representing the navigation hierarchy generated by the pipeline.

    Returns: * str: The complete YAML configuration string ready to be written to mkdocs.yml.

    Raises: * This function does not explicitly raise exceptions.

    Example: 

    def build_mkdocs_config(site_name: str, nav_yaml: str) -> str:
    """Build a complete mkdocs.yml for local --mkdocs output."""
    # Extract nav items from nav_snippet (strip the "nav:" header line)
    nav_lines = nav_yaml.split("\n")
    nav_body = "\n".join(nav_lines[1:]) if nav_lines else ""

    return (
        f"site_name: '{site_name}'\n"
        f"theme:\n"
        f"  name: material\n"
        f"  features:\n"
        f"    - content.code.copy\n"
        f"markdown_extensions:\n"
        f"  - pymdownx.highlight:\n"
        f"      anchor_linenums: true\n"
        f"      use_pygments: true\n"
        f"  - pymdownx.superfences:\n"
        f"      custom_fences:\n"
        f"        - name: mermaid\n"
        f"          class: mermaid\n"
        f"          format: !!python/name:pymdownx.superfences.fence_code_format\n"
        f"  - pymdownx.inlinehilite\n"
        f"nav:\n"
        f"  - Home: index.md\n"
        f"{nav_body}\n"
    )

    The function extracts individual navigation entries by splitting nav_yaml across newline boundaries and stripping the initial nav: declaration line via \n.join(nav_lines[1:]). It then embeds the resulting indented navigation tree beneath a hardcoded - Home: index.md root item. The configuration registers the pymdownx.superfences custom fence using the Python class resolver !!python/name:pymdownx.superfences.fence_code_format, enabling client-side rendering of embedded Mermaid diagrams.
