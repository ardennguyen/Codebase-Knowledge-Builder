    i18n.py

    Source: utils/i18n.py

    Technical Overview

    While files.py structures and slices raw codebase files for language model consumption during the knowledge extraction process, utils/i18n.py provides the runtime internationalization engine responsible for localizing user-facing CLI strings. Specifically, it monitors missing localized UI strings in utils/strings.csv, orchestrates automatic translation using external Large Language Models (LLMs), and synchronizes the translated entries back to disk.

    Architecturally, this module was extracted from utils/output.py to break a severe circular dependency chain: output.py $\rightarrow$ call_llm.py $\rightarrow$ token_utils.py $\rightarrow$ output.py. By isolating LLM-driven translation into i18n.py, the CLI output subsystem delegates translation tasks dynamically without binding core logging facilities directly to LLM inference drivers. i18n.py serves as the sole boundary where the output system imports call_llm.py.

    The translation pipeline operates in batch mode. When a non-English language is requested, the system reads strings.csv using the UTF-8 Byte Order Mark (utf-8-sig) encoding to ensure cross-platform spreadsheet and filesystem compatibility. It scans for absent columns or empty translation cells, structures all missing strings into a JSON payload, injects them into the translation prompt template (prompts/common/translate_strings.md), and invokes call_llm.py. The extracted translations are parsed via regular expressions to handle non-JSON conversational wrapping safely, merged into the tabular dataset, and committed back to strings.csv.

    Phase 1: Precondition Checks and Guard Clauses

        True if translations were written (caller should reload strings), False otherwise.
    """

        return False

    The routine begins by performing lazy local imports of emit_raw from utils.output, avoiding circular import penalties during startup. It checks if the requested target column is "english"; if so, it immediately returns False because English is the canonical baseline language and requires no synthesis. Next, it validates that csv_path is both non-empty and points to an existing file on the filesystem; otherwise, execution halts cleanly without attempting file operations.

    Phase 2: Missing Translation Discovery and Row Parsing

        # Collect strings that have no translation in the target language column
    missing = {}
    is_new_column = False
    with open(csv_path, encoding="utf-8-sig") as f:
        reader = csv.DictReader(f)
        fieldnames = list(reader.fieldnames)
        is_new_column = lang_col not in fieldnames
        for row in reader:
            key = row.get("STRING_KEY", "").strip()
            if not key or key.startswith("#"):
                continue
            # Check if the language column exists and has a value
            lang_text = row.get(lang_col, "").strip() if lang_col in fieldnames else ""
            if lang_text:
                continue  # Already translated

            english_text = row.get("english", "").strip()
            if english_text:
                missing[key] = english_text

    if not missing:
        return False
    This phase reads the localization source file using utf-8-sig encoding, initializing a csv.DictReader instance to parse header names and row mappings. The method checks whether lang_col already exists within fieldnames and flags is_new_column accordingly. It loops through all entries, skipping empty keys and comment rows marked with #. If the target column is missing or contains only whitespace for a given key, the canonical "english" string is extracted and registered into the missing dictionary. If missing contains no elements, all strings are up to date, and the function exits returning False.

    Phase 3: Prompt Construction and LLM Inference

        emit_raw("PROGRESS", f"[i18n] New language '{language}' — adding column to strings.csv")
    emit_raw("PROGRESS", f"[i18n] {len(missing)} strings need translation to {language}")

The module lazily imports call_llm from call_llm.py and serializes the missing dictionary into formatted JSON using json.dumps(..., ensure_ascii=False). It locates and reads the markdown prompt template located at prompts/common/translate_strings.md, populating its template variables {language} and {entries}. The rendered prompt is dispatched via call_llm alongside the configured caching policy (use_cache) and reasoning budget (thinking_level).

    Phase 4: Response Extraction, Serialization, and Persistence

    except Exception as e:

If a match is found, it is deserialized into a Python dictionary and committed to disk via the internal helper _write_translations_to_csv. A SUCCESS status is logged and True is returned. If JSON extraction fails or any unexpected I/O or network exception occurs, a WARNING is emitted, and False is returned so the caller falls back to English defaults gracefully.

    Internal Helpers

    _write_translations_to_csv()

    Visibility: Private / Internal
    Signature: def _write_translations_to_csv(csv_path, lang_col, fieldnames, translations) -> None:

    Description: Reads existing rows from strings.csv, updates missing keys with their newly translated values, adds the language column to the header list if previously absent, and writes the updated records back to disk using UTF-8 BOM encoding.

    def _write_translations_to_csv(csv_path, lang_col, fieldnames, translations):
    """Write LLM translations back into strings.csv, persisting them for future runs.

    If the target language column doesn't exist, it is added to the CSV.
    """
    rows = []

    with open(csv_path, encoding="utf-8-sig") as f:
        reader = csv.DictReader(f)
        fieldnames = list(reader.fieldnames)
        # Add language column if it doesn't exist
        if lang_col not in fieldnames:
            fieldnames.append(lang_col)
        for row in reader:
            key = row.get("STRING_KEY", "").strip()
            if key in translations:
                row[lang_col] = translations[key]
            rows.append(row)

    # Write with BOM so Excel opens as UTF-8 without extra import steps
    with open(csv_path, "w", encoding="utf-8-sig", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=fieldnames)
        writer.writeheader()
        writer.writerows(rows)

    The function executes a read-modify-write workflow on strings.csv. It first opens the CSV with encoding="utf-8-sig", reads the header schema via csv.DictReader, and dynamically appends lang_col to fieldnames if it was not already present. It iterates over each record; when a record's STRING_KEY is present in the translations dictionary, the corresponding dictionary value is assigned to row[lang_col]. All mutated and unmutated rows are preserved in order within the rows list. Finally, it reopens the file in write mode ("w"), ensuring newline="" and encoding="utf-8-sig". Using csv.DictWriter, it flushes the updated headers and all rows back to disk, ensuring that downstream runs and external spreadsheet applications (such as Microsoft Excel) correctly interpret multi-byte Unicode strings without encoding corruption.

    Parameters: * csv_path (str): Absolute filesystem path to strings.csv. * lang_col (str): Target column name to add or populate (e.g., "vietnamese"). * fieldnames (list[str]): List of column names discovered in the CSV header during initial reading. * translations (dict[str, str]): Key-value map of string keys to translated text values.

    Returns: * None: Mutates the file directly on the filesystem.

    Raises: * OSError: If the file cannot be opened for reading or written to due to permissions or missing directory paths. * csv.Error: If parsing or writing the CSV data encounters serialization errors.

    Example: 

    # Actual internal usage inside auto_translate():
_write_translations_to_csv(csv_path, lang_col, fieldnames, translations)

    Data Structures

    strings.csv Row Schema

    The structure representing individual localization records stored on disk and read into memory via csv.DictReader:

    Field Type Description
    STRING_KEY str Unique uppercase identifier for the UI string (e.g., CLI_STARTING, ERROR_OCCURRED), or a comment starting with #.
    english str The canonical English baseline text used as the translation source and default fallback.
    <lang_col> str Dynamically discovered or appended lowercase target language column (e.g., vietnamese, french, japanese).

    Missing Translations Dictionary (missing)

    In-memory dictionary collected during CSV scanning and serialized as JSON for prompt formatting:

    Field Type Description
    key str The string identifier (STRING_KEY) matching untranslated entries.
    value str The baseline English text (english) that needs translation. 
    {
  "CLI_STARTING": "Starting codebase analysis...",
  "PROGRESS_PARSING": "Parsing source files..."
}

    LLM Translations Response (translations)

    In-memory dictionary decoded from the LLM's JSON response payload:

    Field Type Description
    key str The string identifier (STRING_KEY) matching the translated entry.
    value str The generated localized string in the requested target language. 
    {
  "CLI_STARTING": "Bắt đầu phân tích mã nguồn...",
  "PROGRESS_PARSING": "Đang phân tích các tệp nguồn..."
}

    Error Handling

    The module adheres to a defensive isolation design to ensure localization issues never crash core documentation pipelines:

    • English Bypass: When lang_col == "english", auto_translate() immediately exits with False. English is the reference implementation language, preventing unnecessary file mutations or API requests.
    • Missing File Safeguard: If csv_path is falsy or os.path.exists(csv_path) fails, execution returns False immediately, allowing consumers to fall back gracefully to default text.
    • Malformed JSON Recovery: The LLM's response is parsed using regex (re.search(r"\{[^{}]*(?:\{[^{}]*\}[^{}]*)*\}", response, re.DOTALL)) to strip conversational markdown fences or preambles. If valid JSON cannot be found or json.loads() fails, the function logs [i18n] LLM response did not contain valid JSON — falling back to English and returns False.
    • Catch-All Exception Guard: The entire translation and disk persistence phase is enclosed in a broad except Exception as e: block. Network failures, API rate limits, file permission errors, or parsing bugs are trapped, logged as WARNING, and handled by falling back to English strings.
    • BOM Normalization: File I/O operations strictly enforce encoding="utf-8-sig". This transparently consumes Byte Order Marks on read and writes them on disk, preserving multi-byte UTF-8 Unicode characters when edited by external spreadsheet tools across Windows, macOS, and Linux.
