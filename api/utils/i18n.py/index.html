    i18n.py

    Source: utils/i18n.py

    Technical Overview

    The utils/i18n.py module provides an automated runtime internationalization (i18n) and translation synchronization engine for the application's user interface strings. It inspects the localization catalog (strings.csv), identifies missing or untranslated UI messages for a specified target language, compiles an inference payload, and dispatches a translation request via a configured Large Language Model (LLM). Once translated, the module dynamically extends the schema of strings.csv (adding language columns as needed) and persists the updated string catalog to disk using UTF-8 with Byte Order Mark (utf-8-sig) encoding.

    Architecturally, this module was decoupled from utils/output.py to resolve a critical circular dependency chain: output.py $\rightarrow$ call_llm.py $\rightarrow$ token_utils.py $\rightarrow$ output.py. Under this decoupled architecture, utils.output delegates missing string resolution to utils.i18n, isolating all direct interactions with utils.call_llm and utils.token_utils inside this single module.

    The translation pipeline operates non-destructively: if the target language is already English, if the localization datastore does not exist, or if an inference error occurs, the module logs diagnostic telemetry and safely falls back to English without halting downstream application execution.

    Public API

    auto_translate()

    Visibility: Public

    Signature: def auto_translate(lang_col, language, csv_path, use_cache, thinking_level):

    Description: Orchestrates the automated translation of missing localized strings. It checks whether translations are required, prepares and formats a translation prompt with missing English key-value pairs, logs token estimations, invokes the LLM through call_llm(), parses the JSON response via regular expressions, and updates strings.csv.

    Because this function coordinates several discrete logical sub-tasks—file inspection, prompt compilation, LLM querying, and disk serialization—its implementation is analyzed across four logical phases below.

    Phase 1: Pre-condition Validation and String Scanning

        from utils.output import emit_raw

    if lang_col == "english":
        return False

    if not csv_path or not os.path.exists(csv_path):
        return False

    # Collect strings that have no translation in the target language column
    missing = {}
    is_new_column = False
    with open(csv_path, encoding="utf-8-sig") as f:
        reader = csv.DictReader(f)
        fieldnames = list(reader.fieldnames)
        is_new_column = lang_col not in fieldnames
        for row in reader:
            key = row.get("STRING_KEY", "").strip()
            if not key or key.startswith("#"):
                continue
            # Check if the language column exists and has a value
            lang_text = row.get(lang_col, "").strip() if lang_col in fieldnames else ""
            if lang_text:
                continue  # Already translated

            english_text = row.get("english", "").strip()
            if english_text:
                missing[key] = english_text

    if not missing:
        return False

    Phase 1 evaluates fast-return conditions: if the requested language is already English or if csv_path does not exist on disk, execution terminates immediately with False. Otherwise, it opens the localization CSV file with utf-8-sig encoding using csv.DictReader. It determines whether lang_col represents a new column in the CSV schema and iterates across each row, discarding empty keys and comment rows prefixed with #. If the cell corresponding to lang_col is blank or nonexistent, the corresponding English string is extracted into the missing dictionary. If no strings require translation, the function exits early.

    Phase 2: Prompt Compilation and Token Estimation

        # Report what we found
    if is_new_column:
        emit_raw("PROGRESS", f"[i18n] New language '{language}' — adding column to strings.csv")
    emit_raw("PROGRESS", f"[i18n] {len(missing)} strings need translation to {language}")

    # Batch translate via LLM
    try:
        from utils.call_llm import call_llm

        entries_json = json.dumps(missing, ensure_ascii=False, indent=2)

        # Load prompt template from prompts/common/translate_strings.md
        prompt_path = os.path.join(
            os.path.dirname(os.path.dirname(os.path.abspath(__file__))),
            "prompts",
            "common",
            "translate_strings.md",
        )
        with open(prompt_path, encoding="utf-8") as pf:
            prompt_template = pf.read()
        prompt = prompt_template.format(language=language, entries=entries_json)

        emit_raw("PROGRESS", f"[i18n] Calling LLM to translate {len(missing)} strings...")
        from utils.token_utils import log_token_estimation, resolve_max_tokens

        try:
            context_tokens = resolve_max_tokens({})
        except Exception:
            context_tokens = 0
        log_token_estimation("TranslateStrings", prompt, context_tokens)

    In Phase 2, telemetry notifications are broadcast to the user interface via emit_raw(), informing consumers of column additions and the count of pending strings. The missing string dictionary is serialized into a formatted JSON string (entries_json) with Unicode preservation (ensure_ascii=False). The function then dynamically resolves the absolute path to prompts/common/translate_strings.md, reads the template, and interpolates the target language name and entries JSON. Token budgeting is performed by resolving maximum available context tokens via resolve_max_tokens({}) and recording metrics through log_token_estimation().

    Phase 3: Model Invocation and JSON Extraction

            response = call_llm(prompt, use_cache=use_cache, thinking_level=thinking_level, step="translate_strings")

        # Extract JSON from response
        json_match = re.search(r"\{[^{}]*(?:\{[^{}]*\}[^{}]*)*\}", response, re.DOTALL)
        if json_match:
            translations = json.loads(json_match.group())
            translated_count = len(translations)

            # Write translations back into strings.csv
            _write_translations_to_csv(csv_path, lang_col, fieldnames, translations)
            emit_raw("SUCCESS", f"[i18n] Translated {translated_count}/{len(missing)} strings — saved to strings.csv")
            return True
        emit_raw("WARNING", "[i18n] LLM response did not contain valid JSON — falling back to English")

    Phase 3 executes the model inference request using call_llm(), tagging the execution step as "translate_strings" and forwarding caller-specified caching and reasoning levels. Because language models may wrap responses in explanatory conversational text or code block markers, an extraction regex (r"\{[^{}]*(?:\{[^{}]*\}[^{}]*)*\}") scans the raw text with re.DOTALL to isolate the root JSON object. If a matching JSON payload is found, it is deserialized into a Python dictionary. The helper _write_translations_to_csv() is invoked to persist results to disk, an informational success message is emitted, and True is returned. If parsing fails, a warning is broadcast.

    Phase 4: Exception Handling and Fallback

        except Exception as e:
        emit_raw("WARNING", f"[i18n] Translation failed: {e} — falling back to English")

    return False

    Phase 4 serves as the fallback boundary. The entire inference, estimation, and deserialization block is encapsulated in an untyped try...except Exception clause. If any step fails—such as prompt file I/O errors, network disconnections during LLM execution, token calculation issues, or malformed JSON payloads—the exception is trapped, a descriptive warning is emitted using emit_raw(), and the function returns False. This guarantees that localization failures never crash the host application.

    Parameters:

    • lang_col (str): Lowercase column name representing the language in strings.csv (e.g., "vietnamese", "japanese").
    • language (str): Capitalized human-readable language display name passed to the prompt template (e.g., "Vietnamese").
    • csv_path (str): Absolute filesystem path to the target strings.csv datastore.
    • use_cache (bool): Flag determining whether LLM response caching is enabled in call_llm().
    • thinking_level (str | None): Model reasoning effort parameter passed to call_llm().

    Returns:

    • bool: True if new translations were received and persisted to the CSV file (indicating that the caller should invalidate and reload in-memory string caches); False if no changes occurred or if translation failed.

    Raises:

    • Does not raise exceptions; all internal runtime exceptions are caught and logged as warnings.

    language="Vietnamese",
    csv_path="/path/to/project/utils/strings.csv",
    use_cache=True,

    Internal Helpers

    _write_translations_to_csv()

    Visibility: Private

    Signature: def _write_translations_to_csv(csv_path, lang_col, fieldnames, translations):

    Description: Persists newly generated translation mappings into strings.csv. It reads the entire file into memory using csv.DictReader to preserve existing translations, appends lang_col to fieldnames if it does not already exist, maps new translated values against row keys, and writes the updated dataset back to disk via csv.DictWriter. The destination file is opened with utf-8-sig encoding and empty newline termination (newline="") to ensure compatibility with spreadsheet editors like Microsoft Excel without character corruption.

    def _write_translations_to_csv(csv_path, lang_col, fieldnames, translations):
    """Write LLM translations back into strings.csv, persisting them for future runs.

    If the target language column doesn't exist, it is added to the CSV.
    """
    rows = []

    with open(csv_path, encoding="utf-8-sig") as f:
        reader = csv.DictReader(f)
        fieldnames = list(reader.fieldnames)
        # Add language column if it doesn't exist
        if lang_col not in fieldnames:
            fieldnames.append(lang_col)
        for row in reader:
            key = row.get("STRING_KEY", "").strip()
            if key in translations:
                row[lang_col] = translations[key]
            rows.append(row)

    # Write with BOM so Excel opens as UTF-8 without extra import steps
    with open(csv_path, "w", encoding="utf-8-sig", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=fieldnames)
        writer.writeheader()
        writer.writerows(rows)

    The function executes a complete in-memory read-modify-write cycle. When appending a new column, the updated fieldnames list is captured dynamically from the active file rather than relying exclusively on caller arguments, mitigating race conditions where columns may have shifted. As it loops through each record, keys present in the translations dictionary update the corresponding row's lang_col entry in-place. Finally, csv.DictWriter.writeheader() and writerows() serialize the mutated state back to csv_path with BOM encoding.

    Parameters:

    • csv_path (str): Absolute filesystem path to the strings.csv file.
    • lang_col (str): Lowercase target language column identifier to update or append.
    • fieldnames (list[str]): List of current header field names extracted from strings.csv.
    • translations (dict[str, str]): Mapping of string keys to their translated values returned by the LLM.

    Returns:

    • None: Mutates the file system artifact in-place.

    Raises:

    • OSError: If the target CSV file cannot be opened for reading or writing due to filesystem permissions.
    • csv.Error: If CSV formatting or field mismatch anomalies occur during writing.

    Example:

    # Direct implementation usage from auto_translate()
_write_translations_to_csv(
    csv_path="/workspace/utils/strings.csv",
    lang_col="vietnamese",
    fieldnames=["STRING_KEY", "english"],
    translations={
        "PROGRESS_ANALYZING": "Đang phân tích mã nguồn...",
        "ERROR_FILE_NOT_FOUND": "Không tìm thấy tệp tin.",
    },
)

    Data Structures

    The module does not declare custom object classes; instead, it manipulates structured dictionaries and CSV datastores.

    strings.csv Schema

    Represents the physical schema of the persistent tabular localization datastore:

    Field Type Description
    STRING_KEY str Unique uppercase identifier for the UI string. Lines beginning with # are treated as comments and ignored.
    english str Canonical source text in English, used as the fallback and translation baseline.
    [lang_col] str Dynamic target language columns (e.g., vietnamese, japanese, spanish) containing translated string values.

    Missing Strings Payload

    The internal dictionary constructed in Phase 1 and serialized as entries_json for prompt injection:

    Key Type Description
    [STRING_KEY] str Mapping key representing the untranslated identifier (e.g., "PROMPT_RUNNING").
    value str The corresponding baseline English string to be translated.

    Example structure: 

    {
  "STAGE_EXTRACT_FACTS": "Extracting architectural facts from codebase...",
  "WARN_FILE_BINARY": "Skipping binary file {path}"
}

    LLM Translations Response Payload

    The parsed dictionary extracted from the LLM's raw text response:

    Key Type Description
    [STRING_KEY] str String key corresponding to a requested key from the missing dictionary.
    value str Translated localized string ready to be inserted into the target column.

    Example structure: 

    {
  "STAGE_EXTRACT_FACTS": "Trích xuất các dữ kiện kiến trúc từ mã nguồn...",
  "WARN_FILE_BINARY": "Bỏ qua tệp nhị phân {path}"
}

    Error Handling

    The module implements a robust, non-terminating error-handling strategy to ensure that localization failures do not disrupt the broader execution pipeline:

    • Short-Circuit Bypass: Calls targeting "english" or pointing to a non-existent CSV path exit immediately returning False, bypassing all network and disk overhead.
    • Comment and Blank Filtering: When processing rows from strings.csv, empty string keys or rows where STRING_KEY begins with # are skipped.
    • Broad Exception Shield: The entire translation sequence—encompassing prompt formatting, token estimation, network inference, and response parsing—is guarded by a top-level except Exception block. Errors are caught, surfaced to the UI via emit_raw("WARNING", ...), and resolved by falling back to English strings.
    • Regex-Based JSON Recovery: Model outputs often contain markdown formatting fences or conversational framing. The module uses re.search(r"\{[^{}]*(?:\{[^{}]*\}[^{}]*)*\}", response, re.DOTALL) to locate and isolate the core JSON object before invoking json.loads().
    • Safe Encoding Practices: All file reads and writes explicitly designate encoding="utf-8-sig". This ensures byte-order marks are properly recognized across POSIX and Windows environments and prevents text corruption in external editors.
