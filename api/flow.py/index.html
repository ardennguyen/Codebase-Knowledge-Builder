    flow.py

    Source: flow.py

    Building upon the token telemetry, context budgeting, and counting infrastructure detailed in token_utils.py, the flow.py module defines the top-level orchestration graph for the codebase analysis and documentation compilation pipeline. It acts as the structural assembly layer that binds domain-specific pipeline tasks into an executable Directed Acyclic Graph (DAG) using the lightweight pocketflow framework.

    Technical Overview

    flow.py is responsible for defining the computational pipeline that ingests source code, decomposes architecture into abstractions, determines reading order, and synthesizes technical tutorial chapters. It establishes a multi-path graph topology that dynamically adapts to repository context sizes through declarative routing operators. Rather than implementing node processing logic directly, flow.py instantiates processing nodes defined in nodes.py and binds them with directed edge abstractions (>>) and conditional dispatch keys (- "route" >>).

    The execution topology centers around three primary extraction pathways governed by context window budgeting: 1. Direct Path ("direct"): Dispatches small-to-medium codebases directly to holistic abstraction identification (IdentifyAbstractions), evaluating system components within a single prompt context. 2. Batch Path ("batch"): Routes larger codebases through a Map-Reduce architecture (MapAbstractions followed by ReduceAbstractions), partitioning file batches across multiple LLM inferences before synthesizing a unified abstraction model. 3. Deterministic Path ("deterministic"): Bypasses heuristic model discovery for massive repositories, employing structural filesystem heuristics (DeterministicFileMapper) to directly assemble chapter outlines without saturation or intermediate relationship passes.

    All execution branches converge downstream into chapter synthesis (WriteChapters) and final artifact concatenation (CombineTutorial), yielding a cohesive technical document. Built-in retry parameters (max_retries=5, wait=20) are configured across network-bound and inference-heavy nodes to guard against intermittent API failures and rate limits.

    Public API

    create_tutorial_flow()

    Visibility: Public
    Signature: def create_tutorial_flow() -> Flow:

    Description: Instantiates all pipeline execution nodes, configures resilience parameters (retries and backoff delays), binds edge topologies including conditional routing branches, and returns the compiled pocketflow.Flow executable graph rooted at the repository fetch node.

    Parameters: * None.

    Returns: * Flow: An initialized pocketflow.Flow instance whose root entry point is bound to FetchRepo.

    Raises: * No explicit exceptions are raised during flow composition. Runtime execution exceptions originating from node actions (e.g., API failures or filesystem errors) propagate according to PocketFlow's execution lifecycle.

    Phase 1: Pipeline Node Instantiation and Retry Policy Configuration

    def create_tutorial_flow():
    fetch_repo = FetchRepo()
    context_router = ContextRouter()
    map_abstractions = MapAbstractions(max_retries=5, wait=20)
    reduce_abstractions = ReduceAbstractions(max_retries=5, wait=20)
    identify_abstractions = IdentifyAbstractions(max_retries=5, wait=20)
    analyze_relationships = AnalyzeRelationships(max_retries=5, wait=20)
    order_chapters = OrderChapters(max_retries=5, wait=20)
    write_chapters = WriteChapters(max_retries=5, wait=20)
    combine_tutorial = CombineTutorial()
    deterministic_mapper = DeterministicFileMapper(max_retries=5, wait=20)
    In this initialization phase, each node component is constructed into an independent execution unit. The non-LLM nodes—FetchRepo, ContextRouter, and CombineTutorial—are instantiated with default parameters since they execute deterministic filesystem operations or fast state transformations. Conversely, all nodes interacting directly with language models through utils/call_llm.py or performing complex heuristic mapping (MapAbstractions, ReduceAbstractions, IdentifyAbstractions, AnalyzeRelationships, OrderChapters, WriteChapters, and DeterministicFileMapper) are initialized with max_retries=5 and wait=20. This uniform fault-tolerance policy ensures that upstream API timeouts, temporary rate-limiting, and network drops are absorbed with a 20-second backoff before any stage raises an unhandled failure.

    Phase 2: Ingestion and Dynamic Routing Binding

        fetch_repo >> context_router

    context_router - "direct" >> identify_abstractions
    context_router - "batch" >> map_abstractions
    context_router - "deterministic" >> deterministic_mapper
    The flow topology begins by linking the repository fetcher directly to the context router via the bitwise shift operator (>>), establishing fetch_repo as the predecessor of context_router. Following repository crawling, context_router performs dynamic branch evaluation based on total token volume calculated via utils/token_utils.py. The subtraction operator (- "key" >>) creates conditional branches within PocketFlow: returning "direct" routes context to identify_abstractions for single-pass analysis; returning "batch" initiates partition-based mapping via map_abstractions; and returning "deterministic" dispatches execution to deterministic_mapper to handle oversized codebases without deep model extraction.

    Phase 3: Architectural Abstraction Extraction Paths

        map_abstractions >> reduce_abstractions

    identify_abstractions >> analyze_relationships
    reduce_abstractions >> analyze_relationships
    This phase defines the convergence mechanics of the architectural abstraction tier. In the batch pathway, map_abstractions streams chunked abstraction outputs into reduce_abstractions, which synthesizes disparate component lists into a unified system model. Both the unified batch results from reduce_abstractions and the single-pass results from identify_abstractions connect into analyze_relationships. Regardless of whether single-pass identification or Map-Reduce abstraction was selected, analyze_relationships receives identical context representations to map dependencies, call hierarchies, and architectural boundaries across abstractions.

    Phase 4: Downstream Synthesis Convergence and Flow Encapsulation

        analyze_relationships >> order_chapters
    order_chapters >> write_chapters

    deterministic_mapper >> write_chapters

    write_chapters >> combine_tutorial

    return Flow(start=fetch_repo)
    The final phase establishes chapter progression and document aggregation. For repositories processed through model-driven abstraction identification, analyze_relationships passes the architectural graph to order_chapters to establish a pedagogical reading order, which subsequently flows into write_chapters. For repositories routed via deterministic_mapper, structural directory mappings bypass relationship and chapter-ordering analysis entirely and feed directly into write_chapters. Once chapter generation completes, all content converges at combine_tutorial, which writes the finalized Markdown documentation and static site artifacts to disk. The entire graph is encapsulated in a Flow instance initialized with start=fetch_repo and returned to the caller.

    Example: 

    # Invocation of create_tutorial_flow within the application entry point (main.py)
from flow import create_tutorial_flow

tutorial_flow = create_tutorial_flow()
shared_context = {
    "repo_path": "https://github.com/example/repo",
    "output_dir": "./output",
}
tutorial_flow.run(shared_context)

    Internal Helpers

    The flow.py module defines no private or internal helper functions; all orchestration logic is encapsulated within the public factory function create_tutorial_flow().

    Data Structures

    Pipeline Context State Schema

    While flow.py defines graph connectivity rather than explicit data structures, the nodes coordinated by this flow share and mutate a centralized dictionary context throughout execution. The following schema documents the keys read, created, and transformed across the DAG:

    Key Type Producing Node(s) Consuming Node(s) Description
    repo_path str Runtime initialization (main.py) FetchRepo Filesystem directory path or remote Git repository URL.
    include_patterns set[str] | None Runtime initialization (main.py) FetchRepo Optional glob whitelist for crawler filtering.
    exclude_patterns set[str] Runtime initialization (main.py) FetchRepo Combined file exclusion globs (derived from exclude_patterns.py and CLI flags).
    files dict[str, str] FetchRepo ContextRouter, IdentifyAbstractions, MapAbstractions, DeterministicFileMapper, WriteChapters Ingested repository mapping from relative POSIX filepaths to raw decoded text content.
    strategy str ContextRouter PocketFlow Routing Engine Routing decision identifier ("direct", "batch", or "deterministic").
    abstractions list[dict] IdentifyAbstractions, ReduceAbstractions, DeterministicFileMapper AnalyzeRelationships, WriteChapters Extracted architectural components, responsibility boundaries, and associated file lists.
    relationships list[dict] AnalyzeRelationships OrderChapters, WriteChapters Dependency graphs, communication interfaces, and cross-abstraction references.
    ordered_chapters list[dict] OrderChapters, DeterministicFileMapper WriteChapters Pedagogically sequenced outline defining chapter titles, objectives, and assigned modules.
    chapters list[dict] WriteChapters CombineTutorial Synthesized Markdown chapter payloads, including frontmatter and cross-chapter technical briefs.
    tutorial_content str CombineTutorial CLI consumer (main.py) Final compiled markdown tutorial content and site navigation structure.

    pocketflow.Flow Object Model

    The primary object returned by flow.py is an instance of pocketflow.Flow. Its structural shape and properties include:

    Attribute Type Description
    start Node The root entry point of the DAG execution pipeline (FetchRepo).
    nodes set[Node] The internal registry of all connected node instances bound into the flow graph.
    edges dict PocketFlow's internal adjacency map linking predecessor nodes to successor nodes or conditional transition mappings.

    Node Retry Policy Configuration

    Nodes bound within flow.py utilize a uniform failure recovery parameter structure:

    Parameter Type Default Value Description
    max_retries int 5 Maximum consecutive retry attempts allowed before an operation raises an unhandled exception.
    wait int 20 Fixed sleep delay in seconds enforced between successive retry attempts when a node action fails.

    Error Handling

    Error management within flow.py is configured declaratively across node bindings:

    • Retry Resiliency: Critical network-bound operations (remote LLM inference via utils/call_llm.py and complex schema parsing in nodes.py) are configured with max_retries=5 and wait=20. This ensures that transient network failures, HTTP 429 rate-limit responses, and upstream provider service interruptions do not cause immediate pipeline crashes.
    • Context Overrun Mitigation: The branching logic originating from ContextRouter guards the LLM from token exhaustion errors. By calculating token capacity prior to abstraction extraction, the graph prevents large repositories from triggering context window overflow errors in single-pass nodes, routing them instead to partitioned batching or deterministic fallback mappings.
    • Graph Topology Integrity: Because pocketflow.Flow requires a valid start node, initializing the graph with start=fetch_repo guarantees that no detached or unlinked nodes can execute out of order, preserving the strict dependency chain from repository retrieval to final artifact combination.
